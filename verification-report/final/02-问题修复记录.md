## 二、P0 问题详细记录（6 个，全部修复）

### P0-01：JWT 不验签，任意 Token 即 admin

| 项 | 内容 |
|----|------|
| 编号 | P0-01 |
| 发现模块 | 安全与性能验证 |
| 问题描述 | `src/bff/middleware/auth.ts` 的 `attachUser()` 仅检查 token 非空，直接赋予 `MOCK_USER(roles:['admin'])`，无任何签名验证。攻击者构造任意字符串作为 Bearer Token 即可获得 admin 权限访问全部 API |
| 根因分析 | 认证中间件仅做"有无 token"判断，未实现 JWT 签发/验签闭环 |
| 修复方案 | 重写 auth.ts：实现 HMAC-SHA256 JWT 签发（signJwt）与验签（verifyJwt），校验 exp/签名/时序安全比较（crypto.timingSafeEqual）；开发态仅接受 jt-/jr- 前缀演示 token，生产环境一律拒绝 |
| 修复文件 | `src/bff/middleware/auth.ts`、`src/bff/routes/auth.ts` |
| 验证结果 | 伪造 token → 401 ✅；篡改签名 → 401 ✅；合法 JWT → 200 ✅ |
| 修复时间 | 2026-09-16 |

### P0-02：错误信息泄露内部细节

| 项 | 内容 |
|----|------|
| 编号 | P0-02 |
| 发现模块 | 安全与性能验证 |
| 问题描述 | `withErrorHandler` 将 `e.message` 直接返回客户端，可能泄露 SQL 错误、文件路径、堆栈，辅助攻击者了解系统内部结构 |
| 根因分析 | 统一错误中间件未区分 4xx/5xx，5xx 原样返回异常消息 |
| 修复方案 | 5xx 统一返回"服务器内部错误，请联系管理员"+ traceId，原始错误仅服务端 console.error；4xx 返回通用业务错误码 |
| 修复文件 | `src/bff/middleware/error.ts` |
| 验证结果 | 故意触发异常仅返回通用文案 + traceId ✅ |
| 修复时间 | 2026-09-16 |

| 修复时间 | 2026-09-16 |

详见第五章，均为体验增强与长期优化项，按迭代排期落地。

## 八、经验教训与改进建议

1. **前后端契约先行**：本次 P0 问题中 5/6 与 API 契约不一致有关（路径前缀、端口、响应结构、枚举值）。建议后续项目在开发前先用 OpenAPI 契约锁定请求/响应结构，BFF 作为唯一适配层，禁止前端直接消费后端领域模型。
2. **安全中间件前置**：JWT 验签、安全头、CSRF、WS 鉴权应在骨架阶段就完成，而非功能验证阶段补救。建议将安全中间件清单纳入项目脚手架。
3. **路由注册闭环**：门诊/住院孤儿模块说明"页面开发"与"路由/菜单注册"必须同步验收。建议路由表生成器与菜单配置自动校验页面存在性。
4. **测试环境一致性**：jsdom 缺失 URL.createObjectURL 等浏览器 API 导致前端用例失败，建议在 CI 中固定 jsdom 版本并补全 polyfill 清单。
5. **注入规则持续扩充**：Prompt 注入检测率从 70.5% 提升到 100% 依赖补充 31 条规则，建议建立攻击样本回归库，每次新增规则自动跑全量样本。
6. **类型安全零容忍**：本次所有 P0/P1 修复后均以 `tsc --noEmit` 0 错误作为回归门禁，证明严格模式是拦截缺陷的最有效手段。
