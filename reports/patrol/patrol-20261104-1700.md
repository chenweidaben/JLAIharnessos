## 4. 本轮发现的三处风险

### 4.1 路由遮蔽：CPOE 必须前置注册才生效（organizer 已主动纠偏并上报）

organizer 在派发阶段曾判断「`POST /orders/:id/review` 与 `/:id/stop` 无既有冲突」，该判断**不成立**：`m570Routes.ts:177` 已注册 review、`orderVerify.ts:24` 已注册 stop，BFF 采用**首匹配胜出**。若按原指令把新路由加在末尾，这两条会被旧 stub 抢走，状态机根本不生效——测出来会是"200 但行为不对"，比报错更难发现。

子代理改为「`orderCpoeRoutes` 前置注册」接管两条路径。遮蔽安全性已复核：`web/src/services/api/care.ts` 的 `base = '/inpatient'`，前端走 `/api/v1/inpatient/orders/...`；`inpatient-care.test.ts`、`apiDocs.test.ts`、`scripts/evidence/m1b2-http-evidence.ts` 同样走 `/inpatient` 前缀 → 无调用方受损。

**副产物（登记 backlog，本轮不清理）**：`m570Routes` 的 review 与 `orderVerify` 的 stop 现为不可达死路由。清理需要通读两个路由模块的全部导出，属超出本轮边界，台账已注记位置。

### 4.2 推送期间并发提交造成三端分裂

首次推送时本地 HEAD 为 `e08b1c2f`，gitcode 推到了 `e08b1c2f`；而 mirror 推送启动前 organizer 又落了收口简报 `ff0d722e`，于是 mirror 收到 `ff0d722e`、本地也已是 `ff0d722e`，**gitcode 落后一个 commit**。三端核对立刻暴露该分裂，补推 gitcode 后对齐。

教训：组织智能体并行开发时，"push 成功"不等于"三端一致"，必须在两次 push 之后**再单独做一次 ls-remote 三端比对**，以比结果为唯一判据，而不能以 push 的 exit code 为判据。

### 4.3 运行态数据被验证动作改变（非缺陷，需知晓）

阶段一验证时对 `ORD-CO-1` 实测过一次 approve，故当前运行态该单为 `approved` 而非 seed 初始的 `pending_review`。E2E 主链跑在每次新建医嘱上，不依赖该状态，重跑不受影响；重启即恢复初始 seed。
