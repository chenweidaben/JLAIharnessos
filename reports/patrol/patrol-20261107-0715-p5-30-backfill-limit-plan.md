## 三方案对比

### A：调大 limit（临时掩盖）
- 做法：`AUDIT_BACKFILL_LIMIT=10000`（主线启动已临时传）
- 优点：立即可用，零风险
- 缺点：**不是方案**。数据继续增长，10000 迟早再撞线。把设计问题推迟到下次重启。
- 结论：不可取，只当过渡。

### B：归档后截断（推荐，高危）
- 做法：将 seq <= N 的老事件归档到 `audit.events_archive`，再从主表删除
- **dry-run 边界**：
  - 按 seq 切：保留最近 1000 条（seq 1878-2877），归档前 1877 条
  - 按时间切：全部在同一天，按时间切无意义
- **可恢复性**：
  - 归档前必须先 `CREATE TABLE audit.events_backup_YYYYMMDD AS SELECT * FROM audit.events`
  - 校验备份行数 = 2877
  - 回滚：`INSERT INTO audit.events SELECT * FROM audit.events_backup_YYYYMMDD`
- **触发条件**：`AUDIT_EVENTS_PRUNE=1` 才生效，不设就维持现状
- **风险**：删审计事件是合规高危。必须二次确认 + 备份校验通过才执行
- **当前是否该执行**：**不该**。2877 条全是 dev 数据，没有合规保留需求。等生产有真实数据再做。

### C：冷热分离（最接近生产，成本最高）
- 做法：热表（最近 N 天）+ 冷表（历史归档），查询 UNION
- 冷热边界：按时间分区（如热表保留 30 天），不按 seq
- 查询路径：读走热表 UNION 冷表，写只走热表
- 优点：生产级，主表永远不膨胀
- 缺点：实现成本高，需要改查询层
- 结论：生产环境再做，dev 不需要

## 推荐

**当前 dev 环境：维持现状（sealDisabled=true），等生产部署时再做 B。**

理由：
1. 2877 条全是 dev 测试数据，没有合规压力
2. 截断是高危动作，dev 阶段做反而引入风险
3. 主线传 10000 作为临时口径已够 dev 用

**生产部署前必须做**：
1. 确定 B 的归档边界（建议按时间 90 天）
