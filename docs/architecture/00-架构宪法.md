## 第一章 第一性原理

### 第 1.1 条 价值排序（不可妥协）

健澜AI原生医院操作系统OS在三甲医院生产环境运行，所有架构决策必须在以下价值冲突时按此优先级裁决，**不得反序**：

> **患者安全 > 系统可用 > 功能丰富 > 开发效率**

- **患者安全**：任何 AI 输出、任何 CDS 提示、任何自动结算结果，不得绕过医生最终确认直接作用于患者医嘱；不得因系统故障导致错误处方被执行。
- **系统可用**：挂号、收费、医嘱、发药、护士站等关键路径不可因单一组件故障雪崩；99.95% 可用性是底线。
- **功能丰富**：在不牺牲前两项的前提下追求功能完整；禁止为了"多一个 AI 功能"侵入主流程。
- **开发效率**：永远排在最后。开发效率让位于前三项时，不得有任何借口。

### 第 1.2 条 三条元原则

**第 1.2.1 条 数据不出院**
涉 PHI 的数据（姓名、身份证、手机、住址、病历、检验影像）必须在医院内网闭环。任何节点不得把 PHI 发送至境外或公有云推理 API。
判定标准：任何对外出向流量在 APISIX 层抓包审计，命中 PHI 正则（身份证 18 位、手机号 11 位、病历号规则）即阻断。每周一次全链路流量抽样审计。

**第 1.2.2 条 旁路先于替换**
A 轨产品以旁路模式挂在医院现有 HIS 旁边运行，不写主流程、不改主库、不抢占招标资格。攒案例、攒资质、攒信任，再谈核心域替换。
判定标准：A 轨产品对 HIS 主库的写入权限为零账号；所有数据回写仅写入 AI 科室自身库（质控日志、反馈样本）。

**第 1.2.3 条 业务养技术**
A 轨（AI 科室造血）必须在 0-6 个月内产生首笔收入；B 轨（Java 核心重构）的成本必须由 A 轨收入与既有现金共同承担，禁止用 12 个月全量重构换一个零收入周期。
判定标准：每月财务例会通报 A 轨 ARR 与 B 轨烧钱速率；若 A 轨 6 个月内未签首单，B 轨立即冻结新模块立项，资源转 A 轨。

### 第 1.3 条 反模式清单（永久禁止）

以下模式在任何阶段、任何客户、任何"临时例外"下均不允许出现：

1. 为了赶 POC 进度，让 AI 节点直连生产 PHI 库；
2. 为了跑通 Demo，让业务代码直连 OpenAI / Claude / Gemini 等境外 API；
3. 为了"快速上线"，在 BFF 写 SQL 直连数据库；
4. 为了"技术先进"，在 Day-1 上 Istio / Service Mesh / 完整 K8s；
5. 为了"一致性"，引入 Seata AT 分布式事务；
6. 为了"省事"，让 AI 输出不经医生确认直接写入病历；
7. 为了"性能"，把病历表改成 update-in-place 而非 append-only。

## 第二章 宪法级硬约束（14 条）

> 本章 14 条为**宪法级硬约束**，逐条定义：条文号 / 条文正文 / 违反后果 / 例外审批流程。
> 所有开发团队（含外包、实习生、合作方）在入职第一天必须书面签收本章。

### 第 2.1 条【语言栈收敛】禁第四语言

**条文**：本系统只允许三种生产语言——

- **Java 21 LTS**：核心交易域（patient-master、registration、outpatient-charge、orders、pharmacy、nursing、emr-core、cds、FHIR Server、EMPI、术语服务）；
- **Python 3.11**：AI 层（FastAPI + vLLM + LangGraph）；
- **TypeScript 5.5**：BFF 聚合层与前端。

禁止在生产代码中引入 Go、Rust、PHP、Ruby、C#、Kotlin（Kotlin 作为 Java 模块的可选项需单独审批）、Dart 等任何第四语言。

**违反后果**：CI 流水线在依赖扫描阶段直接红灯；若已合并主干，发布经理必须在 24 小时内回滚，当事团队 TL 记一次架构违规。

**例外审批**：需架构委员会 2/3 多数投票，且必须证明三种现有语言均无法满足（如极端性能瓶颈、既有 SDK 仅存在于第四语言）。例外有效期最长 6 个月，到期复审。

---

### 第 2.2 条【分布式事务】禁 Seata AT

**条文**：跨服务分布式一致性一律采用"**本地消息表 + Spring StateMachine Saga**"模式：

- 本地事务内同时写业务表与 `local_outbox` 表；
- Outbox Relay 轮询 `PENDING` 记录投递 Kafka，投递成功后置 `SENT`；
- 下游服务消费事件，失败时发补偿事件（`*.cancel` / `*.refund`）。

禁止引入 Seata AT / Seata TCC / Seata Server；禁止在业务库中建立 `undo_log` 表；禁止使用全局行锁。

**违反后果**：代码评审一票否决；若已上线，立即回滚——Seata AT 在挂号高峰会锁死 `patient_id` 索引行，P99 秒级，属于生产事故级隐患。

**例外审批**：本条文无例外。任何"Seata 更简单"的诉求必须通过本地消息表模式解决。

---

### 第 2.3 条【服务网格】禁 Istio / Service Mesh（12 个月内）

**条文**：自本宪法生效日起 12 个月内，禁止引入任何 sidecar 模式 Service Mesh（Istio、Linkerd、Consul Connect 等）。流量治理统一在 APISIX（边缘）+ Sentinel（服务侧）完成。

理由：Istio sidecar 单跳增加 100-200ms P99，直接击穿 P99<200ms 预算；医院信息科 3-5 人运维团队无法 hold 住 Envoy + istiod 排错。

**违反后果**：基础设施变更评审一票否决；K8s 集群配置一旦检测到 sidecar 注入标签，SRE 值班立即清理并追责。

**例外审批**：12 个月后若确需引入，**仅允许 Istio Ambient 模式（无 sidecar）**，且需架构委员会 + SRE 负责人联合签字、性能压测报告证明 P99 增量 < 20ms。

---

### 第 2.4 条【模块化单体优先】禁 Day-1 全微服务

**条文**：Java 核心域必须以 **Spring Boot 3.5.3 + Spring Modulith 1.4**（Java 21）模块化单体起步，单进程多 Maven 模块（mod-emp / mod-reg / mod-charge / mod-pharm / mod-shared / mod-bootstrap），跨模块走 Spring ApplicationEvent 本地事件，接口定义在 `mod-shared-api`。

**拆出独立进程的触发条件**（四选一即可）：

1. 该模块有独立扩缩容需求（如挂号早高峰 vs 收费全天平坦）；
2. 该模块需要独立发布节奏（不与其他模块同周期上线）；
3. 该模块独立数据量 > 5000 万行（如 EMR 文书）；
4. 该模块有独立合规边界（如医保对接需独立审计域）。

只有当**第 3 个模块**满足上述任一条件时，才允许引入 Spring Cloud Alibaba 2023.0.3 + Nacos 2.4。

**违反后果**：新模块若直接以独立微服务立项，架构师办公室在设计评审阶段直接打回；已上线者必须在下一个迭代合并回模块化单体。

**例外审批**：由首席架构师书面批准，并在架构委员会备案。

---

### 第 2.5 条【数据出境】禁境外大模型 API

**条文**：所有涉 PHI 的 LLM 调用必须走院内 vLLM 本地部署开源模型（Qwen2.5-72B-Instruct / DeepSeek-V3 / GLM-4）。禁止业务代码直接调用 OpenAI、Anthropic、Google Gemini、Azure OpenAI、AWS Bedrock、Claude API 等任何境外大模型服务。

出口流量在 APISIX / NetworkPolicy 层加 URL 黑名单，命中即阻断。

非 PHI 场景（医学文献检索、患者教育材料生成）若确需调用云 API，必须经脱敏网关，禁止业务代码直连云厂商 SDK。

**违反后果**：一经发现，代码立即下线，安全团队立案调查；依据《数据安全法》第 31 条可能构成数据出境违规。事故直接报架构委员会主任与公司合规负责人。

**例外审批**：本条文无例外。

---

### 第 2.6 条【PHI 隔离】AI 节点禁直连 PHI 生产库

**条文**：Python / vLLM 节点禁止直连生产 PHI 库（含患者姓名、身份证、手机、住址、完整病历表）。AI 节点必须访问独立脱敏视图（`v_phi_masked_*`），并通过 NetworkPolicy 层硬隔离。

脱敏视图规则：姓名脱敏为"患者X"、身份证仅保留前 6 后 4、手机中间 4 位星号、住址仅保留到区级、病历中的 PHI 字段在视图层正则替换。

依据：《个人信息保护法》第 28、55 条。

**违反后果**：安全审计发现即触发 P0 事件，AI 节点立即下线；当事团队 TL 与 DBA 双签整改报告。

**例外审批**：无。任何"Demo 需要看真实数据"的诉求必须在脱敏沙箱完成，不得进入生产。

---

### 第 2.7 条【薄 BFF】BFF 禁行内 SQL

**条文**：BFF（TypeScript / Bun / Node 层）必须保持薄聚合，只做四件事——协议转换、并行聚合、鉴权与上下文注入、SSE 流式透传。

ESLint 规则强制：BFF 仓库行内 SQL 数 = 0，禁止出现 `pg.query`、`pool.query`、SQL 字符串模板、`SELECT` 关键字直写。BFF 与业务库之间只允许 HTTP/gRPC 调用。

**违反后果**：CI 流水线 ESLint 红灯，禁止合并；存量 `route → repo → db` 直连写法必须在绞杀者模式切流过程中清除，不得新增。

**例外审批**：无。BFF 一旦变厚即成为新单体，违背第 2.4 条模块化优先精神。

---

### 第 2.8 条【双运行时】Bun 代码必须兼容 Node 22 LTS

**条文**：BFF 代码必须同时通过 **Bun 1.4** 与 **Node.js 22 LTS** 测试。禁止使用 `bun:*` 特有模块（如 `bun:sqlite`、`Bun.serve` 高级特性、`Bun.Terminal` 等）；只允许使用 Web 标准 API（fetch、Request、Response、WebSocket）。

Dockerfile 必须多阶段构建，同时产出 Bun 镜像与 Node 镜像；部署侧选运行时（医院若已统一 Node 则用 Node，不绑定 Bun）。

**违反后果**：CI 双运行时测试任一失败即红灯；仓库若出现 `import "bun:..."` 语句，依赖扫描阶段直接阻断。

**例外审批**：需架构师办公室 + 运维负责人联合签字，且必须提供 Node 侧等价实现方案作为兜底。

---

### 第 2.9 条【病历不可篡改】append-only + 哈希链 + CA 签章

**条文**：所有电子病历写入必须满足三件套——

1. **append-only 版本表**：任何病历记录只允许 INSERT，不允许 UPDATE / DELETE；修改必须新增新版本行；
2. **哈希链**：每条新版本行的 `prev_hash = SHA256(上一行全字段)`，形成可校验链；
3. **TSA 时间戳 + CA 签章**：每条写入带 TSA 时间戳与 CA 数字签名，验签服务独立部署。

依据：《电子病历应用管理规范（国卫医发〔2017〕8号）》第 13、17 条。

**违反后果**：任何对病历主表的 UPDATE / DELETE 语句在数据库账号权限层直接拒绝；DBA 必须回收业务账号的 UPDATE/DELETE 权限。事故级违规直接报医疗合规负责人。

**例外审批**：无。

---

### 第 2.10 条【可观测性】跨服务调用必须带 traceId

**条文**：所有跨服务调用（HTTP / gRPC / Kafka 消息）必须携带 OpenTelemetry traceId。BFF 入口生成 `traceparent`，全链路透传。Java / Python / TS 三语言必须接入统一 OTel SDK artifact。

日志必须统一 JSON 格式，Loki 采集；指标必须进 Prometheus；链路必须进 Jaeger。

**违反后果**：新服务上线前的可观测性检查为一票否决项——无 traceId 透传的服务禁止接入生产。

**例外审批**：无。

---

### 第 2.11 条【外呼降级】医保 / 第三方外呼必须熔断 + 降级

**条文**：所有外呼医保、银联、电子票据、第三方互联通接口必须满足——

- 熔断器配置（错误率阈值、半开恢复）；
- 降级行为预先定义并在压测环境演练过；
- 关键路径（挂号提交）必须支持"**先自费后追溯退费**"——患者先挂号成功，医保异步结算。

熔断降级矩阵（关键路径）：

| 接口 | 限流阈值 | 熔断条件 | 降级行为 |
|---|---|---|---|
| 挂号提交 | 3000 QPS / 集群 | 医保外呼 P99 > 1.5s | 先自费后追溯退费 |
| 医保外呼 | 100 QPS / 实例 | 错误率 > 50% 持续 10s | 熔断 30s，切降级通道 |
| AI 问诊 | 128 并发 | 排队 > 30 或单请求 > 8s | 切规则模板生成结构化建议 |
| 医生工作站登录 | 500 QPS | — | 仅缓存，不降级 |

**违反后果**：未配置熔断的外呼客户端禁止上线；未演练降级路径的功能不得进入生产。

**例外审批**：无。

---

### 第 2.12 条【国密】加密必须支持 SM2 / SM3 / SM4 切换

**条文**：全链路加密必须支持国密算法切换——

- **SM2**：数字签名（替代 RSA）；
- **SM3**：摘要算法（替代 SHA-256）；
- **SM4**：存储加密（替代 AES）；
- **TLS**：替换为 GMSSL 国密 TLS。

依据：等保三级 8.2.2 +《密码法》第 27 条。

加密抽象层必须在 `mod-shared` 中提供，业务代码不得直接 `new AES...`；国密与国际算法的切换通过配置中心 Nacos 完成。

**违反后果**：代码中出现 `AES` / `RSA` / `SHA-256` 直写而未走加密抽象层，代码评审打回；等保测评不通过。

**例外审批**：无。

---

### 第 2.13 条【方言抽象】数据库方言必须抽象，保留 PG → 达梦可迁移性

**条文**：所有 SQL 必须经过 Repository 层方言抽象（MyBatis-Plus 多方言配置），禁止在业务代码中写 PostgreSQL-only 语法——包括但不限于 `RETURNING`、`JSONB` 操作符（`->>`、`?`、`@>`）、`FILTER (WHERE ...)`、`ON CONFLICT` 方言细节。

EMR 文书的 JSON 字段使用通用 JSON 类型，禁止依赖 PG JSONB 专有索引。

Repository 层必须为 PG 与达梦 8 各写一套单元测试，CI 双库跑通。

**违反后果**：CI 方言测试红灯；任何 PG-only 语法在代码评审阶段直接打回。

**例外审批**：需架构师办公室 + 信创工程师联合签字，且必须提供达梦等价语法的迁移计划。

---

### 第 2.14 条【AI 反馈闭环】AI 输出必须带采纳 / 修改 / 拒绝

**条文**：所有 LLM 输出（病历草稿、CDS 建议、导诊答复、辅助问诊结果）必须在医生工作站 UI 上提供三个按钮——**采纳 / 修改 / 拒绝**。

- 医生采纳：样本标注为正例；
- 医生修改：样本标注为改写对（`input → output_original → output_corrected`）；
- 医生拒绝：样本标注为负例。

所有未采纳样本（修改 + 拒绝）必须回流再训练数据集，7 日一次增量微调。**未接反馈闭环的 AI 接口禁止上线**。

同时，CDS 输出仅作"提示/建议"，最终医嘱必须医生确认——产品形态规避 II/III 类医疗器械注册。

**违反后果**：AI 接口上线评审一票否决；产品形态若让 AI 自动写入病历（无医生确认），立即下线。

**例外审批**：无。

## 第三章 双轨战略条款

### 第 3.1 条 双轨定义

| 轨道 | 内容 | 周期 | 目标 | 技术栈 |
|---|---|---|---|---|
| **A 轨（造血）** | 保留现有 Bun+TS 单体 BFF，聚焦 AI 科室产品：病历质控、AI 导诊、CDS 辅助、护理看板 | 0-6 个月 | 签 3 家医院 POC / SaaS，产生首笔收入 | Python FastAPI + vLLM + TS BFF 旁路 |
| **B 轨（重构）** | Java 核心域模块化单体 → 绞杀者模式渐进替换 HIS/EMR 核心 | 6-24 个月 | 真实三甲生产环境落地 | Java 21 + Spring Boot 3.5.3 + Modulith 1.4 |

### 第 3.2 条 A 轨边界

A 轨产品必须满足：

1. **旁路模式**：挂在医院现有 HIS 旁边跑，不写主流程主库；
2. **只读优先**：除 AI 科室自身的质控日志、患者反馈外，不修改 HIS 既有数据；
3. **独立脱敏视图**：访问 HIS 数据走只读视图 + PHI 脱敏（呼应第 2.6 条）；
4. **不抢招标资质门槛**：不承诺"HIS 替换"，定位为"AI 增值模块"。

### 第 3.3 条 B 轨边界

B 轨必须满足：

1. **绞杀者模式**：通过 APISIX / Nginx 门面层按 URL 路由，新老并行、双写对账、灰度切流、秒级回滚；
2. **迁移批次严格执行**：
   - 第一批（M1-M6）：patient-master、registration、outpatient-charge；
   - 第二批（M6-M12）：orders、pharmacy、nursing；
   - 第三批（M12-M18）：emr-core、cds；
3. **中台并行**：FHIR Server、EMPI、术语服务（ICD-10 / LOINC）由 Java 团队同步建设，互联互通四甲必配。

### 第 3.4 条 资源分配

- 人力：A 轨团队（Python AI + 前端 + 产品）约占总人力 40%；B 轨团队（Java + DBA + SRE）约占 60%；
- GPU 资源：A 轨独占 H20 96GB × 2 节点（或昇腾 910B × 2），B 轨不占用；
- 生产环境：A 轨与 B 轨共享 k3s 集群但 NetworkPolicy 隔离；AI 节点不与交易节点混部。

### 第 3.5 条 冲突解决

- **代码冲突**：A 轨 BFF 仓库与 B 轨 BFF 仓库若演进分叉，以 B 轨新 BFF 为准，A 轨 BFF 作为 legacy 保留至绞杀完成；
- **数据冲突**：A 轨旁路数据与 B 轨核心数据双写时，以 B 轨主库为准，A 轨数据视为影子副本；
- **时间冲突**：A 轨收入优先于 B 轨里程碑。当 B 轨里程碑 delay 影响 A 轨 POC 交付时，B 轨资源可临时支援 A 轨，但须架构委员会备案。

### 第 3.6 条 商业底线

- 12 个月全量重构 TCO 约 1800 万元，期间零收入，初创现金撑不到三甲回款周期（18-36 个月）；
- 必须用业务养技术，不能用融资养技术；
- 3 年内不做"全栈 HIS 替换"，只做 AI 增值 + 核心域模块化备选。

## 第六章 合规红线（最硬 5 条）

> 本章从决策基线第 3 节抽取最硬 5 条，违反任一条即触发 P0 安全事件。

### 第 6.1 条 AI 不碰 PHI

Python / vLLM 节点禁止直连生产 PHI 库。必须访问独立脱敏视图，NetworkPolicy 层硬隔离。
依据：《个人信息保护法》第 28、55 条。

### 第 6.2 条 病历 append-only + 哈希链 + CA 签章

所有病历写入满足 append-only 版本表 + SHA256 哈希链 + TSA 时间戳 + CA 签章验签。业务账号回收 UPDATE/DELETE 权限。
依据：《电子病历应用管理规范（国卫医发〔2017〕8号）》第 13、17 条。

### 第 6.3 条 禁境外大模型 API

vLLM 必须本地部署开源模型，出口流量加 URL 黑名单。非 PHI 场景接云 API 必须经脱敏网关。
依据：《数据安全法》第 31 条。

### 第 6.4 条 国密全链路

SM2（签名）/ SM3（摘要）/ SM4（存储加密）全链路；TLS 替换为 GMSSL。加密抽象层统一在 `mod-shared`。
依据：等保三级 8.2.2 +《密码法》第 27 条。

### 第 6.5 条 FHIR Server + EMPI 独立部署

Kafka / APISIX 不能替代 ESB / FHIR Server。FHIR Server 与 EMPI 必须作为独立 Java 服务部署，满足互联互通四甲 IHE PIX/PDQ/XDS/ATNA Profile 举证要求。

### 第 6.6 条 其他合规要点（保留）

- 等保三级：三权分立、审计日志全量留存 ≥ 6 个月、入侵防范、恶意代码防范按 8.1-8.5 逐项映射；
- 电子签名：CA 证书在微服务间通过 mTLS + JWT 声明传递，签名验签服务独立部署；
- 医保对接：CHS 接口、医保电子凭证、DRG/DIP 分组器放在 `medical-insurance` 独立服务，结算对账异步化；
- SaMD 边界：CDS 仅作"提示/建议"，最终医嘱必须医生确认。

### 第 6.7 条 合规审计频次

- 等保三级测评：每年一次正式测评，每半年一次自查；
- 密码评估：每年一次；
- 电子病历评级：按医院客户评级进度（五级）随时配合；
- 医疗器械检测：SaMD 边界外的功能每年复盘一次，确认未越界进入 II/III 类器械范畴；
- 审计日志：全量留存 ≥ 6 个月，关键操作（病历写入、权限变更、医保结算）日志留存 ≥ 3 年。

## 第七章 性能预算（P99 < 200ms 拆解）

### 第 7.1 条 总预算

**挂号提交关键路径 P99 预算：200ms**（三甲医生工作站体感阈值，3000 QPS 峰值）。

### 第 7.2 条 分层预算

| 层 | 组件 | P99 预算 | 说明 |
|---|---|---|---|
| L1 | 边缘网关 APISIX | **≤ 10ms** | TLS 终止、JWT 校验、限流、路由 |
| L2 | BFF（TS / Bun） | **≤ 20ms** | 鉴权、上下文注入、并行聚合（不写 SQL） |
| L3 | Java 业务逻辑 | **≤ 80ms** | Spring Modulith 模块内调用 + 本地事件 |
| L4 | 数据库（含 PgBouncer） | **≤ 60ms** | PG 16，单条索引查询 HikariCP ≤ 15/实例 |
| L5 | 网络与序列化 | **≤ 20ms** | HTTP/gRPC + JSON 序列化 |
| L6 | 应急余量 | **10ms** | GC 停顿、排队、抖动 |
| **合计** | — | **≤ 200ms** | — |

### 第 7.3 条 JVM 与运行时预算

- **GC**：ZGenerational ZGC（不是 G1），目标 P99 停顿 < 1ms；
- **堆**：4C8G 容器堆定 4G（`-Xms4g -Xmx4g`）；
- **冷启动**：lazy-init + readiness `initialDelay=30s` + CronHPA 早 7:00 预热到 6 Pod；CRaC 二期再上。

### 第 7.4 条 容量基线（2000 床三甲）

| 服务 | 峰值 QPS | Pod 数 | CPU | 内存 | HikariCP 连接 |
|---|---|---|---|---|---|
| registration（挂号） | 3000 | 6 | 4C | 8G | ≤15/实例 |
| outpatient-charge | 800 | 4 | 4C | 8G | ≤15/实例 |
| orders / pharmacy | 500 | 3 | 4C | 8G | ≤10/实例 |
| emr-core | 200 | 3 | 4C | 8G | ≤10/实例 |
| AI 问诊（vLLM 节点） | 200 并发 | 2 节点 GPU | 32C | 256G + 2×96G 显存 | 不直连业务库 |
| BFF | 5000 | 4 | 2C | 4G | 不直连业务库（HTTP） |

PG 集群前置 PgBouncer transaction 模式（pool_size=50、max_db_connections=150），避免连接风暴。

### 第 7.5 条 AI 路径预算（独立）

- AI 问诊超时阈值：**8 秒**（不是 30 秒）；
- 单卡 7B AWQ 量化稳定并发 60-80 路；2 节点合计 128 路；
- 排队 > 30 或单请求 > 8s，立即切规则模板生成结构化建议；
- 绝不让医生工作站干等。

### 第 7.6 条 高可用预算

- **RPO = 0**：Patroni 同步流复制；
- **RTO ≤ 5 分钟**：主备同城自动切换；
- **年可用性 ≥ 99.95%**（年停机 ≤ 4.3 小时）；
- Redis 哨兵（1 主 2 从 3 哨兵）；
- Kafka 3 Broker，min.insync.replicas=2，acks=all；
- **不做双活**（对 <30 人团队过度设计）。

### 第 7.7 条 告警阈值

Alertmanager 告警触发条件（任一即 P1）：

- CPU > 80%；
- 内存 > 85%；
- P99 > 300ms；
- 5xx 错误率 > 1%；
- 磁盘 > 80%；
- PG 主从延迟 > 1s。

告警分级：P1 告警 5 分钟内电话通知值班 SRE；P2 告警 15 分钟内企业微信通知；P3 告警日报汇总。任何 P1 告警未在 30 分钟内确认，自动升级到架构师办公室。

### 第 7.8 条 压测与预算回归

- 每次大版本发布前，必须在预发环境跑一轮全链路压测，复刻早高峰 3000 QPS 挂号场景；
- 压测报告必须包含分层 P99（网关/BFF/Java/DB 各层实测 ms 数），与第 7.2 条预算对比；
- 任一层实测超过预算 120%，本版本禁止发布；
- 压测环境配置必须与生产 1:1（Pod 数、CPU、内存、连接池、PgBouncer 参数完全一致），禁止"低配压测高配上线"。

### 第 8.5 条 技术栈升级流程

第四章锁定版本的升级（如 Spring Boot 3.5.3 → 3.5.4、Kafka 3.7 → 3.8）：

- 小版本 patch 升级：SRE + 对应 Tech Lead 联合签字，预发环境验证 1 周；
- 大版本 minor 升级：架构委员会评审；
- 跨大版本 major 升级：视为宪法修订，走第 8.2 条流程。

### 第 8.6 条 审计与合规检查

- 首席架构师办公室每季度组织一次宪法合规审计，抽查所有生产仓库的 ESLint 规则、依赖扫描结果、NetworkPolicy 配置、AI 节点出向流量；
- 审计发现的违规项录入整改台账，限期 30 天关闭；
- 连续两个季度审计零违规的团队，授予"架构合规优秀团队"称号，作为年终绩效加分项；
- 审计结果直接报公司 CTO 与合规负责人。

### 第 8.7 条 与既有代码的兼容

- 现状 Bun+TS 单体 BFF（1957 路由）中大量 `route → repo → db` 直连写法，不要求一次性清除，但**禁止新增**；
- 存量直连写法必须在绞杀者模式切流到对应 Java 模块时同步清除，不得遗留到老单体下线之后；
- 老单体路由在切流完成 95% 后进入只读维护模式，剩余 5% 管理后台低流量模块在阶段 2 准出前必须下线。

## 第九章 附录：术语表

### 第 9.1 条 业务术语

- **PHI**：Protected Health Information，受保护健康信息，含姓名、身份证、手机、住址、病历、检验影像等。
- **HIS**：Hospital Information System，医院信息系统。
- **EMR**：Electronic Medical Record，电子病历。
- **CDS**：Clinical Decision Support，临床决策支持。
- **EMPI**：Enterprise Master Patient Index，企业级患者主索引。
- **FHIR**：Fast Healthcare Interoperability Resources，HL7 快速医疗互操作资源规范。
- **IHE PIX/PDQ/XDS/ATNA**：互联互通四甲要求的 IHE Profile。
- **DRG / DIP**：按疾病诊断相关分组 / 按病种分值付费，医保支付方式。
- **CHS**：医保信息平台接口（China Health Security）。
- **SaMD**：Software as a Medical Device，医疗器械软件。
- **等保三级**：网络安全等级保护第三级。
- **互联互通四甲**：国家医疗健康信息互联互通标准化成熟度四级甲等。
- **电子病历五级**：电子病历系统功能应用水平分级评价五级。

### 第 9.2 条 架构术语

- **绞杀者模式（Strangler Fig）**：通过门面层路由，新系统逐步替换老系统流量，老系统最终被"绞杀"下线。
- **模块化单体（Modulith）**：单进程内按 Maven 模块隔离，跨模块走本地事件，避免 Day-1 分布式调用。
- **本地消息表（Outbox Pattern）**：本地事务内同时写业务表与 outbox 表，Relay 异步投递 Kafka。
- **Saga**：长事务拆为一系列本地事务，每步有补偿动作。
- **旁路模式**：AI 产品挂在医院现有 HIS 旁边运行，不写主流程。
- **双写对账**：老系统与新系统同时写，每日凌晨比对影子表与主表。
- **灰度切流**：按患者尾号、科室、医生逐步切流到新系统。
- **回滚预算**：每次灰度必须有 10 秒内切回老系统的预案。

### 第 9.3 条 中间件与算法术语

- **APISIX**：国产 Apache 顶级网关。
- **Nacos**：注册中心 + 配置中心。
- **Sentinel**：阿里开源熔断限流组件。
- **Patroni**：PostgreSQL 高可用管理工具，同步流复制。
- **PgBouncer**：PostgreSQL 连接池，transaction 模式。
- **vLLM**：开源大模型推理引擎。
- **MCP（Model Context Protocol）**：模型上下文协议，仓库已接入 `@modelcontextprotocol/sdk 1.29`。
- **LangGraph**：基于状态机的 Agent 编排框架。
- **k3s**：轻量级 Kubernetes 发行版，单二进制。
- **ZGenerational ZGC**：JDK 21 分代 ZGC，目标 P99 停顿 < 1ms。
- **SM2 / SM3 / SM4**：国密非对称加密 / 摘要 / 对称加密算法。
- **GMSSL**：国密 TLS 标准。
- **CA 签章**：数字证书机构签章。
- **TSA**：时间戳机构。
