# 健澜AI原生医院操作系统OS（jianlan-gang-os）重构方案——合规可落地性评审报告

> 评审对象：Java(Spring Cloud) + Python(FastAPI+vLLM) + TS(Bun BFF) 微服务重构架构
> 目标场景：大型三甲医院生产环境
> 评审维度：网络安全等级保护三级、电子病历系统应用水平五级/六级、互联互通标准化成熟度四甲、电子签名与病历合规、数据安全法/个保法、医保对接、医疗器械软件（SaMD）、信创适配
> 评审日期：2026-10-19
> 评审角色：医疗信息合规与系统架构联合评审

---

## 1. 总体结论

新架构（Spring Cloud 微服务 + FastAPI/vLLM AI 节点 + Bun BFF，K8s + APISIX + Kafka + PostgreSQL + Redis）在**技术选型上具备支撑等保三级、电子病历六级、互联互通四甲的潜力**，但**不能默认"过评"**——等保三级是"合规底线"，可通过边界划分、三权分立、审计集中落地；电子病历六级与互联互通四甲的核心不在中间件，而在**CDS 知识库、全院闭环、术语标准与主索引（EMPI）的工程化落地**，这部分当前方案描述不足。最大的合规风险集中在三处：**①Python/vLLM AI 节点直接接触 PHI 字段且未做脱敏与隔离，违反个保法第二十八条与人类遗传资源管理条例；②FHIR 网关与 EMR 版本管理（病历篡改检测）缺位，互联互通四甲与电子病历六级的"全流程数据闭环"无法举证；③Spring Cloud + PostgreSQL 直接上生产而未做国密改造与信创适配，等保三级 8.2.2 通信传输与医院信创清单会被一票否决。** 建议在架构宪法中固化"PHI 不出安全域、AI 节点只见脱敏视图、FHIR/EMPI 作为独立中台服务、国密 SM2/SM4 全链路、SaMD 边界由 CDS 产品经理与 RA 联合评审"五条红线后再进入开发。

## 2. 逐项合规要求映射表

### 2.1 网络安全等级保护三级（GB/T 22239-2019）

| 等保三级控制项 | 等级要求要点 | 新架构如何满足 | 证据/控制点 | 缺口 |
|---|---|---|---|---|
| 8.2.1 网络架构 | 划分不同安全区域，区域间访问控制；关键设备冗余 | K8s NetworkPolicy 划分为 DMZ（BFF/APISIX）、业务区（Java 微服务）、数据区（PG/Redis）、AI 区（vLLM）、管理区（运维/审计） | CNI 网络策略矩阵、APISIX 路由白名单、VPC 子网划分图 | AI 区与业务区是否物理/逻辑隔离需在网络设计书明确 |
| 8.2.2 通信传输 | 完整性、保密性；采用校验技术或密码技术 | mTLS 1.3 服务间加密；入库字段级加密；国密 SM2/SM4 改造 | APISIX 双向认证、Kafka TLS、PG 列加密 | 当前方案未提国密，三甲医院等保测评 increasingly 要求 SM 算法 |
| 8.3.1 边界防护 | 跨越边界的访问受控；非授权设备接入受控 | APISIX 作为唯一北向入口；K8s Ingress 白名单；运维堡垒机 | APISIX 插件链、WAF、堡垒机会话录像 | 东西向服务间调用未做零信任 mTLS，默认 Service Account 过宽 |
| 8.3.2 访问控制 | 最小权限；默认拒绝 | RBAC + ABAC；服务间 OAuth2 Scope；数据库视图隔离 | Keycloak/自研 IAM、PG Row Level Security | Redis 无细粒度 ACL，需升级 Redis 6+ ACL |
| 8.3.3 入侵防范 | 最小化安装； Closing 端口；检测新型攻击 | 镜像精简（distroless）、Falco 运行时检测、HIDS | 镜像扫描（Trivy）、Falco 规则集 | AI 节点（Python 镜像）依赖庞杂，镜像扫描风险高 |
| 8.3.4 恶意代码防范 | 边界与计算环境恶意代码检测 | 部署防病毒/EDR；AI 模型文件签名校验 | EDR 代理、模型仓库签名 | vLLM 加载的 HuggingFace 模型无签名机制，需自建模型仓库 |
| 8.3.5 / 8.4.3 安全审计 | 审计覆盖每个用户、重要行为；记录保存不少于 6 个月 | APISIX 访问日志 + 微服务审计日志 + 数据库审计（DAS）统一入 Kafka → 日志中心（ELK/OpenSearch）→ 审计平台 | 三权分立审计员账号；日志防篡改（WORM）；留存 180 天以上 | 业务操作级审计（谁改了哪条医嘱、改前改后值）未在方案中体现 |
| 8.4.1 身份鉴别 | 口令复杂度、双因素、登录失败处理 | IAM 统一认证；医生站 CA 证书 + 口令双因素；服务间 mTLS | 4A 平台、CA 对接 | 微服务间"机器身份"（service identity）方案未明 |
| 8.4.2 访问控制 | 安全管理员、安全审计员、系统管理员三权分立 | 独立的 admin/auditor/sec-admin 三角色；K8s RBAC 绑定 | K8s ClusterRole 拆分；堡垒机三权账号 | 当前 Spring Cloud 默认 admin 角色过大 |
| 8.4.7 / 8.4.8 数据完整性与保密性 | 重要数据传输/存储完整性、保密性 | PG TDE 或列级 AES-256/SM4；PHI 字段（姓名、身份证、手机、住址）列加密 | KMS 密钥管理；加密字段视图 | AI 节点读取的 SQL 是否走加密视图未明确 |
| 8.4.9 数据备份恢复 | 本地备份+异地备份；热冗余 | PG 主从 + 定时备份；同城双活/异地灾备 | RPO/RTO 指标（建议 RPO≤15min，RTO≤2h） | 方案未提异地灾备，三甲等保三级要求异地备份 |
| 8.4.10 剩余信息保护 | 鉴别信息、敏感数据释放前彻底删除 | K8s PV 销毁策略；日志脱敏；内存清零 | 存储加密擦除 | Python AI 进程内存中 PHI 残留无控制 |
| 8.4.11 个人信息保护 | 仅采集必要；明示同意 | 最小字段集；隐私授权页 | 个保影响评估（PIA）报告 | AI 训练数据是否做了 PIA 未提及 |
| 8.5.1-8.5.4 安全管理中心 | 系统管理、审计管理、安全管理三权分立；集中管控 | 统一运维平台（JumpServer）、统一审计平台、统一 SOC | 三权分立矩阵 | 需在 K8s 命名空间与 ClusterRole 层面落地 |

### 2.2 电子病历系统应用水平分级评价（五级/六级）

依据：国家卫生健康委《电子病历系统应用水平分级评价管理办法（试行）》及《电子病历系统应用水平分级评价标准（试行）》。

| 评价维度 | 五级要求 | 六级要求 | 新架构分工建议 | 缺口 |
|---|---|---|---|---|
| 数据管理 | 全院数据集中存储、统一管理、互联互通 | 全流程数据闭环、可追溯 | EMR 服务（Java）承载病历结构化存储；数据中台（Java+PG）做 CDR | 需明确 EMR 服务与 CDR 的边界，避免双写 |
| 诊疗记录 | 病历文书结构化、知识库辅助书写 | 高级 CDS、智能模板、自然语言生成 | CDS 服务（Java 规则引擎 Drools/Rete）+ AI 服务（Python/vLLM 辅助书写、ICD 智能编码） | AI 生成内容必须"AI 辅助、医生签发"，不能自动入病历 |
| 医嘱处理 | 医嘱闭环（开具-审核-执行-核对） | 全闭环 + 负面清单实时拦截 | 医嘱服务（Java）+ 药房服务（Java）+ 护理服务（Java）通过 Kafka 事件驱动闭环 | 闭环用药的"双人核对、麻精药品专册"流程需在业务层硬编码 |
| 护理记录 | 护理文书电子化、与医嘱联动 | 护理全程闭环、风险预警（跌倒/压疮） | 护理服务（Java）+ CDS 风险规则 | 跌倒/压疮量表需内置标准化 |
| 临床决策支持（CDS） | 初级 CDS：药物相互作用、过敏、重复用药 | 高级 CDS：个性化推荐、路径优化、预测模型 | CDS 引擎（Java Drools）+ AI 推理（Python）双层：规则层硬拦截，AI 层软提示 | AI 预测模型须有"医生可拒绝、可解释、可审计"机制 |
| 患者隐私 | 病历访问留痕、脱敏展示 | 全访问行为审计、数据最小化 | EMR 服务记录谁在何时看了哪个患者病历；BFF 层按角色脱敏 | 需在 APISIX/微服务切面统一实现"病历翻阅审计" |
| 病历版本与篡改检测 | 病历修改留痕 | 病历哈希链、时间戳、CA 签名 | EMR 服务实现 append-only 版本表 + 哈希链 + 时间戳服务对接 | **当前方案完全缺失病历版本管理与哈希链，这是六级硬伤** |

### 2.3 医院信息互联互通标准化成熟度（四甲/五甲）

依据：国家卫生健康委统计信息中心《医院信息互联互通标准化成熟度测评方案》及配套标准（WS/T 447、WS/T 500 系列、HL7 FHIR R4）。

| 测评维度 | 四甲要求 | 新架构如何满足 | 缺口 |
|---|---|---|---|
| 基础设施与平台 | 集成平台（ESB）或 FHIR Server；数据中心（CDR） | **不建议用 Kafka+APISIX 直接替代 ESB**。Kafka 是消息总线，不具备 ESB 的协议转换、消息路由、编排、可视化监控能力。建议：独立部署 FHIR Server（如 HAPI FHIR 或自研）作为集成平台核心，Kafka 作为事件后端，APISIX 作为北向 API 网关 | 方案中"Kafka+APISIX 替代 ESB"是典型误区，需在架构评审中纠正 |
| 数据中心 CDR | 患者主索引 EMPI、临床数据存储 | EMPI 服务（Java）独立部署；CDR 基于 PG/Greenplum | EMPI 的"跨院查重、合并、追溯"规则需产品化 |
| 术语标准 | ICD-10、ICD-9-CM3、LOINC、SNOMED CT、ATC | 术语服务（Java）统一维护字典；FHIR CodeSystem/ValueSet 映射 | 当前 HIS/EMR 自带字典，需做术语映射层 |
| 服务接口规范 | HL7 v2/v3、FHIR R4、DICOM、IHE 集成规范 | FHIR Server 暴露 RESTful API；DICOM 对接 PACS 通过独立网关 | 需实现 IHE PIX/PDQ、XDS、Audit Trail 相关 Profile |
| 信息安全 | 与等保三级衔接 | 同 2.1 | — |
| 运营与运维 | 平台监控、台账 | 可观测性栈（Prometheus/Grafana/OpenTelemetry） | 需补充 FHIR 接口调用量、成功率监控 |

### 2.4 电子签名法与电子病历合规

依据：《中华人民共和国电子签名法》（2019修正）第十三、十四条；《电子病历应用管理规范（试行）》（国卫医发〔2017〕8号）；《电子病历系统功能规范（试行）》。

| 合规项 | 要求 | 新架构落地方案 | 缺口 |
|---|---|---|---|
| 可靠电子签名 | 签名制作数据专属、签名时受控、改动能被发现 | 医生站 USBKey/软证书 CA；EMR 服务在病历提交时调用 CA 签章服务；签章值（含原文哈希）存入病历表 | 微服务间不能传递"用户签名"，必须由 BFF/EMR 服务在边界重新签章，防止服务间伪造签名 |
| 时间戳 | 病历时间可信 | 对接国家授时中心或行业 TSA；签章时加盖 RFC3161 时间戳 | 方案未提 TSA |
| 签名验签 | 事后可验证 | EMR 服务内置验签工具；归档病历 PDF 化后二次签章 | 需在病历归档流程固化 |
| 病历篡改检测 | 任何修改留痕 | 病历表 append-only + 每行哈希链（prev_hash + row_hash）；定期哈希值上链或入 WORM 存储 | **当前方案缺失，六级必查项** |
| 病历保存时限 | 门诊≥15年，住院≥30年 | 归档存储（对象存储 + 蓝光/磁带） | 架构需规划冷存储层 |

### 2.5 数据安全法 / 个人信息保护法 / 人类遗传资源

依据：《数据安全法》第二十一条分类分级；《个人信息保护法》第十三条（同意）、第二十八条（敏感个人信息）、第二十九条（单独同意）、第五十五条（PIA）；《人类遗传资源管理条例》（国务院令第717号）。

| 合规项 | 要求 | 新架构落地方案 | 缺口 |
|---|---|---|---|
| 数据分类分级 | 一般/重要/核心数据；PHI 属敏感个人信息 | 数据资产目录；PHI 字段打标；分级存储 | 需建立数据分类分级台账 |
| 敏感个人信息单独同意 | 病历、健康数据属敏感个人信息 | 患者就诊时签署电子知情同意；AI 辅助诊断单独授权 | AI 训练是否用了病历数据需单独同意 |
| AI 训练数据脱敏 | 训练数据须去标识化 | **Python/vLLM AI 节点不得直连生产 PHI 库**。通过"脱敏视图"或独立脱敏库访问；姓名/身份证/手机/住址/病案号全部替换为 token；保留医学字段（诊断、检验、用药） | **当前方案最大风险：vLLM 直接读生产库会违反个保法第二十八条** |
| PIA 个人信息保护影响评估 | 处理敏感个人信息前必须 PIA | AI 模块上线前出具 PIA 报告 | 未提及 |
| 人类遗传资源 | 基因/蛋白组等数据不得擅自出境、对外提供 | 若 AI 训练涉及基因数据，须科技部人遗办审批 | 若仅病历文本/影像，不涉及；但若有组学数据需红线 |
| 数据出境 | 关键信息基础设施数据不得出境；个信出境需安全评估 | **禁止调用境外大模型 API（OpenAI/Claude/Gemini）处理病历**；vLLM 必须本地部署开源模型（Qwen/DeepSeek/GLM 等） | 若团队习惯用境外 API，这是红线 |
| 数据最小化 | 仅必要字段 | AI 服务按需字段；BFF 按角色裁剪响应 | 需在 API 网关做字段级脱敏 |

### 2.6 医保对接

依据：国家医保局《国家医疗保障信息平台接口规范》（CHS 接口）、医保电子凭证规范、CHS-DRG/DIP 分组方案。

| 合规项 | 要求 | 新架构落地方案 | 缺口 |
|---|---|---|---|
| CHS 接口 | 就医结算、费用明细、目录匹配 | 独立"医保服务"（Java）作为院内系统与国家医保平台之间的唯一通道；通过 APISIX 白名单出院 | 医保接口需 CA 证书与专网（医保 VPN/专线），不能走公网 |
| 医保电子凭证 | 扫码就医、实名认证 | BFF 对接医保电子凭证 H5/小程序 | 需区分院内扫码与院外渠道 |
| DRG/DIP 分组器 | 结算前预分组、费用预警 | 独立"DRG/DIP 服务"（Java），内置国家分组器 + 本地细则；出院结算前调用 | 分组器需跟随国家版本季度更新 |
| 结算对账 | 日对账、月对账、差异处理 | 医保服务生成对账文件；财务服务核对 | 对账失败的人工干预流程需产品化 |
| 费用明细上传 | 医嘱明细、收费明细与医保目录映射 | 收费服务（Java）维护医保目录映射表 | 目录映射工作量大，需运营团队 |

### 2.7 医疗器械软件（SaMD）

依据：国家药监局《医疗器械软件注册指导原则》（2022年第8号通告）、《人工智能医疗器械注册审查指导原则》。

| 功能模块 | 是否构成 SaMD | 注册建议 | 新架构合规边界 |
|---|---|---|---|
| 医嘱规则拦截（过敏、重复用药、相互作用） | 通常作为医院信息系统功能，不单独注册；但若宣称"辅助诊断"则需评估 | 按医院内部 CDS 工具管理，不对外销售 | CDS 规则引擎须留痕、可解释 |
| AI 辅助诊断（影像识别、病理切片） | 大概率构成 II 类/III 类 SaMD | 需 NMPA 注册证；未取证不得用于临床决策 | **vLLM 加载的开源模型若用于诊断推荐，必须明确"仅科研/演示"边界，不能进入生产医嘱流** |
| AI 辅助病历书写（生成病历草稿） | 一般不构成 SaMD（仅文书辅助） | 无需注册，但医生必须复核签发 | UI 上明确标注"AI 生成，待医生确认" |
| AI 智能编码（ICD 推荐） | 通常不构成 SaMD | 无需注册 | 编码结果由病案员确认 |
| 预测模型（再入院、脓毒症预警） | 若直接驱动临床干预可能构成 SaMD | 建议作为"科研预警"，不自动联动医嘱 | 预警仅展示，不自动执行 |

### 2.8 信创适配

依据：卫健委、工信部信创要求；国密局 SM 算法要求。

| 层级 | 现状 | 国产替代选项 | 适配工作量评级 |
|---|---|---|---|
| CPU | x86_64（Intel/AMD） | 鲲鹏 920（ARM）、飞腾 S2500（ARM）、海光 3350（x86 兼容） | 中：JVM 跨架构无压力；vLLM 需 ARM 版 wheel |
| OS | CentOS/Ubuntu | 麒麟 V10、统信 UOS | 低：Linux 通用 |
| JDK | OpenJDK 21 | 毕昇 JDK（华为）、Dragonwell（阿里）、Kona（腾讯） | 低：直接替换 |
| 数据库 | PostgreSQL 15 | 达梦 DM8、人大金仓 KingbaseES、OceanBase | **高：PG 与达梦 SQL 方言差异、存储过程、JSONB、数组类型不兼容；预估 3-6 个月改造** |
| 缓存 | Redis 7 | 国产 Tair、Codis；或继续 Redis（开源） | 低 |
| 消息队列 | Kafka | 国产 RocketMQ、Apache Pulsar | 中：API 差异，需适配层 |
| 网关 | APISIX（开源） | 可继续；或替换为国产 API 网关 | 低 |
| AI 推理 | vLLM + NVIDIA GPU | vLLM 对昇腾 910B 支持需走 MindSpore/vLLM-Ascend 分支；性能待验证 | **高：vLLM 原生 CUDA，昇腾需 CANN 适配，生产成熟度待验证；建议初期 NVIDIA + 后期切换** |
| 国密 | TLS 1.3 + AES | 国密 SM2/SM3/SM4 全链路 | 中：APISIX 支持国密插件；PG 需加解密层改造 |
| 浏览器/终端 | Chrome/Edge | 奇安信、360 安全浏览器 | 低 |

## 3. 关键风险点

### 风险 1：AI 节点直连生产 PHI 库，违反个保法第二十八条

- **风险描述**：Python/vLLM AI 服务若直接连接生产 PostgreSQL，读取患者姓名、身份证、手机、住址、完整病历，用于模型推理或微调，即构成"敏感个人信息处理"。
- **违反条款**：《个人信息保护法》第二十八条（敏感个人信息处理须具有特定目的和充分必要性，并采取严格保护措施）、第二十九条（处理敏感个人信息应取得个人单独同意）、第五十五条（事前 PIA）；《数据安全法》第二十七条（数据安全保护义务）。
- **修正方案**：
  1. AI 服务一律连接独立"脱敏库"或通过 PG 视图访问，PHI 字段替换为 token；
  2. 模型微调/训练数据必须来自脱敏数据集，留存脱敏规则文档与 PIA 报告；
  3. AI 服务 Pod 与业务库在 K8s NetworkPolicy 层面隔离，仅允许访问脱敏库；
  4. 上线前由法务/合规出具 PIA 审批。

### 风险 2：病历版本管理与篡改检测缺失，电子病历六级无法过评

- **风险描述**：方案未设计病历 append-only 版本表、哈希链、时间戳、CA 签名验签流程。电子病历六级评审中，"病历可追溯、不可篡改、任何修改留痕"是必查项。
- **违反条款**：《电子病历应用管理规范（试行）》（国卫医发〔2017〕8号）第十三、十七条；电子病历分级评价标准六级"数据管理"维度；等保三级 8.4.3 安全审计。
- **修正方案**：
  1. EMR 服务核心表（病历文书、医嘱、护理记录）采用 append-only 设计，禁止 UPDATE/DELETE；
  2. 每行记录 `prev_hash` + `row_hash`（SHA-256/SM3），形成哈希链；
  3. 对接国家 TSA 获取 RFC3161 时间戳；
  4. 每次医生签署调用 CA 签章服务，签章值与病历哈希绑定；
  5. 归档病历 PDF 化并二次签章，入 WORM 存储。

### 风险 3：用 Kafka + APISIX 替代 ESB/FHIR Server，互联互通四甲不过

- **风险描述**：Kafka 是异步消息总线，APISIX 是 API 网关，二者均不具备 ESB/FHIR Server 的协议转换（HL7 v2 XML/JSON）、消息路由、可视化编排、IHE Profile 支持能力。互联互通四甲测评明确要求"集成平台"与"FHIR 服务"举证。
- **违反条款**：《医院信息互联互通标准化成熟度测评方案》四级甲等"基础设施"与"平台服务"维度；WS/T 447、WS/T 500 系列标准。
- **修正方案**：
  1. 独立部署 FHIR Server（推荐 HAPI FHIR 或基于开源二开）作为集成平台核心；
  2. Kafka 作为事件后端，承接 CDR 异步同步；
  3. APISIX 作为北向 API 网关，统一鉴权、限流、审计；
  4. 实现 IHE PIX/PDQ（患者身份查询）、XDS（文档共享）、ATNA（审计）Profile；
  5. EMPI 作为独立微服务，承担跨系统患者主索引。

### 风险 4：未做国密改造与信创适配，等保三级与医院招标一票否决

- **风险描述**：当前方案默认 TLS 1.3 + AES + x86 + 开源组件，未规划 SM2/SM3/SM4 国密算法与国产 CPU/OS/数据库/数据库替代。三甲医院 increasingly 在招标中要求"全栈信创"与"国密合规"。
- **违反条款**：等保三级 8.2.2 通信传输（采用密码技术）；《密码法》第二十七条（关键信息基础设施使用商用密码）；卫健委信创相关指导文件。
- **修正方案**：
  1. APISIX 启用国密 SSL 插件（SM2 证书）；
  2. 服务间 mTLS 支持国密双证书；
  3. PHI 字段加密采用 SM4；
  4. 数据库层在架构设计阶段即评估达梦/KingbaseES 迁移，避免后期重写；
  5. AI 推理层初期可用 NVIDIA，但需规划昇腾 910B 适配路线图。

### 风险 5：境外大模型 API 处理病历数据，数据出境红线

- **风险描述**：若团队为图便利，将病历文本转发至 OpenAI/Claude/Gemini 等境外 API，即构成数据出境。
- **违反条款**：《数据安全法》第三十一条（关键信息基础设施数据出境安全管理）；《个人信息保护法》第三十八至四十条（个信出境需安全评估/标准合同/认证）；《人类遗传资源管理条例》。
- **修正方案**：
  1. 架构宪法明确"禁止境外 API 处理 PHI"；
  2. vLLM 本地部署开源模型（Qwen2.5/DeepSeek-V3/GLM-4 等）；
  3. 出口流量在 APISIX/防火墙层面加 URL 黑名单；
  4. 日志审计中对境外域名访问实时告警。

## 4. AI 层专项合规

### 4.1 大模型训练数据合规

1. **数据来源**：训练/微调数据必须来自医院脱敏数据集，由数据治理团队出具《脱敏报告》；不得直接使用生产库。
2. **脱敏规则**：直接标识符（姓名、身份证、手机、住址、病案号、医保号）全部替换为 token；准标识符（年龄、性别、民族）泛化（年龄分段）；保留医学必要字段（ICD 编码、检验项、用药、手术）。
3. **同意管理**：患者就诊时签署的《知情同意书》须覆盖"去标识化数据用于科研/模型训练"条款；否则训练数据须排除该患者。
4. **PIA**：每次模型版本上线前完成个人信息保护影响评估，留存报告至少 3 年。
5. **模型仓库**：自建模型仓库（Model Registry），所有模型文件签名（cosign），vLLM 启动前校验签名，防止供应链投毒。

### 4.2 患者隐私在 Java/Python/TS 三层间流转

```
[医生工作站] 
    │ HTTPS + CA 证书
    ▼
[APISIX BFF 网关]  ← 字段级脱敏（按角色裁剪）
    │ mTLS (SM2)
    ▼
[Java 业务微服务]  ← PHI 列加密存储；访问审计
    │ 事件驱动 (Kafka TLS)
    ▼
[Python AI 服务]   ← 只见脱敏视图，不见 PHI 原文
    │
    ▼
[vLLM 推理]        ← 本地开源模型，不出院
```

关键控制点：
- Java 业务服务向 Python AI 服务传参时，在 SDK 层强制走"脱敏序列化器"，PHI 字段自动打码；
- Python 服务 Pod 的 NetworkPolicy 仅允许访问脱敏库与模型仓库；
- AI 推理结果（如"建议诊断 ICD-XX"）必须标注"AI 辅助，医生确认"，不得自动写入医嘱；
- AI 调用日志单独留存，含 prompt 摘要、模型版本、医生反馈。

### 4.3 医疗 AI 注册边界

| AI 功能 | 合规定位 | 临床使用方式 |
|---|---|---|
| 病历文书生成草稿 | 文书辅助，非 SaMD | 医生编辑后签发，AI 内容不直接入档 |
| ICD 智能编码推荐 | 编码辅助，非 SaMD | 病案员确认后入库 |
| 检验危急值预警 | 院内 CDS，按医院信息系统管理 | 弹窗提醒，不自动执行 |
| 影像/病理 AI 识别 | **可能构成 II/III 类 SaMD** | 未取证不得用于临床诊断；若与第三方合作，须核查对方注册证 |
| 脓毒症/再入院预测 | 科研预警性质 | 仅展示，不联动医嘱 |
| 智能问诊导诊 | 非诊断，导诊性质 | 明确"不替代医生诊断" |

## 6. 必须写进架构宪法的合规条款

以下条款建议作为 jianlan-gang-os 架构宪法（Architecture Constitution）的强制条目，任何 PR 违反须 reject：

1. **PHI 不出安全域原则**：任何包含直接标识符（姓名、身份证、手机、住址、病案号、医保号）的数据流，不得离开医院安全域；AI 服务、第三方集成、数据分析均通过脱敏视图访问。
2. **禁止境外 API 原则**：禁止在生产环境调用任何境外大模型 API（OpenAI/Claude/Gemini 等）处理患者数据；AI 推理一律 vLLM 本地部署开源模型。
3. **病历 append-only 原则**：EMR 核心表（病历文书、医嘱、护理记录、体温单）禁止物理 UPDATE/DELETE；任何修改通过新增版本行实现，全行哈希链 + 时间戳 + CA 签名。
4. **三权分立原则**：系统管理员、安全管理员、审计管理员三角色独立，任何单一账号不得同时拥有配置权限与审计权限；K8s ClusterRole 按此拆分。
5. **国密优先原则**：对外通信与 PHI 存储优先采用 SM2/SM3/SM4；在国密组件成熟前，可用 AES/RSA 过渡，但架构须预留切换点。
6. **AI 辅助、医生签发原则**：AI 生成的任何临床内容（病历草稿、诊断建议、编码推荐）必须由医生/病案员人工确认后方可进入正式记录；UI 必须显著标注"AI 生成"。
7. **FHIR/EMPI 独立原则**：集成平台（FHIR Server）与患者主索引（EMPI）作为独立中台服务，不允许业务微服务直连其他业务库做患者身份合并。
8. **审计全覆盖原则**：所有 PHI 访问（读、写、导出、打印）必须产生审计日志，日志入 Kafka → WORM 存储，留存不少于 180 天（建议 1 年），审计员独立可查。
9. **医保唯一通道原则**：所有医保接口调用必须经独立"医保服务"微服务，通过医保专网/CA 出院；业务服务不得直连国家医保平台。
10. **SaMD 边界原则**：任何可能构成医疗器械软件的 AI 功能（影像识别、自动诊断、自动干预建议），未经 NMPA 注册或 RA 评审，不得进入生产医嘱闭环；仅可在科研模式下运行。
11. **数据最小化原则**：BFF 响应按角色裁剪字段；微服务间传参仅携带必要字段；日志中 PHI 字段自动脱敏。
12. **信创预留原则**：数据库访问通过 ORM/抽象层，禁止手写 PG 特有方言（JSONB、数组、窗口函数特例），为达梦/KingbaseES 迁移预留空间；AI 推理通过抽象接口调用，为昇腾适配预留空间。

## 7. 评审结论与下一步建议

新架构在中间件选型（K8s + Spring Cloud + FastAPI + APISIX + Kafka + PG）层面**技术成熟度足够**，但要通过三甲医院等保三级、电子病历六级、互联互通四甲的"三评"，必须在开发启动前补齐以下工作：

1. **第 1-2 个月**：完成合规架构设计书，包含网络分区图、三权分立矩阵、PHI 数据流图、病历版本管理设计、FHIR/EMPI 部署方案、国密改造路线图；
2. **第 2-3 个月**：搭建合规基线（IAM、审计平台、KMS、CA 对接、脱敏视图、WORM 日志）；
3. **开发全程**：架构宪法 12 条作为 PR 门禁；
4. **上线前**：完成等保三级测评、PIA 报告、病历篡改检测验证、FHIR 接口互操作测试、医保联调；
5. **信创节奏**：生产环境第一期可 x86 + 开源，但架构预留国产替换点；第二期根据医院招标要求切换。

**不补齐上述缺口直接开发，预计在等保测评、电子病历六级评审、互联互通四甲测评中分别出现 3-5 项不符合项，整改周期 3-6 个月。**
