# 01 · 健澜杠OS 产品需求文档（PRD）

> 版本：v1.0
> 撰写日期：2026-10-19
> 撰写人：产品总监 / 运营 VP
> 事实来源：`00-决策基线.md`（唯一事实源）、`review-2-compliance.md`、`review-4-business-cost.md`

---

## 0. 文档导读

本 PRD 不写"提供智能化解决方案"这类空话。每一条需求都落到一个具体岗位、一个具体工位、一个具体时间点：

- 工位 1：门诊大厅导诊台（上午 8:00-11:30 高峰，3000 人次/3 小时）
- 工位 2：医生工作站（呼吸内科主治医师，日接诊 60-80 人次）
- 工位 3：护士站（普外科病区 45 床，白班 8 名护士管 45 个病人）
- 工位 4：收费窗口（日门诊 1 万人次，峰值窗口吞吐 3000 QPS 挂号）
- 工位 5：病案室质控岗（出院病历 180 份/日，人工质控 4 人/班）
- 工位 6：信息科值班室（3-5 人，传统 Windows 运维背景）

所有需求均按"双轨并行"原则切分：A 轨（0-6 月）是先卖钱的 AI 科室产品，B 轨（6-24 月）是渐进替换 HIS 核心域的模块化单体。

## 1. 产品定位

### 1.1 一句话定位

**健澜杠OS 是"挂在医院现有 HIS 旁边的 AI 智能层"，不是全栈 HIS 替换产品。**

它不替代医院已经在用的卫宁 WiNEX、东华 DHRIP、创业睿医或东软 HIS。它做三件事：

1. 在现有 HIS 的数据出口（视图、中间库、HL7/FHIR 接口）旁路取数；
2. 在医生工作站、护士站、门诊大屏、患者小程序四个触点上叠加 AI 能力；
3. 在医院需要替换核心域（挂号/收费/医嘱/EMR）时，以"绞杀者模式"逐模块灰度替换，而不是一次性推翻。

### 1.2 为什么不能做全栈 HIS 替换

决策基线 §1.2 已明确：三甲招标硬门槛通常要求"成立 ≥10 年、同类三甲案例 ≥5 个、等保三级、CMMI5"。健澜作为初创公司，**连投标资格都没有**。硬做全栈替换，12 个月 TCO 1800 万期间零收入，而三甲 HIS 项目回款周期 18-36 个月（含 3 年质保金 10%），账上现金撑不到回款。

因此本 PRD 的产品路径是：
- **A 轨（0-6 月）**：AI 科室产品，SaaS 订阅 50-150 万/家/年，科室级决策，不进院级招标，销售周期 3-6 个月，回款 3-6 个月；
- **B 轨（6-24 月）**：Java 模块化单体，先做 EMPI、挂号、门诊收费三个最高并发模块，作为现有 HIS 的"核心域备选"，待 A 轨积累 3 家以上三甲案例后再谈替换。

### 1.3 产品不替代医生决策（SaMD 边界）

依据 `review-2-compliance.md` §2.7 与决策基线 §3.9：所有 AI 输出（病历草稿、诊断建议、用药提醒、导诊建议）均为"提示/建议"，最终医嘱、最终病历、最终处方必须由医生人工确认后才能进入正式医疗记录。UI 上必须显著标注"AI 生成，待医生确认"。这一边界使产品形态规避 II/III 类医疗器械注册证要求。

## 2. 目标客户画像

### 2.1 决策链上的三类人

| 角色 | 关心什么 | 不关心什么 | 买单触发点 |
|---|---|---|---|
| **信息科主任（CIO）** | 系统不宕机、PHI 不泄露、等保三级过评、不影响现有 HIS、出问题有人兜底 | 模型参数、开源协议、微服务框架 | "旁路部署，不动主流程；SLA 99.95%；驻场工程师响应 30 分钟" |
| **分管院长（业务副院长）** | 电子病历六级评审、互联互通四甲、DRG/DIP 控费、患者满意度 | 代码是 Java 还是 Go | "病历质控减少 80% 人工工作量；CDS 降低用药错误率；导诊让门诊效率提升 20%" |
| **临床科室主任** | 病历写得快、值班不被无效电话打断、质控不扣分 | 公司估值、融资轮次 | "出院病历自动质控，明天就少开两个质控会；护理看板把跌倒/压疮风险提前 2 小时报出来" |

### 2.2 目标医院画像

- 床位规模：1500-3000 张（典型 2000 床）；
- 日门诊：8000-15000 人次（典型 10000）；
- 电子病历评级现状：四级（冲五级）或五级（冲六级）；
- 现有 HIS：卫宁 WiNEX / 东华 DHRIP / 创业睿医 / 东软 任一；
- 信息科：3-8 人，传统 Windows + SQL Server 运维背景，**hold 不住原生 K8s + Service Mesh**（这是决策基线 §2.1 选 k3s 而非 kubeadm K8s 的直接原因）；
- 付费预算：科室级 50-150 万/年，院级 300-800 万/年（首期 POC 阶段）。

### 2.3 首批 POC 目标客户

按 `review-4-business-cost.md` §5.2 优先级：
1. **浙江本土三甲**（杭州、宁波、温州）：依托创业慧康浙江本土关系反向切入，重点攻病历质控；
2. **已有东华/卫宁 HIS 但 AI 能力弱的医院**：做"AI 插件"而非竞争对手；
3. **电子病历五级冲六级的医院**：病历版本哈希链、CDS 闭环、护理风险预警是六级必查项，买单意愿最强。

## 3. A 轨产品（0-6 个月，先卖钱）

A 轨保留现有 Bun+TS 单体 BFF 快速包装，后端 Python FastAPI + vLLM 本地推理。四个产品均为旁路模式：不写回 HIS 主库，只在前端叠加视图与提醒。

### 3.1 产品 A1：病历质控 AI

#### 3.1.1 场景

呼吸内科张医生下午 17:30 下班前提交一份出院病历。传统流程：
1. 病案室质控岗次日上午人工翻病历，一份 15-20 分钟；
2. 发现缺陷后打回病区，护士站电话通知医生；
3. 医生修改后再提交，来回 2-3 天；
4. 180 份/日出院病历，4 个质控员全天看不完，月底积压。

#### 3.1.2 用户故事

- 作为**病案室质控员**，我希望出院病历在医生提交后 30 秒内自动跑完完整性、逻辑性、内涵性三层质控，标出缺陷位置并给出修改建议，这样我只需要复核而不是从头看；
- 作为**临床医生**，我希望提交病历前能看到一份"AI 预检查报告"，告诉我主诉和现病史对不上、诊断 ICD 编码缺手术编码、抗菌药使用无感染指征，这样我在提交前就改好，不被打回；
- 作为**分管院长**，我希望每月看到一份全院病历质控热力图：哪个科室缺陷率最高、哪类缺陷最常见，这样我开质控会时有数据。

#### 3.1.3 核心功能清单

| 编号 | 功能 | 说明 |
|---|---|---|
| A1-F01 | 出院病历自动拉取 | 通过 HL7 v2 / 中间库视图，按 Discharge 事件从 HIS/EMR 旁路拉取病历 XML/JSON |
| A1-F02 | 三层质控规则引擎 | 完整性（必填项缺漏）、逻辑性（主诉-诊断-用药一致性）、内涵性（医疗术语合理性） |
| A1-F03 | LLM 内涵质控 | vLLM 本地 Qwen2.5-72B 跑"这份病历是否存在临床逻辑矛盾"，超时 8s 切规则模板 |
| A1-F04 | 缺陷定位与建议 | 在病历原文上高亮缺陷段落，右侧面板给出"建议修改为……" |
| A1-F05 | 医生端预检查 | 医生工作站插件，提交前一键自检，返回 0-100 分 |
| A1-F06 | 质控打回闭环 | AI 生成质控意见 → 医生端弹窗 → 医生"采纳/修改/拒绝"三态反馈 → 未采纳样本回流再训练（决策基线 §6.14） |
| A1-F07 | 科室质控看板 | 月度缺陷率、返工率、平均修改时长，按科室下钻 |
| A1-F08 | 哈希链存证 | 每次质控结果 append-only 入库，prev_hash + row_hash（SM3），对接 TSA 时间戳（依据 `review-2` §2.4） |

#### 3.1.4 输入 / 输出

- 输入：HIS/EMR 旁路视图（患者ID 脱敏 token、主诉、现病史、诊断、手术、用药、检验、护理记录）；
- 输出：结构化缺陷清单 JSON + 病历原文高亮 HTML；
- **合规边界**：AI 节点 Pod 在 K8s NetworkPolicy 层禁止直连生产 PHI 库，仅允许访问独立脱敏视图（决策基线 §3.1、§6.6）。姓名/身份证/手机/病案号全部替换为 token。

#### 3.1.5 验收标准

- 一份 3000 字出院病历，端到端质控耗时 P95 ≤ 30 秒，P99 ≤ 60 秒；
- 完整性规则命中率 ≥ 99%（必填项缺漏必须 100% 抓到）；
- 内涵质控误报率 ≤ 20%（质控员复核后认为"AI 误判"的比例）；
- 与医院现有 4 人/班质控岗对比，人工复核时长下降 ≥ 60%；
- 连续运行 30 天，PHI 字段在 AI 节点日志中出现次数 = 0（审计抽查）。

### 3.2 产品 A2：AI 导诊 / 预问诊

#### 3.2.1 场景

周一上午 8:30，门诊大厅涌入 1500 人。传统流程：
1. 患者排队到导诊台，护士口头问"哪里不舒服"，平均 2-3 分钟/人；
2. 8 个导诊护士台，3 小时最多服务 480 人，剩下 1000 人瞎排队；
3. 挂错号率约 15%（挂了心内科实际该挂呼吸科），到诊室后被医生退回重新挂号。

#### 3.2.2 用户故事

- 作为**门诊患者**，我在小程序上输入"咳嗽 3 天、低烧 37.8℃、有黄痰"，AI 立刻告诉我"建议挂呼吸内科普通号，今天 10:00-11:00 还有号，路径是门诊楼 3 楼东区"，并在我到院前生成一份结构化预问诊单；
- 作为**分诊护士**，我希望导诊台的自助机把 80% 简单分诊吃掉，我只处理疑难（胸痛、晕厥、儿童高烧）；
- 作为**出诊医生**，我打开医生工作站，已经能看到患者预问诊的结构化主诉、既往病史、当前用药，**比患者自己口述更准**，省 3 分钟问诊时间。

#### 3.2.3 核心功能清单

| 编号 | 功能 | 说明 |
|---|---|---|
| A2-F01 | 小程序对话式预问诊 | 多轮对话，症状引导（部位-持续时间-加重因素-伴随症状），最终收敛到 ICD-10 科室推荐 |
| A2-F02 | 科室/号源实时查询 | 旁路读 HIS 挂号剩余号源（只读），推荐可挂号的时段 |
| A2-F03 | 自助导诊机 | 门诊大厅 8 台自助机，方言+普通话双语语音交互 |
| A2-F04 | 预问诊单结构化输出 | 主诉/现病史/既往史/过敏史/当前用药，XML 推送至医生工作站 |
| A2-F05 | 急症识别与拦截 | 胸痛/呼吸困难/意识障碍关键词触发"请立即前往急诊"，并自动联系急诊分诊台 |
| A2-F06 | 满意度回流 | 患者看完病后评价导诊准确性，错分样本回流 |

#### 3.2.4 输入 / 输出

- 输入：患者自然语言症状描述、HIS 科室字典与号源状态；
- 输出：科室推荐 + 号源时段 + 结构化预问诊单；
- **合规边界**：明确标注"AI 导诊不替代医生诊断"；急症拦截仅引导至急诊，不做诊断。

#### 3.2.5 验收标准

- 预问诊平均轮数 ≤ 5 轮，端到端耗时 ≤ 90 秒；
- 科室推荐与医生最终科室一致率 ≥ 85%；
- 门诊大厅导诊台人工分流压力下降 ≥ 50%（高峰时段护士呼叫次数对比）；
- 急症关键词召回率 100%（漏判 = 医疗事故红线，必须零漏）；
- 小程序日活导诊用户数 ≥ 3000（1 万门诊的 30%）。

### 3.3 产品 A3：CDS 临床决策支持

#### 3.3.1 场景

普外科李医生开医嘱：头孢曲松 2g ivgtt qd + 头孢克肟 200mg po bid。传统流程：
- 两种头孢重复用药，药师事后发药时才发现，此时医嘱已执行；
- 检验血钾 2.8 mmol/L（危急值），护士 30 分钟后才看到电话报告，期间医生可能继续开利尿剂。

#### 3.3.2 用户故事

- 作为**开医嘱的医生**，我在医生工作站输入药品时，系统实时弹"与您 1 小时前开的头孢曲松同类，是否重复？"，我一键确认或取消；
- 作为**值班医生**，检验危急值一出现，我的工作站立刻弹窗+手机短信，要求 5 分钟内签收，否则升级到二线；
- 作为**临床药师**，我希望看到全院药物相互作用日志，哪些医生高频踩坑，用于药事培训。

#### 3.3.3 核心功能清单

| 编号 | 功能 | 说明 |
|---|---|---|
| A3-F01 | 实时用药规则拦截 | 药物相互作用、重复用药、过敏史冲突、肝肾功能禁忌、剂量超上限，规则引擎（Drools）硬拦截 |
| A3-F02 | 检验危急值闭环 | LIS 旁路订阅危急值事件 → 医生工作站弹窗 → 签收（5 分钟超时升级）→ 处置记录 |
| A3-F03 | 个性化推荐 | 基于患者既往病历，LLM 软提示"该患者既往对青霉素过敏史，请谨慎" |
| A3-F04 | 规则知识库 | 内置国家处方集 + 抗菌药物临床应用指导原则，季度更新；支持医院自定义规则 |
| A3-F05 | 医生反馈闭环 | 每条提示有"采纳/修改/拒绝/误报"四态，误报率周报复盘 |
| A3-F06 | 审计留痕 | 所有 CDS 提示与医生响应入审计日志，留存 ≥ 6 个月（等保三级 8.3.5） |

#### 3.3.4 输入 / 输出

- 输入：医生工作站医嘱流（旁路订阅）、LIS 检验结果（旁路）、患者过敏史/肝肾功能（脱敏视图）；
- 输出：实时弹窗、硬拦截、签收工单；
- **合规边界**：
  - 硬拦截（过敏、严重相互作用）走规则引擎，不经过 LLM，确定性可解释；
  - 软提示（个性化推荐）走 LLM，明确标注"AI 辅助，医生确认"；
  - **最终医嘱必须医生点击确认**，CDS 不自动改医嘱（`review-2` §2.7 SaMD 边界）。

#### 3.3.5 验收标准

- 用药规则拦截响应 P99 < 200ms（与挂号同 SLA，不拖慢医生工作站）；
- 危急值从 LIS 产生到医生弹窗 ≤ 5 秒；
- 危急值 5 分钟签收率 ≥ 95%；
- 医生硬拦截误报率 ≤ 5%（超过则医生会"无脑点忽略"，产品失效）；
- 上线 6 个月，全院用药错误事件率下降 ≥ 30%（医院质控数据对比）。

### 3.4 产品 A4：护理看板

#### 3.4.1 场景

普外科病区 45 床，白班 8 名护士。传统流程：
- 早上 7:30 交接，护士长对着白板手工排班，谁管 1-15 床、谁管 16-30 床；
- 32 床王大爷昨晚起夜摔了一跤，没人知道他属于"跌倒高风险"（Morse 评分 55 分）；
- 护士站在 4 楼，输液架上的点滴打完了，患者按铃，护士跑过来要 2 分钟。

#### 3.4.2 用户故事

- 作为**护士长**，我希望系统根据患者数量、护理等级、护士资质、N1-N4 能级，自动生成排班建议，我 5 分钟调完而不是 30 分钟；
- 作为**责任护士**，我进入病房前，手持 PDA 已经提示"32 床 Morse 跌倒评分 55，床栏已拉起；18 床 Braden 压疮评分 12，2 小时内需要翻身"；
- 作为**科护士长**，我希望看到病区实时风险热力图：哪些患者跌倒/压疮/非计划拔管风险升高。

#### 3.4.3 核心功能清单

| 编号 | 功能 | 说明 |
|---|---|---|
| A4-F01 | 智能排班 | 输入护理任务量、护士能级、休假、资质，输出排班建议，护士长可拖拽调整 |
| A4-F02 | 风险预警 | Morse 跌倒、Braden 压疮、MNA 营养、非计划拔管量表自动计算，风险升高实时推送 |
| A4-F03 | 护理任务看板 | 输液、口服药、测血压、翻身、护理记录，按床号聚合，已做/待做/超时三色灯 |
| A4-F04 | 床头卡电子屏 | 每床一块小屏，显示患者护理等级、饮食、过敏史、今日重点（非 PHI 明文，屏上按角色脱敏） |
| A4-F05 | 交接报表 | 交班时自动生成"重点关注患者清单"（高风险 + 新入院 + 手术当天），护士长打印或扫码带走 |

#### 3.4.4 输入 / 输出

- 输入：HIS 医嘱执行记录（旁路）、护理评估表（护士录入）、护士排班表（HR 系统旁路）；
- 输出：排班建议、风险预警、任务看板；
- **合规边界**：床头卡屏属于公共区域显示，PHI 字段（姓名、诊断）按"床号 + 姓氏 + 护理等级"脱敏显示，不显示完整诊断与身份证号。

#### 3.4.5 验收标准

- 排班生成耗时 ≤ 30 秒（45 床 / 8 护士场景）；
- 排班建议与护士长最终排班一致率 ≥ 70%（低于此则没人用）；
- 高风险患者风险预警提前量 ≥ 2 小时（在事件发生前触发）；
- 上线 6 个月，病区跌倒/压疮事件率下降 ≥ 25%；
- 护理记录书写时长人均每日减少 ≥ 30 分钟。

### 3.1.6 真实场景走查（周一上午 9:00 急诊后转入住院的肺脓肿患者）

呼吸内科张医生周一上午收了一个 58 岁男性肺脓肿患者，从急诊转上来，周二下午做完胸腔穿刺，周三上午主任查房后开出院。整个病历包含：急诊留观记录 6 小时、入院记录 1 份、首次病程记录、日常病程记录 3 份、三级检诊记录（住院医师写、主治医师修改、主任医师审）、手术/操作记录（胸腔穿刺）、麻醉记录摘要、知情同意书 2 份（操作同意书 + 输血同意书）、出院小结、医嘱单 12 张、护理记录单 24 小时。

## 4. B 轨产品（6-24 个月，核心域渐进替换）

B 轨基于 Spring Boot 3.5.3 + Spring Modulith 1.4（Java 21），单进程多模块起步，跨模块走本地事件。与现有 HIS 的对接方式统一为"旁路读写 + 灰度切流"：先以双写模式并行 4-8 周，确认数据一致后，再把流量从老 HIS 切到新模块。

### 4.1 模块 B1：患者主索引 EMPI

#### 4.1.1 核心功能

- 跨系统患者身份合并：同一患者在 HIS、体检系统、互联网医院、检验系统里有多个 patient_id，EMPI 通过姓名+性别+出生日期+手机号+身份证号多因子概率匹配，生成全局 EMPI ID；
- 查重/合并/拆单工作台：信息科人工审核疑似重复档案；
- IHE PIX/PDQ Profile 暴露 FHIR Patient 接口（互联互通四甲必查项，决策基线 §2.6、`review-2` §2.3）；
- 患者主索引变更审计：谁合并了哪两个档案、什么时间、审批人是谁，全留痕。

#### 4.1.2 与现有 HIS 旁路对接

- 上线初期：EMPI 只读老 HIS 患者表，每晚跑批生成匹配建议，信息科审核；
- 灰度期：新业务（互联网医院注册）写入 EMPI，再同步到老 HIS；
- 替换期：老 HIS 患者服务下线，所有系统直连 EMPI。

#### 4.1.3 为什么 EMPI 是 B 轨第一优先级

大三甲医院普遍存在"一个人多个档案"的问题：王阿姨 10 年前在门诊挂过号（档案 A）、3 年前住院（档案 B）、去年用互联网医院注册（档案 C）。老 HIS 里这三个 patient_id 互不相通，导致：
- 医生在门诊看不到王阿姨 3 年前的住院记录；
- 检验系统里王阿姨的历史检验结果散在三个档案下；
- 体检系统的健康数据无法回流到临床。

EMPI 不做，后面所有模块（挂号、收费、医嘱、EMR）都是"在错误的患者身份上建高楼"。所以 B 轨第一刀必须切 EMPI，即使它不直接产生收入。

### 4.2 模块 B2：挂号（registration）

#### 4.2.1 核心功能

- 当日挂号、预约挂号、加号、退号、号源池管理；
- 分时预约（15 分钟段），号源释放规则（提前 15 分钟未取号释放）；
- 多渠道：窗口、自助机、小程序、公众号、第三方平台（支付宝/微信健康）；
- 医保电子凭证扫码挂号；
- 与 HIS 老挂号模块双写对比。

#### 4.2.2 性能硬指标

依据决策基线 §4.1：
- 峰值 QPS = 3000（周一上午 8:00-8:30 半小时内集中挂号）；
- P99 响应 < 200ms；
- Pod 数 = 6，每 Pod 4C8G，HikariCP 连接 ≤ 15/实例；
- 前置 PgBouncer transaction 模式（pool_size=50、max_db_connections=150），防连接风暴；
- 限流 3000 QPS/集群；医保外呼 P99 > 1.5s 时，降级为"先自费后追溯退费"（决策基线 §4.3）。

#### 4.2.3 与现有 HIS 旁路对接

- 阶段 0（M6-M9）：新挂号模块只接小程序渠道，窗口与自助机仍走老 HIS；
- 阶段 1（M9-M12）：自助机切流 50%；
- 阶段 2（M12+）：全渠道切流，老 HIS 挂号模块进入只读归档。

#### 4.2.4 降级场景走查（医保平台挂了）

周一 8:05，医保局专网抖动，医保外呼 P99 从 200ms 飙到 2.5 秒。传统 HIS 会卡住——每个挂号请求都要等医保返回，窗口排队 50 人，患者开始吵。

健澜挂号模块的降级路径：
- 8:05:10：APISIX 检测到医保外呼 P99 > 1.5 秒，自动触发熔断；
- 8:05:11：挂号请求改为"先自费后追溯退费"——患者先按全价挂号，HIS 正常出号；
- 8:05:12：后台异步队列记录"待医保结算"任务；
- 8:30：医保恢复，异步队列批量补结算，多收的钱原路退回患者账户；
- 患者感知：挂号速度没变慢，3 天后收到"医保已报销 18 元"的推送。

这就是决策基线 §4.3 写"先自费后追溯退费"的原因——**不能让医保平台的故障堵死医院门口**。

### 4.3 模块 B3：门诊收费（outpatient-charge）

- 收费/退费/发票管理、医保实时结算、电子票据；
- 医保外呼独立 medical-insurance 服务，通过医保专网/CA 出院（决策基线 §3.8）；
- 日对账/月对账异步化，对账失败人工干预工作台；
- 峰值 800 QPS，4 Pod，每 Pod 4C8G。

### 4.4 模块 B4：医嘱（orders）

- 门诊医嘱、住院医嘱、长嘱/临嘱、停药/改量；
- 医嘱闭环：开具 → 审核 → 执行 → 核对 → 签名（Kafka 事件驱动）；
- 麻精药品专册双人核对硬编码；
- 与 A3 CDS 模块通过本地事件订阅，开医嘱时实时调用规则引擎；
- 峰值 500 QPS，3 Pod。

### 4.5 模块 B5：药房（pharmacy）

- 门诊药房发药、住院摆药、库存管理、近效期预警；
- 药品字典与医保目录映射；
- 与医嘱模块通过 Kafka 事件驱动，医嘱执行自动触发摆药任务。

### 4.6 模块 B6：护理（nursing）

- 护理记录、体温单、评估表、医嘱执行单；
- 与 A4 护理看板共享数据底表，A4 是前端视图，B6 是业务内核。

### 4.7 模块 B7：EMR 核心（emr-core）

- 病历文书结构化存储、模板管理、三级检诊（住院医师/主治/主任）；
- **append-only 版本表 + 哈希链 + TSA 时间戳 + CA 签章**（决策基线 §3.2、`review-2` §2.4，电子病历六级必查）；
- 归档病历 PDF 化后二次签章，入 WORM 存储；
- 门诊病历保存 ≥ 15 年，住院病历保存 ≥ 30 年；
- 峰值 200 QPS，3 Pod；
- AI 辅助书写（A1/A3）生成的草稿，必须医生人工编辑后签发，AI 内容不直接入档。

### 4.8 中台模块（贯穿）

- **FHIR Server**（HAPI FHIR 二开）：独立部署，IHE PIX/PDQ/XDS/ATNA Profile，互联互通四甲必配；
- **术语服务**：ICD-10、ICD-9-CM3、LOINC、SNOMED CT、ATC 统一字典；
- **医保服务**：CHS 接口、DRG/DIP 分组器，季度跟随国家版本更新；
- **审计服务**：所有 PHI 访问（读/写/导出/打印）入 Kafka → WORM 存储，留存 ≥ 180 天。

### 5.1 性能

| 服务 | 峰值 QPS | P99 延迟 | Pod 数 | CPU/内存 |
|---|---|---|---|---|

JVM：ZGenerational ZGC，目标 P99 停顿 < 1ms；4C8G 容器堆定 4G（-Xms4g -Xmx4g）；CronHPA 早 7:00 预热到 6 Pod。

### 5.2 可用性

- **目标 99.95%**（年停机 ≤ 4.3 小时），不是 99.99%（决策基线 §1.3，对 <30 人团队 99.99% 是财务自杀）；
- 主备同城，Patroni 同步流复制，RPO=0、RTO ≤ 5 分钟；
- Redis 哨兵（1 主 2 从 3 哨兵）；
- Kafka 3 Broker，min.insync.replicas=2，acks=all；
- 不做双活（对 <30 人团队过度设计）；
- 部署形态分三阶段：Docker Compose + systemd + Keepalived（POC）→ 双机主备 Patroni（1-2 家生产）→ k3s 1.30 全封装离线 Helm Chart（≥3 家）。

### 5.3 合规与安全

- **等保三级**：三权分立（系统管理员/安全管理员/审计管理员）、审计日志全量留存 ≥ 6 个月、入侵防范、恶意代码防范按 GB/T 22239-2019 8.1-8.5 逐项映射；
- **电子病历六级**：append-only + 哈希链 + TSA + CA 签章、CDS 闭环、全流程数据可追溯；
- **互联互通四甲**：FHIR Server + EMPI + IHE PIX/PDQ/XDS/ATNA；
- **国密改造**：SM2 签名 / SM3 摘要 / SM4 存储加密，TLS 替换 GMSSL（依据《密码法》第 27 条）；
- **数据安全**：AI 节点 NetworkPolicy 硬隔离，禁止直连生产 PHI 库；禁止境外大模型 API（OpenAI/Claude/Gemini），vLLM 必须本地开源模型（Qwen2.5-72B / DeepSeek-V3 / GLM-4）；
- **个保法**：PHI 列加密、字段级脱敏、PIA 报告、患者单独同意。

### 5.4 信创路线图

- 数据库：PostgreSQL 16 → 达梦 8（M6-M9 迁移，3-6 月）；
- CPU：x86 → 鲲鹏 920（M9-M18）；
- OS：Ubuntu/CentOS → 麒麟 V10 / 统信 UOS；
- JDK：OpenJDK 21 → 毕昇 JDK；
- AI 推理：初期 NVIDIA H20 96GB × 2 节点，Q4 启动昇腾 910B 适配；
- 数据库方言必须抽象（MyBatis 方言层），禁止手写 PG 特有 JSONB/数组/窗口函数特例。

### 5.5 可观测性

- 统一 traceId：OpenTelemetry SDK（Java / Python / TS 三语言 artifact），BFF 入口生成 traceparent 并透传；
- 日志统一 JSON，Loki + Promtail 采集；
- 指标 Prometheus + Grafana；
- 链路 Jaeger；
- 告警阈值：CPU > 80%、内存 > 85%、P99 > 300ms、5xx > 1%、磁盘 > 80%、PG 主从延迟 > 1s。

## 6. 功能优先级（MoSCoW）

### 6.1 Must have（不做不能上线）

- A1 病历质控：完整性规则引擎 + 医生端预检查 + 审计日志；
- A2 AI 导诊：小程序预问诊 + 急症拦截零漏判；
- A3 CDS：用药规则硬拦截 + 危急值闭环签收；
- A4 护理看板：风险预警（Morse/Braden）+ 交班重点清单；
- B 轨基础设施：k3s 离线 Helm Chart、Patroni 主备、PgBouncer、国密 SM4 存储加密；
- 合规基线：三权分立、审计 WORM、PHI 脱敏视图、AI 节点 NetworkPolicy 隔离。

### 6.2 Should have（GA 后 3 个月内补齐）

- A1：LLM 内涵质控、科室质控热力图；
- A2：自助机语音交互、方言识别；
- A3：个性化推荐（LLM 软提示）、临床药师药事报表；
- A4：智能排班自动建议、床头卡电子屏；
- B 轨：EMPI 跨系统合并、挂号多渠道全量切流、门诊收费医保实时结算。

### 6.3 Could have（GA 后 6 个月内择机做）

- B 轨：医嘱闭环、药房摆药、护理内核；
- 中台：FHIR Server IHE XDS Profile、术语服务 ICD-11 映射；
- AI：未采纳样本回流再训练流水线、模型仓库 cosign 签名。

### 6.4 Won't have（本版本不做）

- 影像 AI 识别（PACS 域，需 NMPA II/III 类注册证）；
- 病理切片 AI；
- 基因/蛋白组学数据分析（人类遗传资源审批红线）；
- 双活数据中心（对 <30 人团队过度设计）；
- Service Mesh / Istio（12 个月内禁用，决策基线 §2.1）；
- Seata AT 分布式事务（挂号高峰会锁死 patient_id 索引，P99 秒级，决策基线 §2.2）。

## 7. 明确不做什么（产品边界）

为避免团队精力分散，本 PRD 明确以下边界：

1. **不做 PACS（影像归档与通信系统）**：影像数据量大、DICOM 协议复杂、有专门的厂商（东软、联影、锐珂）。健澜只通过 DICOM 网关旁路读取影像报告文本，不存储影像本身；
2. **不做 LIS（检验信息系统）**：只订阅 LIS 危急值与检验结果事件，不替代 LIS 做标本流转、仪器对接；
3. **不做手术室麻醉系统**：麻醉机监护数据对接、手术室排班、气切记录等属于高风险域，需要专门医疗器械资质；
4. **不做 HRP（医院资源规划）/ 财务总账 / 固定资产**：这些是用友、金蝶、东软望海的地盘；
5. **不做互联网医院自营诊疗**：只做院内 HIS 的 AI 增值，不做跨院问诊平台（那是京东健康、阿里健康的战场）；
6. **不做全栈一次性替换 HIS**：B 轨是模块化绞杀者，不是推翻重来；
7. **不做面向 C 端的健康管理 App**：不做运动、睡眠、饮食建议，聚焦院内临床场景；
8. **不做境外大模型 API 调用**：数据出境红线，vLLM 必须本地开源模型。

## 9. 风险与依赖

1. **医疗 Domain Expert 招不到**：A 轨所有产品的临床规则都依赖这个岗位。招不到则项目不启动（决策基线 §5.2）；
2. **POC 客户决策慢**：三甲信息科主任"不敢用年轻公司"是默认态度，需要通过免费 4 周 POC + 驻场工程师建立信任；
3. **等保三级整改**：若 PHI 脱敏、三权分立、WORM 日志任何一项不到位，等保测评会出 3-5 项不符合，整改 3-6 个月；
4. **信创适配超期**：达梦 8 迁移预估 3-6 个月，若 M9 还没完成，投公立三甲标会被一票否决；
5. **vLLM 昇腾适配**：Q4 启动昇腾 910B 适配，性能若不达 NVIDIA H20 的 70%，信创路线需重新评估。

## 10. 附录：术语表

- **EMPI**：Enterprise Master Patient Index，企业级患者主索引；
- **CDS**：Clinical Decision Support，临床决策支持；
- **POC**：Proof of Concept，概念验证；
- **PHI**：Protected Health Information，受保护健康信息（含姓名/身份证/手机/住址/病案号）；
- **SaMD**：Software as a Medical Device，医疗器械软件；
- **RPO/RTO**：恢复点目标 / 恢复时间目标；
- **WORM**：Write Once Read Many，一次写入多次读取存储（审计日志专用）；
- **MoSCoW**：Must / Should / Could / Won't 优先级方法。
