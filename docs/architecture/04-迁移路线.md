## 0. 本路线的核心立场（先读这一段）

**本路线不是"12 个月全量重构到 Java+Python+TS 三层微服务 + K8s + Spring Cloud 全家桶"，而是"双轨并行 18-24 个月、模块化单体起步、合规与信创硬约束前置、AI 造血反哺重构"。**

三条不可动摇的前提：

1. **A 轨先造血，B 轨后重构**。12 个月全量重构 TCO 约 1800 万、期间零收入，三甲 HIS 项目回款 18-36 个月，初创账上现金撑不到回款。必须用业务养技术，不能用融资养技术。
2. **Java 核心以 Spring Modulith 模块化单体内起步，不 Day-1 上微服务**。第 3 个模块需要独立扩缩容时，才引入 Spring Cloud Alibaba + Nacos。
3. **合规与信创是硬约束，不是收尾工作**。等保三级、电子病历六级、互联互通四甲、国密 SM2/SM3/SM4、信创适配，全部前置到 B 轨 M13-M24 的关键路径上，不允许"先上线再补测评"。

## 1. 总体迁移原则

### 1.1 绞杀者模式（Strangler Fig）——唯一可解释、可回滚的路径

现有 Bun+TS 单体 BFF 承载 1957 路由，全量重写是自杀。按业务域逐一切流、门面层路由、双写对账、灰度回滚，是唯一在三甲客户面前可解释、可回滚的路径。

- **老单体不推倒**：TS BFF 保留为聚合层，逐步"绞杀"其中的业务路由。
- **新服务按域切入**：patient-master、registration、outpatient-charge 三个最高并发核心域先行。
- **门面层（ACL）统一切流**：所有流量先过 `gangos-gateway`，由它决定走老单体还是新 Java 服务。
- **回滚预算**：每次灰度切流必须有"10 秒内切回老单体"的预案；路由规则变更必须在预发环境演练回滚。

### 1.2 门面层 ACL（Anti-Corruption Layer）

在现有 Nginx/APISIX 之上加一层 Router Service（TS/Bun），按 URL 规则路由到老单体或新服务：

```
client
  ▼
APISIX 3.9
  ▼
gangos-gateway (TS, port 8080)
  ├── /api/v2/emp/*      → svc-emp (Java Modulith)
  ├── /api/v2/reg/*     → svc-reg (Java Modulith)
  ├── /api/v2/charge/*   → svc-charge (Java Modulith)
  ├── /api/v2/orders/*   → svc-orders (Java Modulith)
  ├── /api/v2/emr/*     → svc-emr (Java Modulith, M13+)
  ├── /api/v2/ai/*      → ai-orchestrator (Python, 8100)
  └── /*                → legacy-monolith (TS/Bun, 8090)   ← 老单体
```

规则配置在 APISIX Dashboard，**改路由 = 改配置，不改代码**。路由维度支持三种：按 URL 前缀、按患者 ID 尾号、按科室 ID。

### 1.3 双写 + 灰度 + 回滚

- **双写**（仅挂号/收费/发药三个强一致域）：老单体写主表，新服务写影子表（`*_shadow`）；Outbox Relay 把老单体写事件投 Kafka，新服务消费后写自己的库。每日凌晨对账，差异 >0.1% 报警。
- **灰度**：1% → 10% → 50% → 100%，按患者 ID 尾号切；先放一个非急诊科室试点，再放主任专家团队自愿试点。
- **回滚**：APISIX 配置热更新秒级切回老单体；影子表数据保留 30 天；新服务写库失败自动 fallback 到老单体写。

### 1.4 双轨并行的组织保障

双轨并行不只是技术路线，更是组织路线。PMO 在 M1 起即按双轨配置人力与汇报线：

- **A 轨责任人**：产品经理 + Python AI 负责人，向 CTO 汇报，每周一晨会同步商务漏斗、POC 交付、模型指标。
- **B 轨责任人**：首席架构师 + Java 高级负责人，向 CTO 汇报，每周三技术评审会同步模块进度、压测结果、合规缺口。
- **共享资源**：运维、合规、Domain Expert 为两轨共享，按周排期；冲突时由 CTO 裁决，优先级原则是"A 轨 POC 现场支持 > B 轨开发"。
- **决策门评审委员会**：CTO、CEO、首席架构师、PMO、合规官五人，每个决策门召开半天评审会，输出 Go/No-Go 结论与签字记录。

## 2. A 轨（AI 造血，M1-M6）详细里程碑

A 轨定位：保留现有 Bun+TS 单体 BFF，聚焦 AI 科室产品——病历质控、AI 导诊、CDS 辅助、护理看板。产品形态为"AI 增值模块"，挂在医院现有 HIS 旁边跑（旁路模式），不碰主流程。

### M1：病历质控 AI MVP 启动（旁路读 HIS 数据）

- **目标**：用现有 TS 单体 BFF 的只读通道，搭出病历质控 AI 的最小可演示版本。
- **交付物**：
  1. `ai-orchestrator` FastAPI 骨架（Uvicorn，worker=CPU×2）；
  2. vLLM 本地部署 Qwen2.5-72B-Instruct（或 DeepSeek-V3），OpenAI 兼容接口 `http://localhost:8000/v1`；
  3. 病历质控规则集 v0（20 条：缺主诉、缺现病史、诊断与用药不符、ICD 编码缺失等）；
  4. 旁路读通道：从 HIS 只读库抽取出院病历文本，入脱敏视图（姓名/身份证/手机/住址 token 化）；
  5. 前端质控结果页 React 19 + Vite 6 原型。
- **负责人**：Python AI 负责人（2 人）、医疗 Domain Expert（1 人）、前端（1 人）。
- **风险**：
  - vLLM 单卡并发仅 60-80 路，MVP 阶段并发低，不构成瓶颈；
  - 脱敏视图若未做好，直接读生产 PHI 库，违反《个保法》第 28 条——M1 必须完成 NetworkPolicy 硬隔离；
  - 境外 API 红线：M1 起禁止任何 OpenAI/Claude/Gemini 调用，出口 URL 黑名单在 APISIX 配好。

### M2：病历质控 MVP 内测 + 反馈闭环

- **目标**：在公司内部模拟病历数据 + 1-2 家关系医院的历史病历（脱敏后）内测，跑通"AI 出质控意见 → 医生采纳/修改/拒绝"闭环。
- **交付物**：
  1. AI 输出 UI 强制带"采纳/修改/拒绝"三按钮（宪法第 14 条）；
  2. 未采纳样本自动回流到训练数据集目录；
  3. 质控报告 PDF 导出；
  4. 内测报告：准确率、误报率、医生满意度（NPS）；
  5. 8s 超时阈值验证：超过 8s 切规则引擎模板，医生工作站不干等。
- **负责人**：Python AI 负责人、产品经理（1 人，Q2 到岗）、测试（1 人）。
- **风险**：
  - 误报率 >30% 会让医生弃用——M2 末误报率必须压到 20% 以下；
  - 反馈闭环若未埋点，后期无法迭代——埋点 SDK 必须 M2 完成。

### M3：签第 1 家 POC（现场部署）

- **目标**：以"AI 病历质控模块"名义签第 1 家 POC 合同，金额 20-50 万，周期 3 个月。
- **交付物**：
  1. POC 合同 + SOW（范围、验收标准、数据合规条款）；
  2. 现场部署包：vLLM + FastAPI + 旁路只读通道，全部离线 tar 包；
  3. 数据合规附件：患者知情同意书覆盖"去标识化数据用于模型训练"条款；
  4. PIA 报告（个人信息保护影响评估）v1。
- **负责人**：CEO/商务、产品经理、交付经理（Q3 到岗前由架构师兼）。
- **风险**：
  - 三甲招标硬门槛（成立≥10 年、同类案例≥5 个、等保三级）初创不具备——POC 只能走民营医院/县级三甲/关系医院，不冲大三甲；
  - 现场网络隔离要求：vLLM 节点不得直连生产 PHI 库，必须走医院信息科提供的脱敏视图——M3 合同里必须写清"数据通道由院方提供"。

### M4：POC 现场部署 + 跑通

- **目标**：第 1 家 POC 现场上线，连续稳定运行 4 周。
- **交付物**：
  1. 现场部署完成报告（含网络拓扑、脱敏视图清单）；
  2. 每日质控报告自动生成；
  3. 医生反馈闭环数据收集（目标：≥50 名医生使用，≥2000 份病历质控）；
  4. POC 中期验收报告。
- **负责人**：交付经理、Python AI 工程师驻场、运维（1 人）。
- **风险**：
  - 医院信息科 3-5 人运维团队接不住——M4 交付包必须是"一键 install.sh"，不允许现场手工编排；
  - GPU 服务器进场：H20 96GB × 2 节点，院方机房电力/散热需提前 2 周确认。

### M5：AI 导诊 + CDS 辅助启动

- **目标**：在病历质控 POC 稳定后，启动第二条产品线——AI 导诊（门诊大厅分诊）+ CDS 辅助（药物相互作用、过敏、重复用药实时弹窗）。
- **交付物**：
  1. AI 导诊原型：患者自然语言描述症状 → 推荐科室 + 就诊建议；
  2. CDS 规则引擎 v0：药物相互作用库（≥5000 对）、过敏库、重复用药检测；
  3. CDS 产品形态边界文档：仅"提示/建议"，最终医嘱必须医生确认（SaMD 规避）；
  4. 签第 2、3 家 POC 的商务材料。
- **负责人**：Python AI 负责人、医疗 Domain Expert、产品经理。
- **风险**：
  - CDS 若直接拦截医嘱，可能构成 II 类医疗器械——M5 必须由 RA/合规评审确认"软提示"形态，不硬拦截；
  - AI 导诊若被患者理解为"诊断"，有医疗纠纷风险——UI 必须显著标注"不替代医生诊断"。

### M6：签第 2、3 家 POC + A 轨阶段总结

- **目标**：A 轨 6 个月结束，签下 3 家 POC，产生首笔收入（目标 100-150 万）。
- **交付物**：
  1. 第 2、3 家 POC 合同；
  2. A 轨半年度复盘：收入、客户数、模型准确率、医生 NPS；
  3. **决策门 D1**：若 3 家 POC 未签满，B 轨暂停（见第 6 节）。
- **负责人**：CEO、PMO、各产品线负责人。
- **风险**：
  - POC 转付费率不及预期——M6 必须开始谈"POC 转年度合同"，不能永远停在 POC；
  - 3 家 POC 同时交付，现场支持人力挤兑——Q3 售后交付 2 人必须 M6 前到岗。

## 3. B 轨（Java 核心重构，M3-M24）详细里程碑

B 轨定位：Java 核心域模块化单体起步，绞杀 TS 单体中的核心交易路由。从 M3 启动（M1-M2 资源全部压 A 轨），到 M24 完成等保三级取证 + 电子病历六级预评估。

### M3：Java Modulith 脚手架 + Nacos + PG + PgBouncer

- **目标**：搭起 Java 侧地基，验证 Spring Boot 3.5.3 + Spring Modulith 1.4（Java 21）单进程多模块骨架可跑。
- **交付物**：
  1. `gangos-trading` Maven 多模块骨架：`mod-emp`、`mod-reg`、`mod-charge`、`mod-pharm`、`mod-shared`、`mod-bootstrap`；
  2. Nacos 2.4 部署（1 主 2 节点）作为配置中心；
  3. PostgreSQL 16 主从 + PgBouncer 1.22 transaction 模式（pool_size=50、max_db_connections=150）；
  4. HikariCP 配置模板：单 Pod maximumPoolSize=15；
  5. JVM 参数模板：ZGenerational ZGC，-Xms4g -Xmx4g；
  6. ESLint 规则强制 BFF 行内 SQL 数 = 0；
  7. Bun 1.4 + Node.js 22 LTS 双运行时 CI 流水线。
- **负责人**：首席架构师、Java 高级工程师（3 人）、运维（1 人）。
- **风险**：
  - 团队首次接触 Spring Modulith，跨模块事件（ApplicationEvent）边界容易被打破——M3 必须定"禁止 @Autowired 对方模块实现类"的 Code Review 规则；
  - PgBouncer 若配错成 session 模式，连接数会暴涨——M3 必须压测验证。

### M4：patient-master（患者主索引）在 Modulith 内跑通

- **目标**：第一个 Java 模块 patient-master 在 Modulith 进程内跑通，提供 EMPI 患者主索引 API。
- **交付物**：
  1. patient-master CRUD + 跨院查重规则（姓名+身份证号模糊匹配）；
  2. Outbox Relay 雏形：本地消息表 + Spring StateMachine Saga，平移现有 `src/bff/outboxRelay.ts`；
  3. MyBatis-Plus 3.5 多方言抽象（PG 实现先，达梦实现留接口）；
  4. 单元测试覆盖率 ≥70%。
- **负责人**：Java 高级 2 人、医疗 Domain Expert（字典规则）。
- **风险**：
  - EMPI 查重规则不准会导致一人多档——M4 必须由 Domain Expert 把规则产品化，不能让开发猜；
  - 禁止 Seata AT：跨模块一致性只用本地消息表 + Saga，M4 必须验证 Saga 补偿事件可重放。

### M5：registration（挂号）跑通

- **目标**：挂号模块在 Modulith 内跑通，支持 3000 QPS 压测。
- **交付物**：
  1. 挂号、预约、退号、号源查询 API；
  2. Sentinel 1.8.8 限流规则：全集群 3000 QPS，单医生 20 QPS；
  3. Redis 号源缓存（Caffeine 1 级 + Redis 2 级）；
  4. `wrk2` 压测报告：P99 < 200ms；
  5. 幂等键 `requestId` 去重机制。
- **负责人**：Java 高级 2 人、运维（压测）。
- **风险**：
  - 号源缓存穿透/击穿/雪崩：空值缓存 60s + Bloom Filter + Redisson 单飞重建 + TTL 抖动——M5 必须逐项验证；
  - 冷启动慢：readiness initialDelay=30s + lazy-init，M5 必须压测冷启动时间。

### M6：outpatient-charge（门诊收费）跑通 + 决策门 D1

- **目标**：门诊收费模块跑通，三个第一批模块在 Modulith 内稳定；**决策门 D1 评审**。
- **交付物**：
  1. 收费、结算、票据 API；
  2. 医保外呼通道雏形（先接测试环境，不碰生产）；
  3. 本地消息表 + Saga 全链路验证（挂号→收费→药房预配药）；
  4. **决策门 D1 材料**：A 轨 POC 数、B 轨 Modulith 稳定性、团队到岗率。
- **负责人**：Java 高级 2 人、首席架构师、PMO。
- **风险**：
  - **决策门 D1 红线**：若 M6 末 A 轨未签满 3 家 POC，B 轨暂停，资源回补 A 轨造血——这是商业基线硬约束；
  - 医保外呼在 M6 不接生产，避免污染 POC 客户。

### M7：orders（医嘱）启动

- **目标**：第二批模块启动，医嘱模块在 Modulith 内跑通。
- **交付物**：
  1. 医嘱开具、审核、执行、核对闭环 API；
  2. Kafka 事件：`order.created`、`order.executed`；
  3. 麻精药品专册、双人核对流程硬编码；
  4. 单元测试 + 集成测试。
- **负责人**：Java 中级 +4（Q2 到岗）、Domain Expert。
- **风险**：
  - 医嘱闭环涉及药房、护理多个下游，Modulith 本地事件容易变成"隐式耦合"——M7 必须定事件 schema 文档。

### M8：pharmacy（药房）+ nursing（护理）启动

## 4. 绞杀者操作手册

### 4.1 门面层如何路由

三种路由维度，按风险从低到高依次使用：

**（1）按 URL 前缀路由（M4 起）**

最安全。新模块上线时，把该模块的 URL 前缀（如 `/api/v2/emp/*`）从老单体切到新 Java 服务。其他 URL 不动。

```yaml
# APISIX route 示例
routes:
  - id: emp-to-java
    uri: /api/v2/emp/*
    upstream:
      type: roundrobin
      nodes:
        "svc-emp:8081": 1
    plugins:
      proxy-rewrite:
        regex_uri: ["^/api/v2/(.*)", "/$1"]
```

**（2）按患者 ID 尾号灰度（M5 起）**

同一 URL，按患者 ID 尾号路由。尾号 0 → 新服务，尾号 1-9 → 老单体。逐步扩大。

```yaml
# APISIX 灰度插件示例
plugins:
  traffic-split:
    rules:
      - match:
          - vars: [["arg_patient_id", "~~", "0$"]]
        weighted_upstreams:
          - upstream:
              name: svc-reg-java
              nodes: { "svc-reg:8082": 1 }
            weight: 100
      - weighted_upstreams:
          - upstream:
              name: legacy-monolith
              nodes: { "legacy:8090": 1 }
            weight: 100
```

**（3）按科室灰度（M9 起）**

先放一个非急诊科室（如体检中心、特需门诊）试点，再放主任专家团队自愿试点。

### 4.2 双写期数据对账脚本怎么写

**影子表设计**：老单体写主表（如 `reg_order`），新服务写影子表（`reg_order_shadow`），结构与主表一致，多三个字段：`shadow_id`、`source`（legacy/new）、`reconcile_status`。

**对账脚本逻辑**（每日凌晨 02:00 跑）：

```sql
-- 1. 找当日主表有、影子表无的记录
SELECT m.id, m.patient_id, m.book_time
FROM reg_order m
LEFT JOIN reg_order_shadow s
  ON s.source = 'new' AND s.biz_id = m.id
WHERE m.book_time::date = CURRENT_DATE - 1
  AND s.id IS NULL;

-- 2. 找影子表有、主表无的记录
SELECT s.id, s.biz_id, s.book_time
FROM reg_order_shadow s
LEFT JOIN reg_order m ON m.id = s.biz_id
WHERE s.shadow_time::date = CURRENT_DATE - 1
  AND m.id IS NULL;

-- 3. 两边都有但字段不一致的（金额、号源、状态）
SELECT m.id,
       m.amount AS m_amount, s.amount AS s_amount,
       m.status AS m_status, s.status AS s_status
FROM reg_order m
JOIN reg_order_shadow s ON s.biz_id = m.id
WHERE m.book_time::date = CURRENT_DATE - 1
  AND (m.amount <> s.amount OR m.status <> s.status);
```

**对账阈值**：
- 差异率 = 差异记录数 / 当日总记录数；
- 差异率 ≤0.1%：通过，出对账报告；
- 0.1% < 差异率 ≤1%：告警，人工复核；
- 差异率 >1%：**立即冻结灰度切流**，回滚到老单体，查根因。

**对账报告**：每日 06:00 自动生成，邮件发给 Java 负责人、DBA、运维。连续 3 天差异率 ≤0.05%，才可进入下一个灰度比例。

### 4.3 灰度切流比例

| 阶段 | 流量比例 | 持续时间 | 准入条件 | 退出条件 |
|---|---|---|---|---|
| G0 | 0% | — | 影子表双写稳定 1 周 | — |
| G1 | 1% | 1 周 | 对账差异率 ≤0.1% | 差异率 >1% 或 P99 > 300ms |
| G2 | 10% | 2 周 | G1 连续 1 周差异率 ≤0.05% | 差异率 >1% 或 P99 > 300ms |
| G3 | 50% | 2 周 | G2 连续 2 周差异率 ≤0.05% | 差异率 >0.5% 或 P99 > 250ms |
| G4 | 100% | 4 周 | G3 连续 2 周差异率 ≤0.05% | 老单体路由下线评估 |

每一步切流必须在业务低峰（晚 22:00 后）进行，切流后驻场观察 2 小时。

### 4.4 回滚预案（一键切回 TS 单体）

**回滚触发条件**（任一）：
1. 对账差异率 >1%；
2. 挂号 P99 > 500ms 持续 5 分钟；
3. 5xx 错误率 >2% 持续 2 分钟；
4. 新服务 Pod 整体不可用（readiness 全失败）；
5. 业务部门投诉（患者挂不上号、收费对不上）。

**一键回滚命令**（APISIX 配置热更新，秒级）：

```bash
# 把 /api/v2/reg/* 全部切回老单体
curl https://apisix:9180/apisix/admin/routes/reg-java \
  -X PPUT -H 'X-API-KEY: $APISIX_KEY' \
  -d '{
    "uri": "/api/v2/reg/*",
    "upstream": {
      "type": "roundrobin",
      "nodes": { "legacy:8090": 1 }
    }
  }'
```

**回滚后动作**：
1. 影子表数据保留 30 天，不删除；
2. 老单体写库恢复为主写，新服务降级为只读消费；
3. 24 小时内出事故复盘报告；
4. 修复后重新从 G1（1%）开始灰度，不跳级。

**回滚演练**：每次灰度切流前，必须在预发环境演练一次回滚，确认 10 秒内完成。

### 4.5 双写期常见问题与处置

双写期（G0-G3 阶段）是故障高发窗口，以下五类问题必须有标准处置预案：

**问题一：影子表漏写（主表有、影子表无）**
- 原因：Outbox Relay 消费延迟、Kafka 消息丢失、新服务消费端异常。
- 处置：对账脚本自动识别后，从 Outbox 表重放该消息；连续 3 天漏写率 >0.1%，暂停灰度升级。

**问题二：影子表多写（影子表有、主表无）**
- 原因：新服务写成功但老单体写失败、或老单体补偿事件未触发。
- 处置：以主表为准，影子表多写记录标记为 `orphan`，不影响业务；每周清理一次。

**问题三：字段不一致（金额、状态）**
- 原因：老单体与新服务业务逻辑差异（如 rounding 规则、状态机定义不同）。
- 处置：Domain Expert 裁决以哪边为准；若是新服务逻辑 bug，修复后重放；若是老单体历史遗留，在新服务侧做兼容映射。

**问题四：灰度切流后 P99 突增**
- 原因：新服务冷启动、连接池预热不足、缓存未命中。
- 处置：观察 5 分钟，若 P99 仍 >300ms，立即回滚；排查慢查询与 GC 日志，修复后从 G1 重新开始。

**问题五：医生投诉（挂号查不到、收费对不上）**
- 原因：双写期数据不一致的用户侧表现。
- 处置：客服/窗口第一时间引导到老单体查询；运维在 30 分钟内定位是哪条记录、哪个尾号段；若影响 >10 个患者，立即回滚。

### 4.6 绞杀者下线判定

老单体不是永远保留。当以下三个条件同时满足时，启动老单体下线流程：

1. 老单体承载流量 <5%，且连续 4 周无增长；
2. 剩余路由全部为管理后台低流量功能，且已排期迁移；
3. 影子表对账连续 8 周差异率 = 0。

下线流程：冻结老单体代码 → 剩余功能迁移到新服务 → 老单体只读运行 4 周 → 只读运行 2 周 → 归档代码库 → 下线服务器。整个下线周期约 8 周，不赶工。

### 5.1 风险监控机制

风险登记册不是一次性文档，PMO 每周五更新一次，每月末由 CTO 主持风险复盘会：

- **红色风险**（概率高 + 影响大）：R1（现金流转负）、R2（医保外呼瓶颈）、R3（vLLM 并发）、R7（达梦适配）。红色风险每周复盘，必须有明确的缓解动作与责任人。
- **黄色风险**（中概率或中影响）：R4、R5、R6、R8、R9。黄色风险每两周复盘。
- **绿色风险**（低概率低影响）：R10。绿色风险每月复盘。
- **新增风险**：任何团队成员发现新风险，24 小时内录入登记册，PMO 在下周例会上评级。
- **风险闭环**：每项风险关闭时，必须有"缓解措施已验证"的证据（压测报告、演练记录、合同条款、测评报告），不能凭感觉关闭。

### 5.2 风险应对的三条铁律

1. **A 轨现金流风险优先于一切技术风险**。当 R1 触发（POC 签不满、现金流转负），B 轨必须暂停，所有 Java/运维资源回补 A 轨——这不是技术决策，是生存决策。
2. **合规风险不接受"先上线再补"**。R4（PHI 直连）、R5（病历哈希链缺失）、R6（FHIR Server 缺失）任一触发，对应模块不得切流，不得上线，没有例外。
3. **性能风险必须有降级预案**。R2、R3、R8 任一触发，必须有"自费降级""规则引擎降级""回滚到老单体"三条退路，不允许硬扛。

**D5 后方向决策**（不在本路线预设）：
- 若三评均过 + A 轨收入稳定：可评估"全栈 HIS 替换"（下一个 24 个月）；
- 若三评有差距 + A 轨收入稳定：继续"AI 增值 + 核心域备选"路线，不碰全栈替换；
- 若 A 轨收入不达预期：收缩 B 轨，回到 A 轨造血优先。

### 6.1 决策门评审流程

每个决策门（D1-D5）按以下流程执行，避免"走过场"：

**T-2 周**：PMO 收集决策门材料（KPI 数据、风险清单、未决项），发给评审委员会预审。

**T-1 周**：各责任人提交自评报告（A 轨收入数据、B 轨技术指标、合规 checklist 完成率、TCO 实际支出）。

**T 日**：半天评审会：
- 各责任人 15 分钟汇报（只讲数据，不讲过程）；
- 评审委员会 30 分钟质询（只问差距，不听解释）；
- 闭门讨论 30 分钟，输出 Go/No-Go/Conditional Go；
- 签字记录归档。

**T+1 周**：PMO 发布决策门结论书，明确下一阶段目标、预算、人员调整。

**Conditional Go 的处理**：若评审委员会认为"方向对但有 1-2 项硬指标未达标"，给出 4-8 周整改期，整改期满后复评；复评仍不达标，转 No-Go。

**No-Go 的处理**：不追责、不甩锅，按本路线既定的回退动作执行（B 轨暂停、资源回补、目标调整），下一个决策门重新评审。
