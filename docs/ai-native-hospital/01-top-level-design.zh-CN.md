## 1. 愿景与定位

**愿景**：让医疗 AI 更简单、更落地。把 jlmedaios 建成"医疗 AI 的安卓"——一个开源、免费、工业级、可被医院信息科与全球开发者共同装配和扩展的医院智能体操作系统，支撑**未来 15 年 AI 原生医院**。

**定位**：不是又一个单点 AI 助手，而是把**核心业务事务系统（HIS + EMR 一体化）**与 **AI 原生能力中台（Agent 编排 / 技能 / 知识 / CDS / RAG）**深度融合的一体化平台：

- 向下：统一临床数据、主数据与外部系统接入；
- 向中：以云原生微服务承载挂号、就诊、医嘱、处方、病历、收费、药事、检验检查、手术麻醉、病案等核心事务；
- 向上：以 AI 中台横切每个业务环节，提供 AI 病历、AI 质控、语音病历、诊断用药辅助、危急值闭环等刚需智能体；
- 全程：医师复核签名、权限可配、数据可追溯、合规内建。

**AI 边界（不可逾越）**：AI 始终定位为辅助与"第二阅片/第二意见"，**所有诊断结论、医嘱、处方、病历签名等具有法律效力的写操作，必须由具备权限的医务人员确认与电子签名**；系统不做自主诊疗。

## 2. 设计原则

1. **AI 原生（AI-Native）**：数据与流程从设计之初就为 Agent 消费、工具调用、上下文构建、人机协同而准备，而非事后外挂。
2. **事务与智能分离、契约解耦**：核心业务事务保证 ACID 与一致性；AI 推理为可失败、可重试、可降级的能力，二者通过标准 API/事件协作，AI 故障不阻断核心诊疗。
3. **标准开放、双轨建模**：FHIR 对外、可演进临床模型（向 openEHR 对齐）对内；HL7 v2、DICOM、SNOMED/LOINC/ICD 全支持。
4. **领域驱动、微服务化**：按限界上下文（Bounded Context）拆分，高内聚低耦合，服务可独立部署、独立伸缩。
5. **安全与合规内建（Secure by Design）**：等保 2.0 三级、最小权限、默认脱敏、全量审计、多租户隔离从第一天就位。
6. **渐进演进（Strangler）**：不推倒已验证资产，按领域绞杀者式替换，每步可运行、可回滚。
7. **高并发与高可用**：无状态服务 + 弹性伸缩 + 事件削峰 + 熔断限流，真实对应三甲一院多区高并发。
8. **可装配、可扩展**：低代码让医院信息科自行编排智能体、技能与页面，生态可贡献。

## 4. L2 核心业务事务层：HIS + EMR 一体化微服务划分

采用领域驱动设计，按限界上下文拆分为可独立部署的微服务。每个服务拥有自己的数据与领域逻辑，通过 API 网关与事件总线协作；**强一致事务在服务内完成，跨服务协作采用 Saga / 事件最终一致 + 补偿**。

| 微服务 | 核心职责 | 关键聚合/实体 | 对外事件（示例） |
|---|---|---|---|
| **门诊服务 Outpatient** | 挂号、分诊、候诊队列、门诊就诊、门诊诊断、门诊病历 | Patient(轻)、Visit、QueueTicket、Diagnosis | `visit.registered` `visit.started` `visit.completed` |
| **住院服务 Inpatient** | 入院/出院/转科(ADT)、床位、病区、查房、护理 | Admission、Bed、Ward、CarePlan | `patient.admitted` `patient.transferred` `patient.discharged` |
| **医嘱处方服务 Orders & Rx** | 医嘱全生命周期、处方开具/审核、执行、停止 | Order、Prescription、PrescriptionItem | `order.placed` `rx.submitted` `rx.approved` `order.cancelled` |
| **病历文书服务 Documentation** | 门诊/住院病历、各类文书、模板、签名、质控 | MedicalRecord、DocumentTemplate、Signature | `record.drafted` `record.signed` `record.quality-flagged` |
| **收费结算服务 Billing** | 门诊/住院收费、医保对接、DRG-DIP 结算、票据 | Invoice、ChargeItem、InsuranceClaim、Settlement | `charge.created` `claim.submitted` `settlement.completed` |
| **药事服务 Pharmacy** | 药品目录、库存、发药、调剂、用药监护 | DrugCatalog、Inventory、Dispense、DrugAudit | `drug.dispensed` `inventory.low` `interaction.warned` |
| **检验检查服务 Diagnostics** | 检验/检查申请、报告、危急值、影像调阅 | LabOrder、LabResult、ImagingOrder、ImagingReport | `result.available` `critical.value` |
| **手术麻醉服务 OR-Anesthesia** | 手术安排、麻醉评估/记录、术中记录 | SurgeryBooking、AnesthesiaRecord | `surgery.scheduled` `anesthesia.started` |
| **病案服务 MedicalRecords-Archive** | 病案首页、归档、编码(ICD/手术)、质控上报 | FrontPage、ArchivedCase、Coding | `case.archived` `coding.completed` |
| **排班与资源服务 Scheduling** | 号源、排班、床位/设备/手术间资源 | Schedule、Slot、Resource | `slot.opened` `appointment.booked` |

> 患者主索引（**EMPI**）与机构/人员/科室主数据由 L4 主数据 + L6 身份域统一治理，各服务通过标识引用、不重复维护。

**事务一致性策略**：
- 服务内：数据库本地事务（含处方 + 明细、医嘱批量等）；
- 跨服务：编排式 Saga（如"就诊完成→生成收费→发药→归档"），每步定义补偿动作；
- 关键医疗写操作采用**状态机 + 双签名**（如高风险处方：医师开具→药师审核→执行）。

## 5. L3 AI 原生能力中台（横切层）

AI 中台以**能力（Capability）+ 技能（Skill）+ 工具（Tool）**三层组织，经编排引擎嵌入业务流程，但不持有业务事务的最终决定权。

### 5.1 Agent 编排引擎
- 多 Agent 协作：单 Agent（任务型）、主管 Agent（Supervisor）路由、顺序/并行/主从协作、**MDT 多学科会诊**；
- 意图分类 → 路由策略 → 上下文构建 → ReAct（推理-工具-观察）循环 → 结果聚合；
- 人机协同节点（Human-in-the-loop）：高风险动作转人工任务（HumanTask），由有权人员审批/签名；
- 会话、消息、调用链全程落库（`agent.conversations / conversation_messages / agent_invocations / human_tasks`）。

### 5.2 技能（Skills）体系与市场
- 技能为可打包、可版本化、可热插拔的能力单元（提示词 + 工具集 + 知识引用 + 输入输出契约 + 风险等级）；
- 内置刚需技能包：**AI 病历生成、AI 病历质控、语音电子病历、智能分诊、诊断辅助、用药/审方辅助、危急值管理、检查检验解读、随访管理、DRG-DIP 编码辅助、患者教育**等；
- 低代码技能编辑器 + 技能市场：医院信息科可自建/导入/发布，支持院内私有与社区共享；
- 技能签名与分级：高风险技能强制人工确认与审计。

### 5.3 医疗知识中台
- 五级知识库：公共医学知识 → 院内制度/路径 → 科室知识 → 个人偏好 → 患者实例；
- RAG 五阶段流水线：查询理解 → 混合检索（关键词 + 向量）→ RRF 融合 → 重排序（权威性/时效性加权）→ 带引用的上下文构建；
- 向量存储 + 文档解析/分块 + 知识库版本管理；权威开放知识（药品说明书、指南、ICD/LOINC/SNOMED 映射）可持续导入。

### 5.4 临床决策支持（CDS）
- 规则引擎：条件树（AND/OR/NOT）+ 动作（提醒/拦截/建议/计算/填表）；
- 规则覆盖药物相互作用、检验危急值、诊疗规范、过敏/禁忌、剂量校验；
- 两种介入：**主动提醒**（非阻断）与**拦截确认**（高风险，需理由 + 签名，可在有权限时 override 并留痕）。

### 5.5 语音与影像 AI
- 语音电子病历：实时语音转写 + 医学术语校正 + 结构化填入病历；
- 影像 AI：以独立模型微服务承载（如已融合的 DAMO-RADAR 腹部 CT），BFF 经标准契约调用，结果作为"第二阅片"由医师复核签名。

> **AI 与事务系统协作铁律**：AI 产生的任何写入，先经 CDS/风控与权限校验，再以"待确认草稿/建议"进入业务服务；最终由医务人员电子签名才转为正式记录。AI 不可直接产生已生效医嘱/处方/诊断。

## 6. L4 数据平台架构

### 6.1 双轨临床模型
- **在线事务**：PostgreSQL 关系模型（现 5 schema 40 表）承载高并发事务；
- **高保真临床（演进方向）**：向 openEHR 原型/模板对齐，新增临床概念不改表结构；
- **对外交换**：统一映射为 FHIR R4/R5 资源；
- 三者经**映射/转换层**双向对应，保证"一次采集、多标准可用"。

### 6.2 医疗大数据湖仓
- **湖仓一体**：业务库 CDC → 数据湖（ODS/DWD/DWS/ADS 分层）→ 科研与分析；
- **主数据管理 MDM**：EMPI 患者主索引、机构/人员/科室、药品、诊疗项目、术语字典；
- **数据治理**：元数据、数据质量、血缘、标准编码、隐私分级（L1 公开/L2 内部/L3 敏感/L4 机密）；
- **科研专病库 & 随访**：队列构建、专病数据集、长期随访，支持临床研究与真实世界证据。

### 6.3 数据生命周期
- 写入即分级、默认脱敏用于展示与导出；
- 版本化/时间感知：电子病历所有修改保留版本与痕迹（可审计、可回溯）；
- 备份恢复：全量 + WAL 归档 + 定期恢复演练（见部署/运维文档）。

## 7. L5 集成与标准、事件驱动

- **标准接口**：FHIR（REST/订阅/批量）、openEHR REST + AQL、HL7 v2.x（ADT/ORM/ORU/MDM…）、DICOM（C-STORE/C-MOVE、DICOMWeb QIDO/WADO/STOW）；
- **适配器框架**：HIS/EMR/LIS/PACS 适配器统一具备重试、熔断、超时、字段映射、厂商适配（卫宁/东华/创业慧康等）；真实对接前以显式 Mock 运行并标注 `INTEGRATION_USE_MOCK`；
- **事件驱动**：以 Kafka（或可落地的消息中间件）替换现有内存总线，支持 Topic、分区、消费组、死信队列、延迟投递、幂等消费、Exactly/At-least-once 语义与事务消息；
- **集成监控**：健康探针、成功率、P95、告警与 Prometheus 导出。

## 8. 多租户与一院多区

- **多租户隔离**：集团/医院为租户，行级 + schema 级隔离策略可配，租户间数据逻辑/物理隔离；
- **一院多区**：院区（Campus）、病区、科室、设备/床位均带院区标识；号源、库存、排班、报表按院区独立、集团汇总；
- **数据范围（DataScope）**：self / dept / campus / hospital / group，配合 RBAC + ABAC 在每条查询与界面中生效；
- 配置、字典、技能、知识库支持"集团统一下发 + 院区差异化覆盖"。

---

## 9. 高并发与高可用

- **无状态化**：业务服务无状态、会话与状态外置（Redis/DB），支持水平弹性伸缩；
- **流量治理**：API 网关限流、熔断、降级；读多写少场景加缓存（Redis）；
- **事件削峰**：高峰（挂号、报告回传、危急值）经消息队列异步削峰；
- **连接池/数据库**：合理连接池、读写分离、分区与索引优化、慢查询治理；
- **韧性**：多副本、健康检查、自动故障转移、灰度/蓝绿发布、回滚；
- **容量目标**：按三甲一院多区（数千医护、日门诊上万、峰值并发数千）设计，落地前以真实压测验证（非仅理论）。

## 10. 安全与合规（Secure by Design）

| 域 | 设计 |
|---|---|
| 身份认证 | 统一身份、JWT 强签名验签、SSO；**MFA 多因素**（等保三级要求，UI 已预留，二期对接） |
| 授权 | **RBAC（角色）+ ABAC（属性/数据范围）**，权限可管理可配置，最小权限、职责分离（开方/审方分离） |
| 数据保护 | AES-256-GCM 静态加密、传输 TLS、**16 类敏感数据脱敏**、字段级权限 |
| 输入安全 | Prompt 注入多层防护（实测检测率 100%）、SQL/XSS/命令注入防护、参数化 |
| 审计 | **哈希链防篡改审计日志**、登录日志、异常行为检测、电子病历痕迹 |
| 合规检查 | 等保 2.0 三级控制域、电子病历分级评价、互联互通成熟度、数据出境/隐私 |
| 多租户 | 租户隔离、跨租户访问默认拒绝、租户级审计 |

## 11. 云原生部署架构

- **容器化**：所有服务构建为固定版本 tag 的 OCI 镜像（非 root、最小镜像、SBOM）；
- **编排**：Kubernetes（Deployment/StatefulSet、HPA、Pod 反亲和、PDB、NetworkPolicy）；PostgreSQL/消息/缓存用 StatefulSet 或托管服务；
- **服务网格/网关**：Ingress/API 网关做 TLS 终止、路由、限流；可选 Service Mesh（mTLS、流量治理、可观测）；
- **可观测性**：统一日志（自动脱敏）、指标（Prometheus）、链路追踪（OpenTelemetry/Jaeger）、告警；
- **环境与交付**：dev/test/prod 配置分离、GitOps、IaC、CI/CD（类型检查→单测/覆盖率→集成→安全扫描→构建→发布）；
- **三种部署形态**：单机演示（docker-compose）、医院私有云（K8s）、集团多院区（多集群/联邦）。

## 13. 质量与验收（每个里程碑的"完成"定义）

一个里程碑只有同时满足才算完成（**禁止用 mock/演示冒充真实系统**）：

1. 数据真落 PostgreSQL，关键写操作可查回、**重启不丢**（psql 证据）；
2. 真实 LLM 闭环：流式、工具调用（ReAct）、消息落库；连不上真库/LLM **明确报错**，演示仅在显式 `DEMO_MODE` 带水印；
3. 端到端正向 + 异常闭环：业务流程贯通，异常/越权/超时被正确处理；
4. 类型检查 0 错误、单元/集成测试全绿且覆盖率达标（≥85%）、关键场景 E2E 通过；
5. 权限/数据范围/多租户隔离经测试验证；安全扫描无高危；
6. 可部署（镜像/编排/文档齐全，"下载就能跑"）、可观测、可回滚；
7. 中英文档同步，许可证 SBOM 完整。

> 配套落地顺序与每阶段范围、验收与回滚，详见《Strangler 渐进重构路线图》。
