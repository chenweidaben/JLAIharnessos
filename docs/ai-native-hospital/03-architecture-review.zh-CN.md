## 1. 执行摘要

本次评审以 **6 个工程视角**（云原生与 CI/CD、数据中台、AI 中台、业务中台、安全合规、高并发一致性）对《00 开源调研》《01 顶层设计》《02 渐进路线图》进行**文档对照真实代码**的抽查。

**总体结论：架构方向正确、骨架真实、底线诚实，可按路线图继续推进。**

1. **方向被代码验证**：HIS+EMR 一体化、AI 中台横切、事务与智能分离、AI 仅辅助且医师签名、真实 PostgreSQL 落库、审计哈希链、限流熔断等**核心主张均有真实代码与测试支撑**，不是 PPT 架构。
2. **已闭环范围扎实**：M0 门诊、M1-A 住院 ADT、M1-B1 急诊、M1-B2 在院三站、M2-A 药房发药、M2-B 病历质控、M2-C 语音病历；后端 1428 测试全绿。
3. **主要风险集中在"工程化落地"而非"架构方向"**：最高优先级两项均在 CI/CD——**流水线分支过滤与实际默认分支（master）不匹配**、**CI 未启动真实数据库复现集成闭环**；其余为 openEHR 仅有愿景、MFA 未持久化/未强制、内存事件总线、统一幂等键与真实压测缺失等。
4. **未发现高危（阻断级）架构缺陷**；风险以"中"为主，2 项 CI 问题评为"高"（不影响本地正确性，但使团队级质量门失效）。

**本轮处置**：2 项高风险与多数中风险在文档层面立即修正（见第 5 节），代码层面的整改按修订后的路线图，从下一里程碑（M3 首切片）起逐项闭环。

## 2. 评审方法与范围

- **评审对象**：`00-open-source-research`、`01-top-level-design`、`02-strangler-roadmap`（中英文）。
- **方法**：每个视角由对应领域专家，先读文档主张，再**抽查真实代码与数据库取证**，逐条判断主张是否成立；问题给出风险等级、优先级与可执行建议。
- **抽查的关键事实（取证）**：
  - 真实数据库：5 schema 共 **61 张基表**（iam 7 / clinical 30 / agent 8 / knowledge 14 / audit 2），无视图。
  - 后端测试 **1428 pass / 0 fail（120 文件）**；前端 **509 测试**（满载下 5 例计时超时，隔离重跑通过，属抖动）。
  - 医疗工具 **38 个**、CDS 规则 **43 条**、FHIR 资源类型 **22 种**、HL7 消息 **16 种**、权威知识源 **26 个**。
  - 代码内 **openEHR/AQL/archetype 引用为 0**；事件总线为进程内内存实现。
- **风险等级**：高 / 中 / 低；**优先级**：P1（立即）/ P2（本里程碑内）/ P3（排期）。

## 3. 六视角发现

### 3.1 云原生微服务 / 可观测 / 弹性 / CI-CD

**现状评价**：BFF 统一 `/api/v1` 与中间件链（认证/限流/CSRF/安全头/租户/日志/错误信封），具备模块化单体→微服务的良好基础；`src/resilience` 五件套（RateLimiter/CircuitBreaker/Bulkhead/ConcurrencyLimiter/AsyncQueue）；BFF 内置 `/metrics`（Prometheus）；有 3 个 GitHub Actions 工作流。

**问题**：

| # | 问题 | 风险 | 优先级 |
|---|---|---|---|
| A1 | **CI 分支过滤与默认分支不匹配**：`ci.yml` 触发于 `main/develop`，实际默认分支为 `master`，推送 master 不触发流水线，团队级质量门形同虚设 | 高 | P1 |
| A2 | **CI 未复现真实 DB 闭环**：无 PostgreSQL service container，`integration-test` 无库可跑（被 `|| echo` 跳过）；本地 1428 只中大量 DB 集成测试在 CI 无法验证 | 高 | P1 |
| A3 | 可观测以自定义指标为主，traceId 已透传但无 OpenTelemetry/OTLP 导出，LLM/Agent 专项指标（首 token、token 成本、工具成功率）未统一 | 中 | P2 |
| A4 | 仍为单 BFF 进程（模块化单体），未拆分为可独立部署/伸缩的进程；K8s/HPA/网格仅在文档（符合当前阶段） | 中 | P3 |
| A5 | CI 固定 Bun 1.3.11，本地为 1.4.2，版本不一致 | 低 | P3 |

**建议**：修正 `ci.yml` 分支为 `master`（含 `master` 通配）；增加 PostgreSQL service container 与 `DATABASE_URL`，跑全量 `bun test` 与 web `vitest`，并加 web 覆盖率门禁；接入 OTel Collector 统一导出 traces/metrics/LLM 指标。

**依据**：`.github/workflows/ci.yml`（branches、无 services）、`src/bff/server.ts`、`src/bff/observability/metrics.ts`、`src/resilience/`。

### 3.2 数据中台（主数据 / 治理 / FHIR·openEHR / 湖仓 / 一院多区）

**现状评价**：真实 5 schema 61 表，统一 `repositories` 访问层；FHIR 有真实代码（Builder/Parser/Client/Resource，22 资源）；HL7（16 消息）、DICOM（DICOMWeb QIDO/WADO/STOW）有实现；租户中间件与 DataScope 已在请求链路生效。

**问题**：

| # | 问题 | 风险 | 优先级 |
|---|---|---|---|
| D1 | **openEHR 零代码**：文档将"FHIR 对外、openEHR 对内"作为双轨核心，但代码中无任何 openEHR/AQL/archetype 实现，6.1 表述易被读为已具备 | 中 | P2 |
| D2 | 文档表数量过时：写"5 schema 40 表"，实际 **61 表** | 低 | P2 |
| D3 | 未见独立 EMPI/主数据归并服务（患者主索引分散在 patientRepo，无跨标识匹配/合并） | 中 | P2 |
| D4 | 湖仓/CDC、元数据/血缘/数据质量为文档方向，未落地（规划在 M5） | 中 | P3 |

**建议**：在顶层设计明确标注 **openEHR 为 M5 演进方向、当前仅 FHIR 落地**；同步真实表数；EMPI 匹配/归并与湖仓纳入 M5，先做最小 EMPI 服务（标识登记 + 匹配 + 合并留痕）。

**依据**：`src/integration/protocols/fhir/`、`src/db/repositories/patientRepo.ts`、库表实测、openEHR 全文检索为 0。

### 3.3 医疗 AI 中台 / 智能体（模型网关 / 工具编排 / ReAct / 护栏 / 模型可插拔）

**现状评价**：模型可插拔（`LLM_PROVIDER` 工厂 + OpenAI 兼容 DeepSeekProvider；ASR 同样有 provider 抽象）；编排器为完整 DAG 引擎（29 文件，DSL/节点/运行时/人工/录制/触发器，12 类节点）；chatAggregator 真实流式 + ReAct 工具 + 消息落库；护栏含 Prompt 注入防护、CDS 拦截、权限码、风险分级、AI 仅出草稿 + 医师签名。

**问题**：

| # | 问题 | 风险 | 优先级 |
|---|---|---|---|
| I1 | 真实 LLM 闭环以 **ReAct 单轮工具调用**为主；多步/多工具链与 Supervisor/MDT 多智能体在引擎中具备，真实闭环待补 | 中 | P2 |
| I2 | 模型网关偏"工厂选择"，缺网关级**配额/成本计量、多 provider 自动故障转移、响应缓存、统一流式超时** | 中 | P2 |
| I3 | 护栏中"Prompt 注入检测 100%"为特定测试集，缺持续对抗集回归；AI 输出的结构化 schema 校验可加强 | 中 | P2 |
| I4 | 技能热插拔/市场（pack 目录）的"信息科发布→运行"真实闭环待 M4 | 中 | P3 |

**建议**：新增统一模型网关（token 计量/配额/故障转移/缓存/超时）；扩展多轮 ReAct 与多智能体真实闭环；对抗集纳入 CI 回归；AI 工具调用结果强制 schema 校验、越权工具直接拒绝。

**依据**：`src/core/agent/providers/`、`src/orchestrator/`、`src/bff/aggregators/chatAggregator.ts`、`src/security/input/`。

### 3.4 业务中台 HIS·EMR（核心业务流 / 临床安全 / 复用）

**现状评价**：七大切片已真实闭环，状态机 + 签名链一致；临床写操作本人签名、AI 仅辅助；路由侧统一 `guarded` + 权限码 + 统一错误信封。

**问题**：

| # | 问题 | 风险 | 优先级 |
|---|---|---|---|
| B1 | 已知观察项：**危急值通知重复堆叠**（缺幂等键）、**in_consult 仅存 zustand**（刷新队列回退，临床产物不丢）尚未全部闭环 | 中 | P2 |
| B2 | 收费/医保/病案、医技 LIS/PACS、手术麻醉、预约随访未闭环（规划在 M3+） | 中 | P3 |

**依据**：`02-strangler-roadmap §2.5.3`、`src/bff/routes/`、`src/bff/aggregators/`。

### 3.5 安全合规（等保 / 隐私 / 审计哈希链 / 权限 / 多租户 / 电子病历评级）

**现状评价**：审计哈希链真实（`audit.audit_logs` BEFORE INSERT 触发器维护 seq/prev_hash/hash，含锁与链状态迁移）；业务事务同事务写审计；JWT HS256 验签 + 时序安全比对；RBAC+ABAC+权限码+DataScope；16 类脱敏、AES-256-GCM；安全响应头、CSRF；MFA 有 TOTP self-service 实现。

**问题**：

| # | 问题 | 风险 | 优先级 |
|---|---|---|---|
| S1 | **MFA 未持久化/登录未强制**：默认 InMemory 存储，等保三级硬性要求未闭环（文档列 M6，建议提前） | 中 | P2 |
| S2 | 等保三级为"设计对齐"，未正式测评；国密 SM2/SM3/SM4 未实现（规划 M6） | 中 | P2 |
| S3 | 哈希链"链内防篡改"具备，但缺**链完整性巡检**与周期性锚定（外部公证） | 中 | P3 |
| S4 | 多租户隔离部分依赖应用层，需逐表核对 RLS 强制程度 | 中 | P2 |

**建议**：将 MFA 持久化（PgMfaStore）+ 登录强制**提前为独立安全切片**；增加哈希链完整性巡检与定时锚定；逐表核对并补齐 RLS，形成"RLS + DataScopeGuard 双保险"。

**依据**：`src/security/mfa/`、`deploy/postgres/init/50–52 audit*.sql`、`src/db/repositories/auditChainRepo.ts`、`src/bff/middleware/tenant.ts`。

### 3.6 高并发一致性（限流 / 熔断 / 重试 / 连接池 / 削峰 / 幂等 / 并发安全）

**现状评价**：resilience 五件套 + BFF 限流；连接池可配（`PG_POOL_MAX=20`）；SQL 大量 UNIQUE/ON CONFLICT，并存在 `FOR UPDATE`/`pg_advisory`/`LOCK TABLE`；状态机 + 唯一约束；审计链有专门锁迁移。

**问题**：

| # | 问题 | 风险 | 优先级 |
|---|---|---|---|
| C1 | 事件总线为**进程内内存**（AgentEventBus/alertBus/IntegrationBus），多实例水平扩展无法跨进程，削峰能力受限 | 高 | P2 |
| C2 | 缺统一**客户端幂等键（Idempotency-Key）框架**，跨超时/重试的安全重试不统一（单表有唯一约束，但无全局机制） | 中 | P2 |
| C3 | 重试在适配器有，缺统一退避与重试风暴防护（Bulkhead 已部分覆盖） | 中 | P3 |
| C4 | 容量目标（数千并发/日门诊上万）要求真实压测，k6 脚本存在但未见近期真实压测基线 | 中 | P2 |

**建议**：引入统一 Idempotency-Key 中间件 + 幂等记录表；按 M5 以 Kafka 替换内存总线（危急值等强责任事件须签收闭环）；用 k6 做真实压测并留存基线；统一指数退避 + 抖动。

**依据**：`src/core/events/`、`src/bff/alertBus.ts`、`src/integration/middleware/IntegrationBus.ts`、`src/db/pool.ts`、`deploy/postgres/init/`。

## 6. 对顶层设计与路线图的影响

1. **总体架构与六层视图不变**：评审验证了分层与"AI 中台横切、事务与智能分离"的正确性，无需重构。
2. **事实性修正**：表数 40→61；openEHR 明确为演进项；补充 FHIR 为当前唯一落地标准。
3. **路线图补强（不改变 M0→M6 主轴）**：
   - 把 **CI 与本地一致性（A1/A2）** 列为最先整改的工程前置；
   - 把 **MFA 持久化/强制** 从 M6 提前；
   - 明确 **Kafka 替换内存总线、统一幂等键、真实压测** 的工程节点；
   - M3 聚焦收费/医保/病案首页，且在收费/退费前先沉淀真实 Saga 样板。
4. **下一里程碑选择**：按里程碑顺序，M3 首切片取 **病案首页（v0.3.0-m3a）**——由已闭环临床数据自动汇聚、ICD/手术编码、归档状态机、医师复核签名，支撑电子病历分级与病案首页上报；收费/医保切片随后。

> **评审结论**：继续按既定路线图推进，但优先补齐 CI/CD 这一"团队级质量门"，并在每个里程碑坚持"真实落库、真实取证、医师签名、可回滚"的完成定义。
