# ADR-016 四套漂移 DDL 选型：独立新模型并存迁移 vs 对齐旧结构

> 架构决策记录（Architecture Decision Record）
> 健澜科技 · 健澜 AI 原生医院操作系统 OS

- 状态：`提案（待架构 / 用户拍板，拍板前不得改动既有表结构与已上线契约）`
- 日期：2026-11-24
- 决策者：核心架构组（待拍板）

## 背景（Context）

`deploy/postgres/init/` 中编号 256 / 349 / 350 / 369 的四套 DDL 定义了目标模型（新列、新表、新枚举、新视图、新规则码），但本地开发库 `jlmedaios@127.0.0.1:5433` 与线上生产代码仍停留在旧结构 / 旧表口径，形成模型漂移。本轮巡检只做**方案细化与代码侧预留标注**，在选型拍板前：

- 不 ALTER / DROP 既有表与列；
- 不改动已上线的 BFF / 前端契约；
- 不回填历史数据、不双写。

四套漂移相互独立，可分别拍板；本文先给出统一的两套候选方向，再逐套对照。

## 候选方案

### 方案 A：新模型落地、独立并存迁移（对齐顶层设计的先进架构方向）

**核心思路**：补齐新表 / 新列 / 新枚举落地，旧表 / 旧列作为过渡保留；聚合器经仓储层逐步切到新模型，过渡期双写或视图兼容；前端切新契约后再下线旧结构。

**统一步骤（四套通用）**：

1. **Schema 落地**：在新迁移脚本中补齐缺失列 / 表 / 索引 / 约束；旧结构不删，先做并列存在。
2. **仓储层适配**：为新模型补独立 repo（或扩展既有 repo），类型与视图层对齐新 DDL；旧 repo 暂留。
3. **读路径切换**：聚合器读优先新模型，新数据缺失时回退旧表 / 视图兜底。
4. **写路径双写 / 回填**：新写入同时落新模型；对存量数据按主题分批回填（256 随访、349 满意度历史问卷、350 规则码映射、369 历史快照）。
5. **前端契约切换**：前端视图层切到新字段，灰度验证后下线旧字段对外口径。
6. **下线旧结构**：确认无旧读路径后，再安排 DROP / 归档（另起 ADR，独立评审）。

**逐套工作量与影响面（粗估，待细化）**：

- **256 随访**：影响面最大。新旧 plans 列语义差异大（旧按预约号 / 预约日期，新按就诊 / 时间点 / 诊断），需新建新模型 repo、提醒扫描任务与回执闭环；存量旧计划是否迁移需定口径。建议新表 `follow_up_plan_v2` 并存而非同名替换，避免旧预约链路被打断。
- **349 满意度**：中等。深化列补齐后，需把旧 emotion_sentiment / key_issues 映射到新 emotion_label / five_why_chain；NPS 分类与 PDCA 阶段接规则函数；历史问卷的新列允许空值回填。
- **350 规则**：中等。需统一规则码体系：旧 9 码与新 STD/DQR/SEC/LC 码做映射或合并去重；规则引擎从 `dq_rules` 切到 `data_quality_rule`；`dq_runs` / `dq_results` 结果表是否随规则表一并迁移需评估。
- **369 运营**：较小。新列 / 视图 / 预测表已落地，缺的是 `ops_metric` 快照回写（mom / yoy / forecast / rank）与定时调度；补齐 ETL / 聚合回写后 `v_ops_trend` 即可出数。

**正面**：模型对齐顶层设计与 FHIR / 数据平台方向；新能力（AI 随访、NPS/PDCA 闭环、治理规则体系、运营趋势预测）有干净落点；旧链路可平滑过渡。
**负面 / 风险**：迁移周期长，过渡期双写一致性与回填正确性要求高；需额外的迁移脚本、回填校验与灰度回滚；256 同名表语义冲突需谨慎处理。
**折中债务**：过渡期内存在新旧两套口径，需在视图层明确主从，避免前端读到混合数据。

### 方案 B：对齐旧结构、废弃新模型 DDL

**核心思路**：撤回未落地的新列 / 新表 / 新规则码设计，代码与前端口径回退到既有旧列；新模型纯函数仅作演示 / 离线计算，不落库。

**统一步骤**：

1. **DDL 收口**：在迁移脚本中标记未落地的新列 / 新表 / 新枚举为废弃，或从 init SQL 移除（已落地的 349 枚举、369 新列 / 视图需评估是否保留为预留）。
2. **代码回退**：聚合器 / 仓储只保留旧列口径；新模型纯函数若不接库则降级为演示工具，不进入生产读路径。
3. **契约冻结**：前端与 BFF 维持现有字段，不再向新模型演进。

**逐套工作量与影响面（粗估）**：

- **256 随访**：工作量小。保留旧 plans / 记录链路；`followUpAggregator` 新模型不接库，仅演示。
- **349 满意度**：工作量小。旧深化列继续使用；新枚举 / 新列不落地，NPS / PDCA 能力暂不进生产。
- **350 规则**：工作量小。维持 `dq_rules` 旧 9 码；新规则体系不启用。
- **369 运营**：工作量小到中。保留旧 `ops_metric` 结构；已落地的新列 / 视图若不使用，需决定保留预留还是回退；`ops_forecast` 预测表已被 `opsForecast.ts` 写入，下线需先评估该路由。

**正面**：短期改动最小，不触碰存量数据与线上契约；风险低。
**负面 / 风险**：放弃顶层设计规划的新能力落点；旧结构长期承担演进压力，后续仍需重做；369 已有代码写入新表，回退需先摘路由。
**折中债务**：技术债累积，新模型与旧实现长期分叉。

## 逐套初步建议（供拍板参考，非最终决策）

| 编号 | 倾向方向 | 理由 |
| --- | --- | --- |
| 256 | 方案 A（新表并存） | 新旧 plans 语义差异大，同名替换风险高；AI 随访计划 / 提醒回执是规划能力，建议新表并存、旧预约链路过渡 |
| 349 | 方案 A（列补齐 + 旧列映射） | 深化列与旧列概念可映射，补齐后承接 NPS / PDCA 闭环；历史数据允许空值回填 |
| 350 | 待拍板（先定规则码主从） | 新旧规则码体系需先确定以哪套为准；在规则引擎主从定下来前，不贸然切表 |
| 369 | 方案 A（补齐回写调度） | 新列 / 视图 / 预测表已落地，缺的只是快照回写与调度，补齐成本低、收益直接 |

## 代码侧预留标注现状（不改契约）

- **已预留**：四套新模型的纯函数聚合器与类型（followUpAggregator、satisfactionDeepAggregator、dataGovernanceAggregator 类型对齐、opsAnalysisAggregator / opsDeepAggregator）；369 `opsForecast` 已落 `ops_forecast`；349 枚举、369 新列与视图已在库。
- **待补（拍板后实施）**：新模型仓储 repo；双写 / 回填脚本；350 新规则码 upsert 与规则引擎切换；369 `ops_metric` 快照回写与定时调度；前端新字段契约。

## 待拍板决策点

1. **256 随访**：新模型是新建 `follow_up_plan_v2` 并存，还是在旧 `follow_up_plans` 上扩列？存量旧计划是否迁移？
2. **349 满意度**：旧 emotion_sentiment / key_issues 是否映射迁移到新 emotion_label / five_why_chain？历史问卷新列如何回填？
3. **350 规则**：旧 9 码与新 STD/DQR/SEC/LC 码合并去重规则如何定？规则引擎与结果表以哪套为准？
4. **369 运营**：是否补齐 `ops_metric` 回写与调度，让 `v_ops_trend` 出数？已落地新列 / 视图是否保留？
5. **迁移窗口与灰度**：双写过渡期长度、回填批次、灰度范围与回滚策略。

## 约束与红线

- 拍板前：不 ALTER / DROP 既有表与列，不改已上线 BFF / 前端契约，不回填历史数据。
- 任何落地迁移需另起迁移脚本 + 回滚脚本，配套单测 / 集成测试与回填校验。
- 双仓（GitHub / GitCode）同步前完成类型门禁与相关回归。
