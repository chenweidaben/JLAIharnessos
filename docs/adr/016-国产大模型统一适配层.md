# ADR-016 国产大模型统一适配层（LLM Gateway）

- 状态：提案 ｜ 日期：2026-11-27 ｜ 决策者：核心架构组

## 背景

架构宪章要求"数据不出院、禁止境外大模型"，生产医疗推理统一走本地 vLLM。但实际存在两类诉求：

1. **多模型并存**：本地 vLLM（院内全自主）、豆包、DeepSeek 等国产模型各有适用场景——病历生成偏通用能力，处方审核偏规则与安全，需按场景择优。
2. **可插拔与降级**：单一模型故障、超时、合规升级时，需要无缝切换；当前若各业务直接对接各家 SDK，将导致厂商锁定、切换成本高、难以统一治理。

若不做统一抽象，`src/` 与 `services-python/` 各自散落多家 SDK 调用，安全策略（国密、脱敏、审计、超时熔断）无法集中落地。

## 决策

引入 **LLM Gateway 统一适配层**，收敛所有大模型调用：

- **统一契约**：所有调用走同一接口 `POST /llm/chat`（`{model, messages, temperature, max_tokens}` → `{reply, usage, model}`），业务层不直接对接厂商 SDK。
- **模型注册可插拔**：`local-vllm`（默认，院内）/ `doubao` / `deepseek` 通过注册表配置切换，适配层屏蔽差异。
- **安全策略内聚**：超时 8s、指数退避重试、熔断降级 mock、敏感字段脱敏、审计日志在 Gateway 统一实施。
- **合规硬约束**：白名单仅允许国产模型 + 本地 vLLM；境外模型（OpenAI/Claude/Gemini/Cohere）在 Gateway 层直接拒绝，fail-closed。
- **分流策略**：按 `riskLevel` 路由——high 风险场景（如处方审核）优先本地 vLLM + 规则引擎，通用生成场景可走豆包/DeepSeek。

## 后果

- 正面：厂商可插拔、安全合规集中治理、切换成本低；满足"数据不出院 + 禁止境外"硬约束。
- 负面：多一层调用与运维；模型间能力差异需在适配层做能力兜底与提示词适配。
- 折中：初期仅接入 local-vllm + 豆包两档，DeepSeek 预留注册位，按需启用。
