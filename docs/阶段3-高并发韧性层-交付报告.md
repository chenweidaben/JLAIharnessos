## 3. 真实压测数据（`bun run scripts/loadtest.ts` 实测）

环境：Windows / Bun 1.4.2，进程内模拟下游延迟 5~15ms。

### 阶段1 · 正常负载（80 并发 × 25 次 = 2000 请求，下游 2% 偶发失败）
- 成功 1965，韧性拒绝 0，下游真实失败 35
- **P50 = 27.6 ms，P95 = 32.6 ms，P99 = 34.1 ms**
- **吞吐 = 2807 req/s**，错误/拒绝率 1.8%，耗时 712ms
- 熔断状态保持 **closed**（符合预期）

### 阶段2 · 下游故障注入（下游 60% 失败）
- 成功仅 45，**韧性快速拒绝 1899**，下游真实失败仅 56
- 被熔断拒绝的请求 **P50 ≈ 0.0 ms**（fail-fast，不再消耗下游资源）
- 拒绝路径吞吐 **45244 req/s**，整体耗时骤降到 44ms
- 熔断状态 **open**，累计快速拒绝 1899 次
- 结论：下游异常时熔断有效保护下游连接池与协程，避免故障级联。

### 阶段3 · 有界队列削峰（一次性灌入 5000 条检验结果回推，worker=8，队列上限=500，drop-oldest）
- 成功消费 508，丢弃 4492
- 吞吐 **22500 req/s**，总耗时 222ms
- 结论：突发洪峰远大于处理能力时，有界队列 + drop-oldest 保护下游不被打穿；生产可对关键通知改用 `backpressure` 让生产者自我限流。

### 开发中修复的两个真实 BUG（已验证）
1. **ConcurrencyLimiter 重复计数**：`release()` 唤醒等待者时既手动 `acquired++`，等待者 `.then()` 又 `acquired++`，导致释放后 `acquired` 不归零。已移除 release 中的重复自增，由等待者统一占用。
2. **AsyncQueue reject 用例时序错误**：原用例 `await push(1)` 阻塞 50ms 后队列已被 worker 排空，导致"满"判断失真。改为手动 gate 控制首个任务长时间占用 worker，使队列真正达上限。

## 5. 与医院高并发场景的对应

| 医院高并发场景 | 本阶段技术对应 |
|---|---|
| 门诊高峰大量并发查询 | TieredRateLimiter 分级限流（查询接口令牌桶宽松放行）+ 舱壁隔离 |
| LIS/PACS 检验结果批量回推 | AsyncQueue 有界队列削峰（worker 限流 + 满策略背压） |
| 危急值多渠道扇出通知 | AsyncQueue（drop-oldest 保近实时）+ CircuitBreaker 防通知网关故障 |
| 多医生同时操作 / 外部 HIS 网关抖动 | CircuitBreaker 三态 fail-fast + 冷却后半开探测自动恢复 |
| 下游慢调用拖垮协程 | ConcurrencyLimiter / Bulkhead 限制在途并发，超时熔断 |
| 登录 / 改密等高危接口暴力尝试 | cache 层滑动窗口精确限流 + 登录失败锁定 |
