# 多租户与一院多区架构（jlmedaios）

> 杭州健澜科技有限公司 · 健澜科技数智医院智能体操作系统（jlmedaios）
> 阶段五：平台级多租户 / 一院多区数据隔离底座
>
> 初心：让医疗 AI 更简单更落地。

---

## 1. 设计目标

为支撑「一院多区」与「多医院 SaaS 平台」两类部署形态，平台必须具备：

1. **数据隔离默认开启**：任何业务数据行天然归属某医院租户；跨租户数据不可见。
2. **院区二级下钻**：一家医院可挂多个院区，院区数据在医院租户内部再按 campusId 隔离。
3. **上下文可解析**：一次请求内，BFF 能从请求头 / JWT 自动解析出当前 `(tenantId, campusId)`。
4. **可管理、可配置**：管理员可在管理后台增删租户/院区、启停、配置租户级参数；默认租户受保护。
5. **与既有体系解耦**：不另起权限体系（复用 `RoleCode`），不破坏既有知识库四级空间、技能覆盖、权限 overlay。

## 2. 与既有「租户」概念的边界

| 概念 | 位置 | 管什么 |
| --- | --- | --- |
| **本模块（平台级租户/院区）** | `src/tenant/` | 「哪个医院、哪个院区」+ 数据行隔离谓词 |
| 知识库四级空间 | `src/knowledge-platform/tenant/TenantManager.ts` | 知识空间可见性（public/hospital/department/personal） |
| 技能租户覆盖 | `src/skills/registry.ts` | 某租户是否启用某技能（`tenantOverrides`） |
| 权限 overlay | `src/security/auth/PermissionConfigStore.ts` | 某角色×模块×操作的覆盖 |

本模块只负责「平台级租户上下文与数据隔离底座」，上述三者各自独立，通过 `tenantId` 字符串对齐衔接。

## 3. 租户模型

```
hospital（医院租户，level=hospital，parentId 为空）
 ├─ campus（院区，level=campus，parentId → hospital）
 ├─ campus
 └─ ...
```

- **Tenant 节点字段**：`id / name / level / parentId / enabled / config / createdAt / updatedAt / deletedAt`。
- **软删除**：`deletedAt` 非空即删除，同时强制 `enabled=false`；删除医院级联软删其下院区。
- **默认保护**：`DEFAULT_TENANT_ID` 指向的默认医院不可停用、不可删除，防止锁死系统。
- **租户级 config**：键值对，用于功能开关、院区别名、业务参数；**禁止存放密钥**（密钥仍走 `process.env` / KMS）。

内置默认租户（来自 `.env`）：

```
MULTI_TENANT_ENABLED=true
DEFAULT_TENANT_ID=demo-hospital
DEFAULT_CAMPUS_ID=main-campus
```

启动即播种「默认医院 + 默认主院区」，开箱可用。

## 4. 运行时上下文 TenantContext

一次请求解析出的上下文：

```ts
interface TenantContext {
  tenantId: string;        // 当前医院租户
  campusId?: string;       // 当前院区（未指定=全院区视图）
  hospitalId: string;      // 恒等于 tenantId（冗余便于语义）
  enabled: boolean;
  config: Record<string, unknown>;
}
```

**解析来源（优先级）**：

1. HTTP 头 `X-Tenant-Id` / `X-Campus-Id`（网关/前端显式指定）；
2. 预留 JWT 中的 `tenant` / `campus` 声明（用户中心下发）；
3. 均未提供 → 回退默认租户。

**行为**：

- `MULTI_TENANT_ENABLED=false`：无论请求头如何，强制回退默认租户（单院部署模式，对业务透明）。
- 启用时：
  - 未知 / 停用 / 已删除租户 → 抛 `MedicalAgentError`（中间件转 **403**）；
  - 指定院区时校验其 `parentId === tenantId`，跨院区越权 → 拒绝。

## 5. 数据隔离策略（DataScopeGuard）

医疗多租户数据隔离红线：

- 所有租户业务数据行**必须携带 `tenantId`**；查询/过滤时**无条件叠加** `tenantId` 谓词。
- 院区场景再叠加 `campusId` 谓词（**仅当上下文指定了院区**）。
- **fail-closed**：行无 `tenantId` 标记一律不可见；指定院区后，无 `campusId` 标记的数据也不泄露。
- 未指定院区 = 院级管理员/集团视图，可见该院租户下全部院区。

生成的谓词可直接用于 SQL `WHERE` / ORM where / 内存过滤：

```ts
dataScopeGuard.buildPredicate(ctx)
// → { tenantId: 'demo-hospital', campusId: 'main-campus' }
```

## 6. BFF 接线

- 中间件 `src/bff/middleware/tenant.ts`：`tenantContextMiddleware(ctx)` 在鉴权之后解析上下文，经 **WeakMap** 挂到 `Ctx`（零侵入，不改既有 `Ctx` 结构）；失败返回 403。
- 管理路由 `src/bff/routes/admin/tenants.ts`：全部 `requireRole('admin')`，Zod 严格校验。

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/v1/admin/tenants/tree` | 租户/院区树 |
| POST | `/api/v1/admin/tenants` | 创建医院或院区 |
| PUT | `/api/v1/admin/tenants/:id/status` | 启停 |
| PUT | `/api/v1/admin/tenants/:id/config` | 浅合并租户级配置 |
| DELETE | `/api/v1/admin/tenants/:id` | 软删除（级联院区） |

> 本阶段不自行改 `server.ts` 注册，由装配方在鉴权后统一接线。

## 7. 与技能 / 权限 overlay 的衔接建议

- **技能覆盖**：`skills/registry.ts` 已有 `tenantId` 维度的 `TenantOverride`。后续可在技能加载处注入本模块解析出的 `ctx.tenantId`，实现「某医院启用/禁用某技能」。
- **权限 overlay**：`PermissionConfigStore` 当前按 `module:action` 做覆盖。后续可扩展为按 `(tenantId, module, action)` 三元键覆盖，实现「某医院独立的权限矩阵」。
- **数据权限到科室/病区**：本模块目前到「院区」一层；科室/病区维度的数据权限由 `DataScopeGuard` 谓词在上层继续叠加 `deptId`（复用 `security/types` 的 `DataScope`）。

## 8. 部署形态

- **单院单院区**：`MULTI_TENANT_ENABLED=false`，永远走默认租户，零成本。
- **单院多院区**：`MULTI_TENANT_ENABLED=true`，默认医院下挂多个院区，前端/网关按 `X-Campus-Id` 切换。
- **多医院 SaaS**：每家医院一个 hospital 节点，数据经 `tenantId` 谓词物理/逻辑隔离；管理后台独立增删租户。
