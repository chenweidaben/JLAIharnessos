## 一、执行摘要

### 1.1 研究目的与范围

围绕健澜AI原生医院操作系统OS 的电子病历模块，本轮完成三条线的穷尽对标：

1. **法规与分级评价线**：穷尽病历全生命周期（创建、修改、签名、审核、锁定、归档、借阅复印、复制、封存、保存期限、销毁、互联网诊疗与远程医疗专项）的现行法律、部门规章、规范性文件与卫生信息标准；按电子病历系统应用水平 5 级（目标等级）、医院信息互联互通四级甲等、医院智慧服务 3 级、医院智慧管理 2 级分别映射 EMR 必备能力。
2. **标准与开源实践线**：梳理 FHIR R4、CDA R2 / WS/T 500、ICD-10/ICD-11、ICD-9-CM-3、LOINC、SNOMED CT 在病历系统中的落点；逐个核实 7 个主流开源 EMR/HIS 项目的真实仓库、License、技术栈、病历核心模块、标准支持度、借鉴点与局限，形成可落地的借鉴矩阵。
3. **本地现状取证线**：在仓库内只读静态扫描与逐文件复核，按 29 个病历流程域给出"现状证据（路径:行号 / 路由 / 页面目录 / SQL 文件）—已有能力（真实落地 / 内存 mock / 仅接口定义 / 未取证）—缺口—对应法规条款—优先级"差距矩阵，并对齐 `docs/COMPLIANCE_BLUEPRINT.md` 六条生产化缺口。

### 1.2 总体判断

**功能骨架已成规模，但合规闭环集中在 P0 层尚未接通，标准互通与高级别评级能力处于规划或接口定义阶段。**

- 本地已具备较完整的病历领域表结构、状态机与部分哈希链参照：病案首页评审链、模板评审链、检验/影像解读行锁与状态白名单、互联网处方事务与药师审核 CAS、归档/封存状态守卫、75 个业务域聚合器已接入审计哈希链。
- 六条生产化缺口（蓝图 P0）在代码取证中**均未闭环**：生产口令核验未接线、病历正文签名/归档后仍可被仓储层覆盖且无版本历史表、27 个核心病历写路径未入审计链、临床表无数据库层 RLS、JWT 单钥无轮换过渡、导出/打印/共享出口无统一逐字段脱敏拦截层。
- 标准互通现状：FHIR 资源模型与网关路由骨架存在，但无持久化、无 `$history` 落库、无 HL7 v2↔FHIR 双向转换；CDA R2 文档表与转换服务零命中；独立术语主数据服务（ICD-10 全量码表、ICD-9-CM-3、LOINC、SNOMED CT、药品/科室字典）未建库。
- 评级定位：以电子病历 5 级（统一数据管理 + 中级医疗决策支持）为目标，当前主要差距在统一数据管理机制（CDR / EMPI / 统一数据模型）、全院知识库、结构化智能化书写覆盖与决策支持留痕；6 级所需的全流程闭环管理尚不在本轮现状范围内。

## 二、研究方法、基线与环境限制

### 2.1 取证方法

- **法规线**：通过国家卫生健康委官网原文页面、规范附件 docx/PDF、全国标准信息公共服务平台（std.samr.gov.cn）、国家法律法规数据库（flk.npc.gov.cn）定向精读；文号、发布/施行日期、效力状态、条款号与来源 URL 逐条登记；查不到文号或日期的条目标注"文号待核 / 日期待核"，未作编造。
- **开源线**：web.fetch 读取各开源仓库主页、README、LICENSE/协议原文、`composer.json`/构建清单与官方 Wiki；License 判断以协议原文为准；未检索到真实可访问仓库的候选（NHN Cloud Healthcare、DHCare、HisTool、SparkEDR 等）不收录正文矩阵，仅在附件 B 4.1 节记录检索过程与排除原因。
- **本地线**：仅使用只读操作（Read 逐文件复核、Grep / Select-String 静态检索、PowerShell 只读计数）；扫描排除 `node_modules`、`pgsql`、`pgdata`、`dist`、`coverage`、`.venv`；能力分四档：**真实落地**（路由→聚合器→仓储→PostgreSQL 表接通，状态机/事务/行锁在源码可见）、**内存 mock**（守卫存在但处理逻辑为纯函数 + 内存种子/Map/数组，不连库）、**仅接口定义**（路由或表存在但运行时未实现/未接线）、**未取证**（静态扫描范围内未找到，不等于生产环境绝对不存在）。

### 2.2 基线文档（只读复核）

- `docs/COMPLIANCE_BLUEPRINT.md`（M247 研发基线）：六条生产化缺口；蓝图自评 append-only 70%、PHI 85%、审计 90%、多租户 65%、JWT 95%、DEMO 80%（开发态），并自述 DB 层 append-only 触发器、WORM、RLS 全量、密钥轮换、真实流量逐字段脱敏拦截等待补。

### 5.4 六项 P0 缺口结论（深描见附件 C 第三节）

1. **P0-① 关闭 DEMO_MODE，接通真实 RBAC 与口令核验**：临床登录路径不做口令哈希比对（`routes/auth.ts:183` 放行注释；`userRepo.ts:17` SELECT_COLS 不含 `password_hash`；`HashUtils.ts:248/271` 核验函数无业务调用）；admin 角色恒绕过权限码（`middleware/auth.ts:318`）；无科室/病区/患者/就诊行级归属授权；多数临床主路由仅 `auth:true` 无独立权限码。
2. **P0-② 病历正文 append-only 写入层拦截 + 版本链**：`medicalRecordRepo.updateMedicalRecordContent:87-100` 无状态条件覆盖正文、旧正文不落历史表；入院记录/病案首页/出院小结 upsert 覆盖无状态守卫；无版本历史表、无 `prev_hash/content_hash`；签名为账号文本，无 CA 证书与 TSA 时间戳。
3. **P0-③ 审计 WORM / 哈希链覆盖病历写路径**：27 个核心病历写路径聚合器 `recordChainAudit` 调用计数为 0（清单见附件 C P0-③）；主操作日志表 `audit.operation_log` 无链；WORM 只增不改未在数据库角色/触发器层强制；审计 fire-and-forget；原始 URL 查询串未脱敏；不记响应状态码。
4. **P0-④ 多租户 RLS + 越权测试**：仅 5 张表有 `hospital_id`；RLS/POLICY/ROLE 全局实测为零；临床聚合器/仓储未接入 `withTenantScope`/`DataScopeGuard`；无跨租户临床病历越权集成测试。
5. **P0-⑤ 密钥轮换 + refresh token**：refresh token 轮换已落地（`auth.ts:246-287`）；但 JWT 单 HS256 单钥，无密钥版本号/双密钥过渡/历史归档；`251-webhooks.sql:66` webhook secret 明文落库。
6. **P0-⑥ 导出 / 批量接口逐字段脱敏拦截**：V14 导出/脱敏/字段授权全部内存纯函数；无统一出口拦截层；两套脱敏实现并存口径不一；病历正文/地址/邮箱/医保卡号/紧急联系人/签名图像未纳入；病历表头与复印申请表 PHI 明文落库。

### 7.1 P0 阶段：合规闭环（六条任务卡）

#### P0-1 生产身份核验与 RBAC 收口

- **目标**：生产环境无 DEMO_MODE 登录路径；口令哈希核验真实接线；权限码覆盖全部临床写接口；补齐科室/病区/患者/就诊行级归属授权；admin 不再临床业务豁免。
- **规范依据**：《网络安全法》第二十一条；GB/T 22239—2019 身份鉴别、访问控制（条款号待附件 A 附录 A11 闭环）；8号文 第九条、第十五条；1079 号标准权限管理要求。
- **切入点**：`src/bff/routes/auth.ts` 登录处理器接通 `userRepo` 口令哈希列与 `HashUtils` 核验函数，失败计入会话台账，移除放行注释分支；`src/db/repositories/userRepo.ts` 扩展 SELECT_COLS 与口令更新方法，明确 bcrypt/argon2 迁移策略；`src/bff/middleware/auth.ts` 拆分登录身份与权限码两层守卫，取消 admin 恒通过；新增数据归属守卫方向，与 `src/tenant/DataScopeGuard.ts`、`tenantAggregator.withTenantScope` 接线；临床主路由按域补齐 `requirePermissionCode` 挂码。
- **验收口径**：生产环境无 DEMO 启动路径；未认证一律 401；口令错误计入失败台账并限流；非授权角色/科室访问病历返回 403 并留痕；单元/集成测试覆盖口令错误/锁定/过期会话、admin 不可绕过临床权限码、跨科室与跨患者越权拒绝；临床写接口权限码矩阵与前端菜单一致。
- **前置依赖**：用户口令哈希迁移方案（存量用户重置或平滑升级）；角色-权限-科室-患者归属模型设计评审。

#### P0-2 病历正文 append-only 写入层拦截 + 版本链

- **目标**：草稿期修改产生新版本快照；提交/签名/归档后仓储层 UPDATE/DELETE 正文被拒绝；历史版本可按时间正序还原、前后内容可比对；每条快照带 prev_hash/content_hash 可跑链校验；签名记录绑定正文哈希与签署人证书（CA 接入前先留接口）。
- **规范依据**：11号文 第七条、第三十三条；8号文 第十四条、第十六条、第十七条；《电子签名法》第十三至十五条（专项映射待补）；1079 号标准修改留痕与版本可追溯要求。
- **切入点**：`src/db/repositories/` 各病历仓储在状态机迁移方法补 FROM/WHERE 源状态白名单；新增版本快照表方向（正文内容、prev_hash、content_hash、作者、时间、来源接口），快照与状态迁移同事务提交；`deploy/postgres/init/` 新增迁移：正文表追加 content_hash/prev_hash 列、版本历史表、BEFORE UPDATE/DELETE 触发器拦截已签名/归档文书正文改写；`src/bff/aggregators/` 病历写路径事务内完成状态校验→快照落表→审计链登记（接 P0-3）→返回版本号；电子签名模块扩展证书字段方向；复核 `orderRepo.updateOrderStatus` 等无守卫方法纳入白名单改造。
- **验收口径**：签名后改写被触发器或守卫拒绝；并发提交版本冲突返回 409；版本链篡改可检出；历史版本只读可比对；集成测试覆盖签名后改写拒绝、并发冲突、链篡改检出、医嘱非法状态迁移拒绝。
- **前置依赖**：病历文档状态机统一设计（草稿→待审核→已审核→归档→解锁审批→修改→重新归档）；版本快照表结构与哈希算法选型（SM3/SHA-256）评审。

#### P0-3 审计 WORM / 哈希链覆盖病历写路径

- **目标**：病历全量写动作（创建/提交/审核/签名/退回/归档/封存/借阅/复印/注销）100% 入链；链校验工具可检出任意单条篡改；数据库层应用角色无审计表 UPDATE/DELETE 权限；审计写入失败不允许静默通过；日志留存满足 ≥6 个月（医疗场景按病历保管年限归档）。
- **规范依据**：《网络安全法》第二十一条（日志留存不少于六个月）；GB/T 22239—2019 安全审计；31号文 查阅/复制/修改留痕；29号文 第二十二条（日志杜绝篡改、删除）。
- **切入点**：`src/bff/aggregators/` 27 个未入链病历写路径（附件 C P0-③ 清单）在状态迁移与快照写入同事务内调用 `recordChainAudit`；`deploy/postgres/init/` 为 `audit.operation_log` 补链列与触发器；应用角色 + 数据库角色分层落地 UPDATE/DELETE 权限回收（WORM）；`data_access_log`、`security_audit_log`、`consult.audit_trail` 补齐链/触发器/不可变约束；`src/bff/middleware/audit.ts` 补响应状态码、URL 查询串脱敏、写库失败重试与告警；新增周期 `verify_chain()` 工具与断裂告警；导出审计记录附链校验结果。
- **验收口径**：写动作入链率 100%；DB 层应用角色审计表只读；审计记录含操作者、角色、动作、资源类型/ID、患者引用、结果、客户端 IP、UA、时间戳、trace_id；链路断裂告警可演示；审计写入失败重试与告警覆盖。
- **前置依赖**：P0-2 版本快照表结构定稿；审计动作类型字典与资源类型字典统一；WORM 数据库角色模型设计评审。

#### P0-4 多租户 RLS + 越权测试

- **目标**：临床表在数据库层启用 RLS；不带租户上下文的查询返回空或被拒绝；绕过 BFF 直连数据库按租户隔离仍生效；跨租户读取/写入/导出越权用例全部拒绝；集团/医共体跨院共享走显式授权与审计留痕，不默认放行。
- **规范依据**：GB/T 22239—2019 边界防护与记录级隔离；《个人信息保护法》访问控制与最小必要；互联互通区域协同方向。
- **切入点**：`deploy/postgres/init/` 补齐临床文书表 `hospital_id` 列与外键；按表启用 RLS 与 POLICY（策略方向 `hospital_id = current_setting('app.hospital_id')`）；建立应用数据库角色与默认拒绝模型；`src/db/repositories/` 查询方法接入租户谓词并与 `DataScopeGuard.buildPredicate` 对齐，上下文缺失 fail-closed；`src/bff/aggregators/` 临床聚合器统一调用 `withTenantScope`；`validateTenantAccess` 用于跨院/跨科室访问审批留痕；`tests/integration/` 新增跨租户越权用例（A 院医生读取 B 院患者病历/医嘱/报告被拒），覆盖创建、查询、导出、汇总报表四条路径。
- **验收口径**：RLS 在 DB 层生效；直连数据库绕过 BFF 仍隔离；缺失/伪造租户标识返回 403；跨租户集成测试全绿；跨院共享有显式授权记录与审计链登记。
- **前置依赖**：租户模型与医院/科室/病区主数据对齐；现有五张表 `hospital_id` 存量数据回填方案。

#### P0-5 密钥轮换与 refresh token 闭环

- **目标**：密钥轮换期间新旧密钥签发/校验均通过；旧密钥到期自动停用；轮换动作入审计链；refresh token 重放（旧 jti 复用）被拒绝；登出后会话与 token 立即失效；webhook secret 不以明文落库。
- **规范依据**：《密码法》第二十七条；GB/T 22239—2019 密码管理；《网络安全法》第二十一条身份鉴别凭证安全管理。
- **切入点**：`src/bff/config/runtimeEnv.ts` 与 `middleware/auth.ts` 引入密钥版本号与密钥集（当前/上一版本并行校验方向），支持轮换过渡窗口；`src/db/repositories/` 会话台账补齐设备/客户端/登出状态查询与批量吊销，refresh token 单次使用约束校验；`deploy/postgres/init/251-webhooks.sql` webhook secret 改哈希/加密存储；API key 表补充轮换时间戳与上次使用时间；运维侧密钥轮换预案、轮换审计留痕、泄露应急吊销流程（部署脚本改动不在本轮范围，仅列方向）。
- **验收口径**：双密钥过渡窗口内新旧兼容；旧密钥到期自动停用；旧 refresh jti 复用拒绝；登出即时失效；webhook secret 加密落库；轮换动作入链可追溯。

- **验收口径**：四类出口全量拦截；非授权角色明文 PHI 不可见；嵌套对象、数组、病历正文、地址/邮箱/医保卡号/紧急联系人场景测试覆盖；字段规则配置化可审计；导出记录字段范围、操作者、时间、用途留痕。
- **前置依赖**：角色-字段-场景脱敏规则矩阵评审；存量明文 PHI 数据迁移与回填方案；P0-3 审计链先于导出入链接通。
