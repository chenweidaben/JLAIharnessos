## 3. 模块间接口与依赖

### 3.1 核心依赖关系

```
核心类型定义（src/types）
    ↑ 被所有模块依赖
    │
    ├── 工具框架（src/core/tools）← 医疗工具（src/medical-tools）
    ├── 安全模块（src/security）← 工具框架（审计、权限）
    ├── 集成模块（src/integration）← 医疗工具（外部系统调用）
    └── UI模块（src/ui）← Agent引擎（状态展示）
```

### 3.2 接口契约

各模块间通过明确定义的TypeScript接口通信：

| 接口 | 提供方 | 使用方 | 定义位置 |
|------|--------|--------|---------|
| MedicalToolDefinition | 工具框架 | 医疗工具 | src/types/tools.ts |
| MedicalToolContext | 工具框架 | 医疗工具 | src/types/tools.ts |
| AuditLogger | 安全模块 | 工具框架、医疗工具 | src/security/audit |
| PermissionChecker | 安全模块 | 工具框架 | src/security/auth |
| DesensitizationEngine | 安全模块 | 医疗工具、集成模块 | src/security/desensitization |
| HISAdapter | 集成模块 | 医疗工具 | src/integration/adapters/his |
| Patient / Encounter / etc. | 核心类型 | 所有模块 | src/types/medical.ts |

### 3.3 集成点

1. **工具框架 ↔ 安全模块**：工具执行前调用PermissionChecker，执行后调用AuditLogger
2. **医疗工具 ↔ 集成模块**：医疗工具通过适配器访问HIS/LIS/PACS
3. **医疗工具 ↔ 安全模块**：输出数据经过DesensitizationEngine脱敏
4. **UI ↔ Agent引擎**：通过AgentEvent事件总线通信
5. **所有模块 ↔ 核心类型**：共享类型定义

## 4. 代码合并与集成流程

### 4.1 Git工作流

```
feature分支开发 → 本地测试通过 → Pull Request → 代码审查 → CI通过 → 合并到develop
                                                                          ↓
                                                                    集成测试通过
                                                                          ↓
                                                                    合并到main（发布）
```

### 4.2 分支命名规范

- `feature/core/tool-framework` - 核心功能
- `feature/medical/patient-tools` - 医疗工具
- `feature/ui/theme` - UI功能
- `feature/security/audit` - 安全功能
- `fix/tool-execution-bug` - Bug修复
- `refactor/core/types` - 重构

### 4.3 代码审查清单

PR合并前必须检查：

- [ ] 功能正确性：代码实现符合需求和设计
- [ ] 代码规范：符合开发规范，命名正确，注释完整
- [ ] 类型安全：TypeScript严格模式通过，无any
- [ ] 安全性：敏感数据脱敏，权限检查，注入防护
- [ ] 测试覆盖：单元测试覆盖核心逻辑，测试通过
- [ ] 文档：关键函数有JSDoc，复杂逻辑有注释
- [ ] 性能：无明显性能问题，大数据量有优化
- [ ] 兼容性：不破坏已有接口，向后兼容

### 4.4 CI/CD流水线

```
提交代码
    ↓
1. 代码静态检查（eslint）
2. 类型检查（tsc --noEmit）
3. 单元测试（bun test）
4. 测试覆盖率检查（核心≥80%，工具≥90%）
5. 安全扫描（依赖漏洞、密钥检测）
6. 构建验证（bun build）
    ↓
全部通过 → 可合并
```

## 5. 测试策略

### 5.1 测试金字塔

```
        /端到端测试\        （医疗场景验收，10%）
       /  集成测试   \       （模块间集成，20%）
      /   单元测试    \      （函数/类级别，70%）
```

### 5.2 测试要求

| 模块 | 单元测试覆盖率 | 集成测试 | 特殊要求 |
|------|-------------|---------|---------|
| 核心引擎 | ≥80% | 必须 | Agent循环端到端测试 |
| 医疗工具 | ≥90% | 必须 | Mock数据测试，边界条件 |
| 安全模块 | ≥95% | 必须 | 渗透测试，脱敏验证 |
| 集成模块 | ≥80% | 必须 | 契约测试，Mock适配器 |
| UI组件 | ≥70% | 推荐 | 组件渲染测试 |

### 5.3 医疗场景验收测试用例

1. **门诊问诊全流程**：患者查询→问诊→病历生成→开医嘱→开检验→确认提交
2. **危急值处理**：检验危急值→警报通知→医生确认→处理记录
3. **医嘱开具审核**：开医嘱→药物相互作用检查→权限确认→CA签名→提交HIS
4. **病历质控**：病历生成→质控检查→缺陷识别→整改建议→重新提交
5. **多科室会诊**：主代理→科室子代理→多学科意见→会诊结论

## 6. 项目管理规范

### 6.1 每日站会

- 时间：每个工作日上午
- 内容：昨天完成、今天计划、遇到的阻塞
- 时长：≤15分钟

### 6.2 迭代周期

- Sprint周期：2周
- Sprint计划：确定Sprint目标和任务
- Sprint评审：演示完成的功能
- Sprint回顾：总结经验教训

### 6.3 缺陷管理

| 严重级别 | 定义 | 修复时限 |
|---------|------|---------|
| P0 致命 | 系统崩溃、数据丢失、安全漏洞 | 24小时内 |
| P1 严重 | 核心功能不可用、医疗错误风险 | 3天内 |
| P2 一般 | 功能缺陷、有替代方案 | 1个Sprint内 |
| P3 轻微 | UI问题、优化建议 | 排期修复 |

### 6.4 配置管理

- 所有配置文件纳入版本控制
- 敏感配置（密钥、密码）使用环境变量，不提交到代码库
- 配置按环境区分（dev/staging/prod）
- 配置变更需要代码审查

## 7. 风险管理

| 风险 | 概率 | 影响 | 应对措施 |
|------|------|------|---------|
| 原始代码source map还原质量问题 | 中 | 高 | 已完成审计，核心模块完整；遇到问题用stub替代 |
| 医疗工具需求变更 | 高 | 中 | 模块化设计，工具可独立迭代；与临床专家持续确认 |
| HIS系统接口差异大 | 高 | 中 | 适配器模式+配置化字段映射；先支持主流厂商 |
| 医疗数据安全合规 | 中 | 高 | 安全内建架构，等保三级设计，第三方安全测评 |
| LLM幻觉导致医疗错误 | 中 | 高 | RAG证据追溯、人工确认机制、高风险操作双重审核 |
| 团队对TypeScript/Ink不熟悉 | 中 | 中 | 开发规范+代码审查+培训，核心模块由资深开发负责 |
