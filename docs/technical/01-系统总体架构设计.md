## 1. 架构概述

### 1.1 设计目标

健澜科技数智医院智能体的架构设计围绕以下核心目标展开：



| 目标维度       | 具体要求                                     |
| ---------- | ---------------------------------------- |
| **医疗级可靠性** | 系统可用性≥99.9%，关键操作零数据丢失，故障自动恢复             |
| **安全合规**   | 等保三级合规，《个人信息保护法》《数据安全法》合规，医疗数据不出境        |
| **可扩展性**   | 支持横向扩展，新医院接入周期≤2 周，新工具开发≤3 人天            |
| **高性能**    | Agent 首响应≤3 秒，工具调用 P95≤2 秒，支持 500 + 并发会话 |
| **可维护性**   | 模块化设计，代码复用率≥70%，完整的测试与监控体系               |
| **集成能力**   | 无缝对接 HIS/EMR/LIS/PACS/ 医保等 10 + 类医院信息系统  |

### 1.2 设计原则



1. **复用优先**：最大化复用 claude-code 2.1.88 经过验证的核心引擎架构，避免重复造轮子

2. **关注点分离**：表现层、编排层、Agent 层、工具层、服务层、基础设施层严格分层

3. **接口驱动**：模块间通过明确定义的接口通信，支持独立开发、测试和替换

4. **安全内建**：安全机制嵌入架构各层，而非事后补丁

5. **配置化适配**：不同医院的系统差异通过配置化适配器解决，而非代码分支

6. **可观测性**：全链路监控、日志、追踪，支持问题快速定位

### 1.3 架构演进路线

本项目基于 claude-code 2.1.88 源代码（source map 还原版，共 1930 个源文件）进行医疗化深度定制，演进路线分为三个阶段：



```
阶段一：架构复用与基础搭建（当前）

├── 复用 claude-code 核心引擎（Agent循环、工具框架、会话管理、上下文管理）

├── 复用 Ink 终端UI框架与设计系统

├── 搭建医疗工具基类与安全框架

└── 建立项目工程化体系（构建、测试、规范）

阶段二：医疗功能填充

├── 开发30+医疗专用工具

├── 实现4层20个智能体

├── 接入HIS/EMR/LIS/PACS系统

├── 构建医学知识库与RAG

└── 终端UI医疗场景定制

阶段三：高级能力与生态

├── 科室子代理体系

├── 临床路径技能库

├── 临床决策支持引擎

├── 多医院适配平台

└── 插件生态与开放API
```

### 2.2 各层职责说明

#### 2.2.1 表现层



* **职责**：用户交互、信息展示、输入处理

* **核心组件**：基于 Ink 的终端 UI、REPL 交互界面、医疗场景专用界面（患者信息栏、危急值警报、医嘱确认面板）

* **技术基础**：React 19 + Ink 6.8 定制分叉，复用原始设计系统与键位框架

#### 2.2.2 编排层



* **职责**：多 Agent 任务调度、流程编排、结果聚合

* **核心组件**：超级调度智能体、任务分发器、结果聚合器、临床路径流程引擎

* **关键能力**：意图识别→Agent 路由→并行 / 串行执行→结果合并→质量校验

#### 2.2.3 Agent 层



* **职责**：AI 推理、决策生成、工具调用、对话管理

* **核心组件**：


  * Agent 引擎（基于 claude-code query.ts 状态机循环）

  * 4 层 20 个业务智能体（诊疗 / 管理 / 赋能 / 平台）

  * 8 类科室子代理（基于 AgentTool）

  * 技能系统（临床路径技能库）

  * 记忆系统（患者长期记忆、诊疗经验记忆）

#### 2.2.4 工具层



* **职责**：具体业务操作执行、外部系统交互

* **核心组件**：


  * 30 个医疗专用工具（8 大分类）

  * 基础工具集（从 claude-code 复用的 Read/Write/Glob/Grep 等）

  * 工具执行框架（buildMedicalTool 工厂、并发执行器、流式执行器）

  * 工具风险管控（三级风险确认、审计日志、权限校验）

#### 2.2.5 服务层



* **职责**：通用业务服务、数据处理、外部对接

* **核心组件**：


  * LLM API 服务（多模型适配、流式处理、缓存）

  * 认证授权服务（SSO 对接、RBAC+ABAC、CA 电子签名）

  * 会话管理服务（持久化、恢复、历史管理）

  * 上下文管理服务（Token 预算、四级压缩、医疗上下文构建）

  * 知识库 RAG 服务（检索、重排序、证据追溯）

  * 审计日志服务（全链路审计、防篡改、合规报告）

  * 集成适配器（HIS/EMR/LIS/PACS/ 医保等系统对接）

#### 2.2.6 基础设施层



* **职责**：计算、存储、网络、运维支撑

* **核心组件**：


  * Bun 运行时（高性能 JS/TS 运行时）

  * PostgreSQL + pgvector（关系型数据 + 向量存储）

  * Redis（缓存、会话、消息队列）

  * MinIO（文件、影像、文档对象存储）

  * Kafka（事件消息总线、系统集成异步通信）

  * 容器编排（Docker/Kubernetes）

  * 监控告警（Prometheus/Grafana/ELK）

### 2.3 层间依赖关系与数据流

#### 2.3.1 依赖方向



* 表现层 → 编排层 → Agent 层 → 工具层 → 服务层 → 基础设施层

* 同层模块间通过事件总线或明确定义的接口通信

## 3. 核心模块设计

### 3.1 Agent 引擎模块

#### 3.1.1 模块职责

基于 claude-code `query.ts` 的状态机式 Agent 循环，负责：



* 接收用户输入，构建医疗上下文

* 调用 LLM 进行推理

* 解析工具调用请求并执行

* 流式输出响应

* 管理多轮对话状态

* 处理中断、恢复、超时

#### 3.1.2 核心类与组件



| 类 / 组件             | 来源             | 职责                         |
| ------------------ | -------------- | -------------------------- |
| `QueryEngine`      | 复用 claude-code | 管理 Agent 会话生命周期，协调查询执行     |
| `MedicalQueryLoop` | 定制开发           | 医疗化 Agent 循环，注入患者上下文、风险管控  |
| `StreamingHandler` | 复用 claude-code | 处理 LLM 流式响应，支持增量渲染         |
| `ToolUseHandler`   | 定制开发           | 医疗工具调用处理，含权限校验、确认、审计       |
| `ContextBuilder`   | 定制开发           | 医疗上下文构建器（患者摘要 + 就诊摘要 + 历史） |
| `InterruptManager` | 定制开发           | 医疗场景中断管理（急诊插入、医生临时离开）      |

#### 3.1.3 Agent 循环医疗化改造点



1. **MedicalToolUseContext 扩展**：在原始 ToolUseContext 基础上增加患者上下文、当前就诊、用户角色、审计器

2. **系统提示词分层**：基础医疗伦理层→角色设定层→科室专业层→当前任务层

3. **医疗风险分区**：工具按风险等级分区执行，高风险工具强制用户确认 + CA 签名

4. **急诊中断恢复**：支持高优先级任务插入，当前任务状态保存与恢复

5. **多轮上下文策略**：门诊问诊 / 查房 / 会诊等不同场景的上下文管理策略

6. **Token 预算重分配**：患者摘要 30%+ 就诊摘要 30%+ 工具结果 25%+ 对话历史 15%

7. **医疗压缩规则**：检验结果只保留异常值、病历摘要提取关键信息

8. **输出安全过滤**：医疗建议输出前经过安全过滤与知识库验证

#### 3.2.4 三级风险确认机制



| 风险等级       | 定义               | 确认流程                | 示例工具                                                           |
| ---------- | ---------------- | ------------------- | -------------------------------------------------------------- |
| **low**    | 只读查询，不修改数据       | 自动执行，无需确认           | query\_patient, get\_lab\_result, get\_drug\_info              |
| **medium** | 数据修改 / 创建，影响诊疗   | 用户确认后执行             | write\_progress\_note, update\_patient\_info, order\_lab\_test |
| **high**   | 涉及医嘱 / 处方 / 用药安全 | 双重确认 + CA 签名 + 上级审核 | create\_order, create\_prescription, cancel\_order             |

#### 3.2.5 并发执行策略

医疗场景下工具执行分为两个分区：



| 分区       | 策略   | 最大并发 | 适用工具               |
| -------- | ---- | ---- | ------------------ |
| **只读分区** | 并行执行 | 10   | 所有 low 风险查询工具      |
| **写入分区** | 串行执行 | 1    | medium/high 风险修改工具 |

特殊规则：



* 同一患者的写入操作必须串行

* 药物相关工具必须先执行 drug\_interaction\_check 再执行 create\_prescription

* 危急值相关工具优先执行

### 3.4 上下文管理模块

#### 3.4.1 模块职责

基于 claude-code 四级渐进式压缩流水线，负责：



* 医疗上下文的构建与组织

* Token 预算的分配与追踪

* 上下文的渐进式压缩

* 医疗数据的智能摘要与提取

#### 3.4.2 四级压缩流水线（医疗适配）



```
Level 1: Snip（裁剪）

&#x20; ├── 工具结果超过大小时截断尾部

&#x20; ├── 检验结果只保留异常值和关键正常值

&#x20; └── 触发条件：单条工具结果 > 2000 tokens

Level 2: Microcompact（微压缩）

&#x20; ├── 旧消息的工具结果替换为摘要

&#x20; ├── 病历内容提取关键信息（诊断、用药、操作）

&#x20; └── 触发条件：上下文使用 > 60% 预算

Level 3: ContextCollapse（上下文折叠）

&#x20; ├── 多轮历史对话合并为摘要

&#x20; ├── 就诊过程提炼为时间线摘要

&#x20; └── 触发条件：上下文使用 > 80% 预算

Level 4: Autocompact（自动压缩）

&#x20; ├── 全量上下文重新构建，只保留核心信息

&#x20; ├── 患者摘要+就诊摘要+当前任务+最近3轮对话

&#x20; └── 触发条件：上下文使用 > 95% 预算
```

#### 3.4.3 医疗上下文构建策略



```
医疗上下文 = 固定部分 + 动态部分

固定部分（约占30% Token预算）：

├── 系统提示词（医疗伦理+角色设定）

├── 患者摘要（基本信息+过敏史+既往史+当前诊断）

└── 就诊摘要（主诉+现病史+查体+初步诊断）

动态部分（约占70% Token预算）：

├── 活跃医嘱与处方（15%）

├── 近期检验检查结果（异常值高亮）（15%）

├── 工具调用结果（25%）

└── 对话历史（最近N轮）（15%）
```

\## 触发条件

\- 主诉含"胸痛""胸闷""胸部不适"

\- 急诊分诊胸痛患者

\- 心电图提示ST段改变

\- 高度怀疑ACS → 启动导管室流程

\- 怀疑肺栓塞 → D-二聚体+CTPA

\[根据诊断分支执行对应子路径]

\- \[ ] 首次医疗接触到心电图≤10分钟

\- \[ ] STEMI患者进门到球囊扩张≤90分钟

### 6.4 与 HIS/EMR/LIS/PACS 系统的网络隔离方案



1. **网络分区**：应用区与医院系统区通过防火墙隔离，仅开放必要端口

2. **API 网关**：所有系统集成调用经过 API 网关，统一认证、限流、审计

3. **白名单控制**：仅允许应用服务器 IP 访问 HIS/LIS/PACS 接口

4. **数据库隔离**：不直接访问 HIS 数据库，通过 HIS 提供的 API 或只读视图

5. **数据流向控制**：默认禁止 HIS 系统主动访问应用区，仅应用区主动调用

6. **加密传输**：所有系统间通信使用 TLS 1.3 加密

7. **集成审计**：所有系统集成调用记录详细审计日志

## 7. 性能与可扩展性设计

### 7.1 性能指标



| 指标              | 目标值         | 测量方式               |
| --------------- | ----------- | ------------------ |
| **Agent 首响应时间** | ≤3 秒（P95）   | 从用户发送到首个 token 输出  |
| **工具调用响应时间**    | ≤2 秒（P95）   | 从工具调用到结果返回（不含外部系统） |
| **上下文压缩时间**     | ≤1 秒        | 触发压缩到完成            |
| **知识库检索时间**     | ≤500ms（P95） | 从查询到返回 Top-K 结果    |
| **并发会话数**       | ≥500        | 同时活跃的 Agent 会话数    |
| **系统吞吐量**       | ≥100 请求 / 秒 | API 网关处理能力         |
| **系统可用性**       | ≥99.9%      | 月度统计               |
| **数据持久化**       | 零丢失         | 会话与操作数据            |

#### 7.2.1 无状态服务扩展

#### 7.2.2 会话亲和性

由于 Agent 会话需要维护上下文状态，采用以下策略：



* 会话状态存储在 Redis（外部化），应用服务本身无状态

* 通过 Ingress 的 session affinity 确保同一会话路由到同一实例（减少 Redis 访问）

* 实例故障时，会话可从 Redis 恢复到其他实例（可能丢失少量上下文，自动触发压缩重建）

#### 7.2.3 数据库扩展



* **PostgreSQL**：读写分离（主库写，从库读），按时间分区大表

* **Redis**：Cluster 模式，数据分片

* **MinIO**：分布式纠删码，线性扩展存储容量

* **Kafka**：增加分区数，扩展消费者组

### 7.3 缓存策略

#### 7.3.1 多级缓存架构



```
L1: 应用内存缓存（Caffeine）

&#x20; ├── 系统配置、字典数据（TTL 1小时）

&#x20; ├── 工具定义元数据（TTL 10分钟）

&#x20; └── 容量：512MB

L2: Redis分布式缓存

&#x20; ├── 患者基本信息（TTL 30分钟，患者更新时主动失效）

&#x20; ├── 会话状态（TTL 24小时）

&#x20; ├── LLM响应缓存（相同问题+相同上下文，TTL 1小时）

&#x20; ├── 知识库检索结果（TTL 5分钟）

&#x20; └── 热点检验检查结果（TTL 10分钟）

L3: 数据库查询缓存

&#x20; ├── PostgreSQL物化视图（统计数据，每小时刷新）

&#x20; └── 只读从库负载均衡
```

#### 7.3.2 缓存一致性策略



* **患者数据**：更新时主动删除 Redis 缓存（Cache-Aside 模式）

* **会话状态**：每次变更写 Redis，定期持久化到 PostgreSQL

* **LLM 响应**：基于问题 + 上下文摘要的哈希作为 key，仅缓存低风险查询类响应

* **缓存穿透**：空结果也缓存（TTL 1 分钟），布隆过滤器防穿透

* **缓存雪崩**：TTL 加随机偏移（±10%），多级缓存降级

### 7.4 大文件 / 大数据量处理方案

#### 7.4.1 DICOM 影像处理



* 影像文件存储在 MinIO，不加载到 Agent 上下文

* Agent 通过`view_dicom`工具获取影像报告摘要和关键发现

* 如需查看影像，通过终端内嵌 DICOM Viewer（Cornerstone.js）流式加载

* 影像 AI 分析（结节检测等）异步执行，结果通过事件通知

#### 7.4.2 大批量检验数据



* 单次查询返回结果限制（默认 100 条），分页加载

* 历史检验结果只返回趋势摘要和异常值，不全量加载

* 大结果集触发 Snip 压缩，只保留前 N 条和异常值

* 统计分析类需求通过异步任务处理，完成后通知用户

#### 7.4.3 流式处理



* LLM 响应：SSE 流式输出，首字节时间 < 3 秒

* 工具执行：StreamingToolExecutor 支持工具执行与 API 流式并行

* 文件导出：流式写入，避免大文件占用内存

* 数据同步：与 HIS/LIS 的数据同步采用批量 + 增量 + 事件驱动

## 8. 架构决策记录（ADR）

### ADR-001：基于 claude-code 2.1.88 架构进行定制开发

**背景**：

健澜科技需要开发数智医院智能体应用。面临两个选择：(1) 从零开始构建 Agent 框架；(2) 基于成熟的开源 Agent 框架进行定制。claude-code 2.1.88 是 Anthropic 官方的 AI 编程助手，其 Agent 引擎经过大规模生产验证，架构设计精良。

**决策**：

选择基于 claude-code 2.1.88 源代码（source map 还原版）进行医疗化定制开发，而非从零构建。

**理由**：



1. **成熟度**：claude-code 的 Agent 循环、工具框架、上下文管理经过生产验证，避免从零开始的架构风险

2. **复用率**：核心引擎复用率约 79%，可大幅缩短开发周期（预计节省 60% 核心引擎开发时间）

3. **架构质量**：六层分层架构、流式处理、四级压缩、子代理系统等设计达到工业级标准

4. **技术栈一致**：TypeScript + React + Ink 技术栈适合终端医疗应用，团队学习成本低

5. **可维护性**：模块化设计使得医疗化定制可以在不破坏核心的前提下进行

**后果**：



* 正面：快速启动，核心引擎稳定，可聚焦医疗业务功能开发

* 负面：需要理解 1930 个源文件的复杂代码库，source map 还原代码可读性有限，需投入时间做架构审计

* 缓解：已完成全面架构审计，输出两份审计报告，明确了复用 / 定制 / 新增的边界



***

### ADR-002：选择 Ink 终端 UI 而非 Web UI

**背景**：

医疗智能体的 UI 呈现方式有两种选择：(1) 基于 Ink 的终端 CLI 界面（与 claude-code 一致）；(2) 基于 React/Vue 的 Web 界面。

**决策**：

选择基于 Ink 的终端 CLI 界面作为主要交互方式，同时预留 Web UI 的扩展能力。

**理由**：



1. **架构复用**：claude-code 的 UI 层（Ink 渲染引擎、设计系统、键位框架、REPL 交互）复用率 85%，Web UI 需要完全重写

2. **医生使用习惯**：许多医生习惯键盘操作，终端 UI 的快捷键效率高于鼠标点击，适合高频操作场景

3. **部署简单**：终端应用无需浏览器，可直接在医生工作站运行，启动快，资源占用低

4. **内网安全**：终端应用数据本地处理，减少网络传输，符合医疗数据安全要求

5. **离线可用**：终端模式支持本地小模型推理，在网络不稳定时仍可使用基础功能

6. **开发效率**：复用 Ink 组件库和设计系统，UI 开发效率高于从零构建 Web 前端

**后果**：



* 正面：UI 复用率高，开发快，部署简单，医生键盘操作效率高

* 负面：终端 UI 的视觉表现力有限，复杂图表和影像展示不如 Web；非技术背景用户学习成本较高

* 缓解：关键复杂界面（DICOM 影像、统计图表）通过内嵌 Web Viewer 解决；提供命令引导和帮助系统降低学习成本；后续可开发 Web 版本作为补充



***

### ADR-003：采用 Bun 运行时而非 Node.js

**背景**：

JavaScript/TypeScript 运行时有两个主要选择：Node.js（行业标准）和 Bun（新兴高性能运行时）。

**决策**：

选择 Bun >= 1.3.0 作为运行时，与原始 claude-code 保持一致。

**理由**：



1. **架构一致**：与原始 claude-code 运行时一致，避免运行时差异导致的兼容性问题

2. **性能优势**：Bun 的启动速度（比 Node 快 3 倍）、包安装速度（比 pnpm 快 2 倍）、测试运行速度均优于 Node

3. **原生 TypeScript**：Bun 原生支持 TypeScript，无需 ts-node 或编译步骤，开发体验更好

4. **内置工具**：Bun 内置打包器、测试运行器、SQLite，减少依赖数量

5. **资源效率**：Bun 内存占用更低，适合多实例部署和终端运行

**后果**：



* 正面：开发体验好，构建快，资源占用低，与原始代码兼容

* 负面：Bun 生态不如 Node 成熟，部分原生模块可能不兼容；医院 IT 团队对 Bun 熟悉度低

* 缓解：核心依赖均已验证 Bun 兼容；提供详细的部署文档和运维指南；Bun 的 API 与 Node 高度兼容，学习成本低



***

### ADR-004：采用 PostgreSQL + pgvector 而非专用向量数据库

**背景**：

医学知识库 RAG 需要向量存储能力。可选方案：(1) 专用向量数据库（Milvus/Qdrant/Weaviate）；(2) PostgreSQL + pgvector 扩展。

**决策**：

选择 PostgreSQL + pgvector 作为向量存储方案。

**理由**：



1. **技术栈简化**：医院环境已普遍使用 PostgreSQL，引入 pgvector 无需新增数据库技术栈，降低运维复杂度

2. **事务一致性**：向量数据与业务数据在同一数据库，保证事务一致性，避免分布式数据同步问题

3. **运维成本**：医院 DBA 已熟悉 PostgreSQL 运维，无需学习新的向量数据库运维

4. **性能足够**：pgvector 在百万级向量规模下性能满足需求，医学知识库的向量规模通常在 10-100 万级

5. **混合查询**：pgvector 支持向量相似度与结构化条件的混合查询，适合医疗场景（如 "心内科 + 2023 年指南" 的过滤检索）

6. **成本**：无需额外的向量数据库服务器和许可证成本

**后果**：



* 正面：技术栈统一，运维简单，事务一致，成本低

* 负面：超大规模（千万级以上向量）下性能不如专用向量数据库；高级向量功能（如多向量、稀疏向量）支持有限

* 缓解：医学知识库规模在 pgvector 能力范围内；如未来规模超预期，可通过分区表和索引优化解决，或迁移到专用向量数据库（接口抽象层支持平滑切换）



***

### ADR-005：采用适配器模式进行医院系统集成

**背景**：

不同医院的 HIS/EMR/LIS/PACS 系统厂商不同（卫宁、创业、东华、联众、智业等），接口协议和数据格式差异大。需要设计可扩展的集成方案。

**决策**：

采用适配器模式（Adapter Pattern）+ 配置化字段映射，为每个 HIS 厂商开发独立适配器，上层通过统一接口调用。

**理由**：



1. **解耦**：Agent 核心逻辑与具体 HIS 系统解耦，新增 HIS 厂商只需开发新适配器，不影响核心代码

2. **可测试**：适配器可独立测试，通过 Mock 服务模拟不同 HIS 接口

3. **配置化**：常见的字段映射和编码转换通过配置文件处理，减少硬编码，新医院接入更快

4. **标准化**：适配器将不同 HIS 的异构数据转换为内部标准模型（基于 HL7 FHIR），上层逻辑统一

5. **可维护**：HIS 接口变更时只需修改对应适配器，不影响其他模块

6. **渐进式**：可先支持主流 HIS 厂商（卫宁、创业），后续逐步扩展

**后果**：



* 正面：扩展性好，新医院接入快，核心逻辑稳定，可独立测试

* 负面：适配器开发工作量大（每个厂商 1-2 周），需要维护多个适配器版本；HIS 接口变更可能导致适配器失效

* 缓解：建立适配器开发规范和测试套件；与 HIS 厂商建立接口变更通知机制；适配器版本化管理，兼容多版本 HIS 接口



***

### ADR-006：医疗数据本地化处理，大模型可云端调用

**背景**：

医疗数据安全要求高，《数据安全法》《个人信息保护法》要求敏感数据保护。大模型推理需要大量算力，完全本地化部署成本高。

**决策**：

采用混合架构：敏感数据（患者标识、病历原文）在医院本地处理和存储，经过脱敏后可发送到云端大模型进行推理；支持完全本地化部署（私有化大模型）作为选项。

**理由**：



1. **合规安全**：患者原始数据不出院，满足医疗数据安全和隐私保护要求

2. **成本平衡**：无需购买昂贵的 GPU 服务器集群，利用云端大模型的弹性算力

3. **性能**：云端大模型能力更强、更新更快，医疗推理质量更高

4. **灵活部署**：对安全要求极高的医院可选择完全私有化部署，对成本敏感的医院选择混合云

5. **脱敏技术成熟**：身份证、手机号、姓名等敏感信息脱敏技术成熟，脱敏后数据无法识别特定个人

**后果**：



* 正面：安全合规，成本可控，AI 能力强，部署灵活

* 负面：需要开发数据脱敏引擎，增加架构复杂度；脱敏可能影响 AI 推理的准确性（如丢失患者姓名关联）；网络延迟可能影响响应速度

* 缓解：脱敏引擎保留医疗必要信息（年龄、性别、诊断、检验值），仅去除身份标识；建立脱敏质量评估机制；网络优化（专线 / CDN / 缓存）降低延迟；关键场景支持本地小模型兜底
