## 1. 医疗数据模型总体设计

### 1.1 数据模型设计原则

健澜科技数智医院智能体的数据模型设计遵循以下六大原则，确保模型在标准化、可扩展性、隐私保护、性能、合规和可维护性之间达到工业级平衡。

#### 1.1.1 标准化原则（Standardization）



| 标准                 | 应用范围                   | 说明                                                     |
| ------------------ | ---------------------- | ------------------------------------------------------ |
| **HL7 FHIR R4/R5** | 患者、就诊、医嘱、处方、检验、检查等核心实体 | 采用 FHIR 资源模型作为实体设计的基准映射，确保与医院 HIS/EMR/LIS/PACS 系统的互操作性 |
| **DICOM 3.0**      | 影像检查报告与影像数据            | 影像引用遵循 DICOM 标准，支持 Study/Series/Instance 三级结构          |
| **ICD-10（临床版）**    | 诊断编码                   | 采用国家医保局发布的 ICD-10 临床版编码体系                              |
| **ICD-9-CM-3**     | 手术操作编码                 | 手术与操作记录采用 ICD-9-CM-3 编码                                |
| **LOINC**          | 检验项目编码                 | 检验项目名称与单位采用 LOINC 标准编码                                 |
| **SNOMED CT**      | 临床术语标准化                | 症状、体征、疾病等临床术语采用 SNOMED CT 概念编码                         |
| **国家医保药品编码**       | 药品目录                   | 处方药品采用国家医保局统一药品编码                                      |
| **电子病历应用管理规范**     | 病历文书结构                 | 病历内容结构符合《电子病历应用管理规范（试行）》要求                             |

#### 1.1.2 可扩展原则（Extensibility）



* **实体扩展字段**：每个核心业务实体预留 `extensions` JSONB 字段，支持医院 / 科室级自定义属性扩展，无需修改表结构

* **枚举值可配置**：visitType、orderType、recordType 等枚举字段采用可配置字典表管理，支持 72 种医学文书类型的动态扩展

* **多租户架构**：数据模型天然支持多医院部署，通过 `hospitalId` 字段实现数据隔离

* **版本化设计**：病历、医嘱、处方等关键实体支持版本管理，每次修改生成新版本，保留完整变更历史

#### 1.1.3 隐私保护原则（Privacy by Design）



* **数据分级**：所有字段标注数据分级（公开 / 内部 / 敏感 / 机密），分级结果驱动加密、脱敏和访问控制策略

* **敏感字段加密**：身份证号、手机号、地址等直接标识符（PII）采用 AES-256 加密存储，密钥由医院 KMS 管理

* **最小化原则**：AI 上下文构建时仅包含诊疗必需的最小数据集，非必要 PII 字段不进入 LLM 上下文

* **脱敏默认**：所有面向 LLM 的工具输出默认执行脱敏处理，仅在明确授权且必要时返回明文

* **患者隔离**：每个患者的数据在存储、缓存、上下文三个层面严格隔离，禁止跨患者数据泄露

#### 1.1.4 性能原则（Performance）



* **读写分离**：热数据（当前就诊、活跃医嘱）走 Redis 缓存，温数据走 PostgreSQL，冷数据归档至对象存储

* **索引优化**：基于查询模式设计复合索引，核心查询路径覆盖索引，避免全表扫描

* **数据分区**：大表（消息、审计日志、检验结果）按时间分区，支持快速历史数据清理和查询裁剪

* **流式处理**：大文本（病历全文、对话历史）采用流式读写，避免全量加载导致内存溢出

#### 1.1.5 合规原则（Compliance）



* **电子病历评级**：数据模型支持电子病历系统功能应用水平分级评价（五级及以上）的数据完整性要求

* **互联互通标准**：支持医院信息互联互通标准化成熟度测评（四甲及以上）的标准化数据集要求

* **医保合规**：支持 DRG/DIP 分组所需的完整诊断、手术、费用数据链路

* **审计可追溯**：所有数据访问和修改操作记录不可篡改的审计日志，符合《医疗机构病历管理规定》要求

#### 1.1.6 可维护原则（Maintainability）



* **命名规范**：表名、字段名采用 snake\_case，实体类名采用 PascalCase，与开发规范保持一致

* **注释完整**：所有表和字段均包含中文注释，说明业务含义、取值范围和约束条件

* **迁移脚本**：所有 Schema 变更通过版本化迁移脚本管理，支持回滚

* **文档同步**：数据模型变更同步更新本文档，保持设计与实现一致

### 1.3 数据模型与 HL7 FHIR 标准的映射关系

健澜科技数智医院智能体的核心实体设计以 HL7 FHIR R4 资源模型为基准，确保与医院现有系统的标准化对接。映射关系如下：



| 本系统实体                   | FHIR R4 资源                          | 映射说明                                                        | 差异与扩展                                                                                                         |
| ----------------------- | ----------------------------------- | ----------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| **Patient（患者）**         | `Patient`                           | 基本信息、联系人、通信方式、管理信息直接映射                                      | 扩展：bloodType（血型）、allergies（过敏史关联 AllergyIntolerance）、chronicDiseases（慢性病标签）、dataLevel（数据分级）、tags（自定义标签）       |
| **Encounter（就诊记录）**     | `Encounter`                         | 就诊类型、科室、参与者、时间、状态、诊断直接映射                                    | 扩展：chiefComplaint（主诉）、visitType 扩展（体检）、session 关联                                                             |
| **MedicalRecord（电子病历）** | `DocumentReference` + `Composition` | 病历元数据映射 DocumentReference，结构化内容映射 Composition               | 扩展：recordType（72 种文书类型）、qualityScore（质控评分）、qcStatus（质控状态）、version（版本号）、source（AI 生成 / 手动 / 导入）                |
| **Order（医嘱）**           | `ServiceRequest`                    | 医嘱类型、内容、剂量、频次、周期、优先级、状态直接映射                                 | 扩展：auditorId（审核人）、orderType 扩展（膳食）、cdsCheckResult（CDS 校验结果）                                                   |
| **Prescription（处方）**    | `MedicationRequest`                 | 处方药品、剂量、频次、天数、数量、开方人、审核人直接映射                                | 扩展：prescriptionType（西药 / 中成药 / 中药饮片）、totalCost（总费用）、drugs 数组（MedicationRequest 的 medicationReference 扩展为内嵌明细） |
| **LabResult（检验报告）**     | `Observation` + `DiagnosticReport`  | 检验项目、结果、单位、参考范围、异常标识映射 Observation；报告元数据映射 DiagnosticReport | 扩展：criticalValueFlag（危急值标记）、notificationRecord（通知记录）、testItems 数组（Observation 集合内嵌）                           |
| **ImagingResult（检查报告）** | `ImagingStudy` + `DiagnosticReport` | 影像检查元数据映射 ImagingStudy，报告内容映射 DiagnosticReport              | 扩展：examBodyPart（检查部位）、images 数组（DICOM 引用，对应 ImagingStudy 的 series/instance）、finding（所见）、impression（印象）        |
| **Session（会话）**         | 无直接对应（自定义扩展）                        | AI 会话为健澜科技特有实体，无 FHIR 标准资源对应                                | 全新设计：sessionType（问诊 / 查房 / 会诊 / 质控 / 教学）、patientId、encounterId、medicalContext（医疗上下文快照）                        |
| **Message（消息）**         | 无直接对应（自定义扩展）                        | AI 对话消息为健澜科技特有实体                                            | 全新设计：role（user/assistant/tool/system）、toolCalls、toolResults、medicalContextDelta                               |

#### 1.3.1 FHIR 交互模式

系统与医院 FHIR 服务器之间的交互采用以下模式：



| 交互类型   | FHIR 操作                                           | 应用场景     |
| ------ | ------------------------------------------------- | -------- |
| **读取** | `GET [base]/Patient/[id]`                         | 患者信息查询   |
| **搜索** | `GET [base]/Encounter?patient=[id]&date=gt[date]` | 就诊记录检索   |
| **创建** | `POST [base]/ServiceRequest`                      | 医嘱回写 HIS |
| **更新** | `PUT [base]/MedicationRequest/[id]`               | 处方状态更新   |
| **订阅** | `Subscription`                                    | 检验结果到达通知 |
| **批量** | `Bundle`（transaction/batch）                       | 患者数据批量同步 |

### 1.4 数据模型与原始 claude-code 会话 / 消息模型的融合方案

健澜科技数智医院智能体基于 claude-code 2.1.88 核心引擎构建，其会话与消息模型在复用原始设计的基础上进行医疗化扩展。融合方案遵循 "**框架复用、字段扩展、上下文医疗化**" 三大策略。

#### 1.4.1 原始 claude-code 会话模型分析

原始 claude-code 的会话模型核心组件：



| 组件              | 源文件                           | 核心机制                                                                        |
| --------------- | ----------------------------- | --------------------------------------------------------------------------- |

| **会话持久化**       | `src/utils/sessionStorage.ts` | 转录文件（Transcript）JSONL 格式持久化，支持`--resume`恢复                                  |
| **消息类型**        | `src/types/`                  | user/assistant/system/tool\_result，支持 text/thinking/tool\_use content block |
| **AppState**    | `src/state/AppStateStore.ts`  | React 外部 Store，维护 messages、toolPermissionContext、mcp 等 50 + 字段              |
| **四级压缩**        | `src/services/compact/`       | Snip→Microcompact→ContextCollapse→Autocompact 渐进式压缩流水线                      |
| **Token 预算**    | `src/query/tokenBudget.ts`    | `createBudgetTracker()`预算追踪，支持自动续接                                          |

原始 claude-code 消息模型与医疗化扩展的融合：



| 维度        | 原始 claude-code              | 健澜科技医疗化扩展                                                                                  | 融合方式                              |
| --------- | --------------------------- | ------------------------------------------------------------------------------------------ | --------------------------------- |
| **消息角色**  | user / assistant / system   | 保留 + 新增 `doctor` / `patient` / `ai_agent` 语义角色                                             | 角色字段扩展，底层 API 仍映射为 user/assistant |
| **内容块**   | text / thinking / tool\_use | 保留 + 新增 `medical_structured`（结构化医疗数据）、`audio_ref`（录音引用）、`image_ref`（影像引用）                  | content block 类型扩展                |
| **工具调用**  | tool\_use / tool\_result    | 保留 + 工具分类扩展为医疗工具集（patient\_/emr\_/order\_/lab\_/cds\_等）                                    | 工具框架复用，工具集替换                      |
| **时间戳**   | 无显式字段（依赖转录文件顺序）             | 新增 `timestamp` 精确到毫秒                                                                       | 消息体扩展字段                           |
| **医疗上下文** | 无                           | 新增 `medicalContext` 对象，包含 currentPatient、currentEncounter、activeOrders、activePrescriptions | 消息级上下文快照                          |
| **会话类型**  | 无（通用编程会话）                   | 新增 `sessionType`：问诊 / 查房 / 会诊 / 质控 / 教学 / 科研 / 随访                                          | 会话级元数据                            |
| **会话关联**  | 无（独立会话）                     | 新增 `patientId`、`encounterId`、`departmentId` 关联                                             | 会话级外键                             |
| **意图标签**  | 无                           | 新增 `intentTag`：风险预警 / 随访 / 病历生成 / 问诊诊疗 / 病例讨论                                              | 会话级分类（与产品需求 M04-F02 对应）           |

#### 1.4.4 转录文件医疗化改造

原始 claude-code 采用 JSONL 转录文件持久化会话。健澜科技医疗化改造方案：



| 维度       | 原始设计                                    | 医疗化改造                                               |
| -------- | --------------------------------------- | --------------------------------------------------- |
| **存储位置** | `~/.claude/sessions/<session-id>.jsonl` | 医院安全存储（PostgreSQL + 对象存储），非本地文件系统                   |
| **保留期限** | 无明确限制                                   | 门诊病历≥15 年，住院病历≥30 年（符合《医疗机构病历管理规定》）                 |
| **关联索引** | 仅 sessionId                             | 增加 patientId、encounterId、doctorId、departmentId 复合索引 |
| **加密存储** | 明文 JSON                                 | 患者 PII 字段加密，转录文件整体加密存储                              |
| **审计日志** | 无                                       | 转录文件访问记录审计日志                                        |
| **压缩策略** | 四级压缩后释放原始消息                             | 压缩摘要保留，原始消息归档至冷存储，支持按需恢复                            |

## 2. 核心业务实体详细设计

### 2.1 患者（Patient）

患者实体是整个数据模型的核心，所有诊疗数据均以患者为中心组织。患者实体包含基本信息、医疗信息、管理信息和数据分级四个维度。

#### 2.1.1 字段定义



| 字段名                    | 类型           | 必填 | 说明                 | 约束                                                                                | 数据分级 |
| ---------------------- | ------------ | -- | ------------------ | --------------------------------------------------------------------------------- | ---- |
| **patient\_id**        | VARCHAR(32)  | 是  | 患者唯一标识（病案号 / EMPI） | 主键，医院内唯一                                                                          | 内部   |
| **hospital\_id**       | VARCHAR(32)  | 是  | 所属医院标识             | 多租户隔离字段                                                                           | 内部   |
| **name**               | VARCHAR(64)  | 是  | 患者姓名               | 非空，界面展示脱敏（如 "李 \* 英"）                                                             | 敏感   |
| **gender**             | ENUM         | 是  | 性别                 | 取值：male/female/unknown                                                            | 公开   |
| **birth\_date**        | DATE         | 是  | 出生日期               | 非空，用于年龄计算                                                                         | 敏感   |
| **id\_card**           | VARCHAR(255) | 否  | 身份证号（AES-256 加密存储） | 加密存储，唯一索引（加密值），支持校验位验证                                                            | 机密   |
| **phone**              | VARCHAR(255) | 否  | 联系电话（AES-256 加密存储） | 加密存储，支持手机号格式校验                                                                    | 机密   |
| **address**            | VARCHAR(512) | 否  | 家庭住址（AES-256 加密存储） | 加密存储                                                                              | 机密   |
| **blood\_type**        | ENUM         | 否  | 血型                 | 取值：A/B/AB/O/RH\_positive/RH\_negative/unknown                                     | 内部   |
| **allergies**          | JSONB        | 否  | 过敏史列表              | 结构：\[{allergen, reaction, severity, note, recordedAt}]，关联 FHIR AllergyIntolerance | 敏感   |
| **chronic\_diseases**  | JSONB        | 否  | 慢性疾病标签             | 结构：\[{diseaseCode (ICD-10), diseaseName, diagnosedAt, status}]                    | 敏感   |
| **emergency\_contact** | JSONB        | 否  | 紧急联系人              | 结构：{name, relation, phone (加密)}                                                   | 机密   |
| **registration\_date** | TIMESTAMP    | 是  | 建档日期               | 非空，默认当前时间                                                                         | 内部   |
| **status**             | ENUM         | 是  | 患者状态               | 取值：active/inactive/deceased/transferred                                           | 内部   |
| **tags**               | JSONB        | 否  | 自定义标签              | 结构：\["VIP","糖尿病管理","高血压随访"]，支持医院 / 科室自定义                                          | 内部   |
| **data\_level**        | ENUM         | 是  | 数据分级               | 取值：public/internal/sensitive/confidential，默认 sensitive                            | 内部   |
| **extensions**         | JSONB        | 否  | 扩展字段               | 医院 / 科室自定义属性，预留扩展                                                                 | 内部   |
| **created\_at**        | TIMESTAMP    | 是  | 创建时间               | 非空，默认当前时间                                                                         | 内部   |
| **updated\_at**        | TIMESTAMP    | 是  | 更新时间               | 非空，自动更新                                                                           | 内部   |
| **created\_by**        | VARCHAR(32)  | 否  | 创建人 ID             | 关联用户表                                                                             | 内部   |
| **updated\_by**        | VARCHAR(32)  | 否  | 更新人 ID             | 关联用户表                                                                             | 内部   |

#### 2.1.2 数据分级说明



| 分级                   | 包含字段                                                                                                     | 保护策略                                         |
| -------------------- | -------------------------------------------------------------------------------------------------------- | -------------------------------------------- |
| **公开（public）**       | gender                                                                                                   | 可在非授权场景展示                                    |
| **内部（internal）**     | patient\_id, hospital\_id, blood\_type, registration\_date, status, tags, data\_level, extensions, 时间戳字段 | 院内系统可访问，需登录认证                                |
| **敏感（sensitive）**    | name, birth\_date, allergies, chronic\_diseases                                                          | 需患者数据访问授权，LLM 上下文中默认脱敏展示                     |
| **机密（confidential）** | id\_card, phone, address, emergency\_contact                                                             | AES-256 加密存储，需特殊权限解密，禁止进入 LLM 上下文（除非明确授权且必要） |

#### 2.1.3 与其他实体的关系



* **1:N → Encounter**：一个患者可多次就诊，通过 `encounter.patient_id` 关联

* **1:N → MedicalRecord**：一个患者有多份病历，通过 `medical_record.patient_id` 关联

* **1:N → Order**：一个患者有多条医嘱，通过 `order.patient_id` 关联

* **1:N → Prescription**：一个患者有多张处方，通过 `prescription.patient_id` 关联

* **1:N → LabResult**：一个患者有多份检验报告，通过 `lab_result.patient_id` 关联

* **1:N → ImagingResult**：一个患者有多份检查报告，通过 `imaging_result.patient_id` 关联

* **1:N → Session**：一个患者可关联多个 AI 会话，通过 `session.patient_id` 关联

* **1:N → FollowupTask**：一个患者有多个随访任务，通过 `followup_task.patient_id` 关联

| **qc\_issues**        | JSONB        | 否  | 质控问题列表           | 结构：\[{ruleId, issueDescription, severity, scoreDeduction, suggestion, resolved}]                                                                                                                                                                                               | 内部   |
| **audio\_ref**        | VARCHAR(256) | 否  | 关联录音文件引用         | ADS 录音转写场景关联原始音频，存储对象存储路径                                                                                                                                                                                                                                                      | 内部   |

#### 2.3.2 版本管理机制

病历版本管理采用 "**当前版本 + 历史版本归档**" 模式：



* `medical_record` 主表存储当前最新版本

* `medical_record_history` 历史表存储每次修改前的版本快照

* 每次修改触发：将当前版本写入历史表 → 主表 version+1 → 更新内容

* 历史版本不可修改，仅支持查看和对比

* 保留期限：门诊病历≥15 年，住院病历≥30 年

#### 2.3.3 与其他实体的关系



* **N:1 → Patient**：通过 `patient_id` 关联患者

* **N:1 → Encounter**：通过 `encounter_id` 关联就诊

* **1:N → QCResult**：一份病历有多条质控结果，通过 `qc_result.record_id` 关联

* **N:M → KnowledgeDoc**：病历可引用知识库文档，通过引用表关联

## 3. 数据存储设计

### 3.1 存储分层架构

健澜科技数智医院智能体采用**热 - 温 - 冷三级存储分层架构**，根据数据访问频率和业务时效性将数据分配到不同存储介质，在性能、成本和合规之间取得平衡。



```
┌──────────────────────────────────────────────────────────────────────┐

│                        三级存储分层架构                                  │

├──────────────────────────────────────────────────────────────────────┤

│                                                                      │

│  │  热数据层（Hot Data）— Redis 集群                           │    │

#### 3.1.1 各层数据分布与策略



| 存储层     | 技术选型               | 数据类型                                            | 访问频率     | 保留策略                         | 典型数据量     |
| ------- | ------------------ | ----------------------------------------------- | -------- | ---------------------------- | --------- |
| **热数据** | Redis 7.x 集群（哨兵模式） | 当前就诊、活跃医嘱、会话消息、患者摘要、近期检验结果                      | 极高（实时访问） | LRU 淘汰 + TTL 过期（会话结束后 24 小时） | <10GB     |
| **温数据** | PostgreSQL 16 主从集群 | 全部结构化业务数据（患者、就诊、病历、医嘱、处方、检验、检查、会话、消息、质控、知识库元数据） | 高（日常业务）  | 全量保留 + 按时间分区，超期归档至冷存储        | 100GB-1TB |
| **冷数据** | MinIO 对象存储 + 磁带归档  | DICOM 影像、录音文件、病历全文、历史会话转录、知识库原文、审计日志归档          | 低（合规查询）  | 门诊≥15 年，住院≥30 年，审计≥6 个月      | TB 级      |

#### 3.1.2 数据流转机制



```
数据产生 → 温数据层（PostgreSQL）持久化

&#x20;   │

&#x20;   ├─ 热数据缓存 → 写入Redis（当前就诊/活跃医嘱/会话消息）

&#x20;   │

&#x20;   └─ 大文件存储 → 写入MinIO（DICOM/录音/病历全文），PostgreSQL存储引用

数据访问 → 先查Redis缓存

&#x20;   │

&#x20;   ├─ 命中 → 直接返回（<1ms）

&#x20;   │

&#x20;   └─ 未命中 → 查询PostgreSQL（<10ms）

&#x20;       │

&#x20;       └─ 回填Redis缓存

数据归档 → 定时任务（每日凌晨）

&#x20;   │

&#x20;   ├─ 超期温数据（如>2年的历史会话）→ 迁移至MinIO归档

&#x20;   │

&#x20;   └─ PostgreSQL保留归档元数据索引，支持按需恢复
```

### 3.2 数据库选型

#### 3.2.1 选型决策矩阵



| 维度           | PostgreSQL 16                   | MySQL 8.0            | Oracle 19c    | 选型结论                              |
| ------------ | ------------------------------- | -------------------- | ------------- | --------------------------------- |
| **JSONB 支持** | ✅ 原生 JSONB，支持 GIN 索引、JSON 路径查询  | ⚠️ JSON 类型，功能较弱      | ⚠️ JSON 支持有限  | PostgreSQL 胜出，医疗实体大量使用 JSONB 扩展字段 |
| **全文检索**     | ✅ 内置 tsvector/tsquery，支持中文分词扩展  | ⚠️ FULLTEXT 索引，中文支持差 | ✅ Oracle Text | PostgreSQL 胜出，病历全文检索需求            |
| **分区表**      | ✅ 声明式分区，支持 RANGE/LIST/HASH      | ⚠️ 分区功能有限            | ✅ 分区功能强       | PostgreSQL 胜出，大表时间分区需求            |
| **扩展性**      | ✅ 开源免费，插件生态丰富（PostGIS、pgvector） | ✅ 开源免费               | ❌ 商业授权昂贵      | PostgreSQL 胜出，pgvector 支持向量检索     |
| **数据完整性**    | ✅ 严格 ACID，支持复杂约束、外键、触发器         | ✅ ACID               | ✅ ACID        | 相当，PostgreSQL 约束更灵活               |
| **医疗行业适配**   | ✅ 多家医疗信息化厂商采用                   | ✅ 广泛使用               | ✅ 大型医院采用      | 均有应用，PostgreSQL 更适合 AI 场景         |
| **运维成本**     | 低（开源）                           | 低（开源）                | 高（商业）         | PostgreSQL/MySQL 胜出               |
| **向量检索**     | ✅ pgvector 插件，支持 ANN 索引         | ❌ 原生不支持              | ❌ 原生不支持       | PostgreSQL 胜出，RAG 知识库向量检索需求       |

**最终选型**：**PostgreSQL 16** 作为核心关系型数据库，理由：



1. 原生 JSONB 支持医疗实体的扩展字段和结构化内容存储

2. pgvector 插件支持知识库向量检索，减少独立向量数据库的运维复杂度

3. 声明式分区支持大表（消息、审计日志）的时间分区

4. 全文检索支持病历内容搜索

5. 开源免费，降低医院私有化部署成本

6. 严格 ACID 合规，满足医疗数据完整性要求

#### 3.2.2 配套存储组件



| 组件             | 版本      | 用途                         | 部署模式                 |
| -------------- | ------- | -------------------------- | -------------------- |
| **PostgreSQL** | 16.x    | 核心结构化数据存储                  | 一主两从，读写分离，PITR 时间点恢复 |
| **Redis**      | 7.x     | 热数据缓存、会话状态、分布式锁            | 哨兵模式，3 节点，开启 AOF 持久化 |
| **MinIO**      | RELEASE | 对象存储，DICOM 影像、录音、文件归档      | 分布式 4 节点，纠删码 EC:4+2  |
| **pgvector**   | 0.7.x   | PostgreSQL 向量检索扩展（知识库 RAG） | 随 PostgreSQL 部署      |
| **PostGIS**    | 3.4.x   | 地理信息扩展（可选，用于区域医疗）          | 随 PostgreSQL 部署      |

### 3.4 索引设计与查询优化

#### 3.4.1 索引设计原则



| 原则          | 说明                      | 应用示例                                                               |
| ----------- | ----------------------- | ------------------------------------------------------------------ |
| **查询驱动**    | 基于实际查询模式设计索引，避免过度索引     | 患者查询按 patient\_id+hospital\_id，就诊查询按 patient\_id+start\_time DESC  |
| **复合索引**    | 高频组合查询条件建立复合索引，遵循最左前缀原则 | idx\_order\_patient: (hospital\_id, patient\_id, start\_date DESC) |
| **部分索引**    | 对高选择性的状态字段建立部分索引，减少索引体积 | idx\_order\_active: WHERE status='active'，仅索引活跃医嘱                  |
| **GIN 索引**  | JSONB 字段和全文检索使用 GIN 索引  | allergies、chronic\_diseases、content 等 JSONB 字段                     |
| **覆盖索引**    | 高频查询的返回字段包含在索引中，避免回表    | 患者列表查询索引包含 name、gender、birth\_date                                 |
| **避免索引列运算** | 索引列不参与函数运算，确保索引可用       | 时间范围查询使用 timestamp BETWEEN，而非 DATE (timestamp)                     |

#### 3.4.2 核心查询路径与索引覆盖



| 查询场景    | 查询条件                                           | 使用索引                              | 预期性能  |
| ------- | ---------------------------------------------- | --------------------------------- | ----- |
| 患者信息查询  | hospital\_id + patient\_id                     | 主键索引                              | <1ms  |
| 患者就诊历史  | hospital\_id + patient\_id + start\_time DESC  | idx\_encounter\_patient           | <5ms  |
| 患者病历列表  | hospital\_id + patient\_id + create\_time DESC | idx\_medical\_record\_patient     | <5ms  |
| 活跃医嘱查询  | hospital\_id + patient\_id + status=active     | idx\_order\_active（部分索引）          | <3ms  |
| 患者检验报告  | hospital\_id + patient\_id + report\_time DESC | lab\_result 表对应索引                 | <5ms  |
| 会话消息查询  | hospital\_id + session\_id + timestamp DESC    | idx\_message\_session             | <5ms  |
| 病历全文搜索  | hospital\_id + title LIKE '% 关键词 %'            | idx\_medical\_record\_title\_trgm | <50ms |
| 质控待处理列表 | hospital\_id + qc\_status=pending              | idx\_medical\_record\_qc\_status  | <5ms  |
| 医生今日就诊  | hospital\_id + doctor\_id + start\_time = 今天   | idx\_encounter\_doctor            | <5ms  |

#### 3.4.3 查询优化策略



1. **分页优化**：大结果集使用 keyset 分页（基于唯一键的 WHERE ... LIMIT），避免 OFFSET 深分页性能问题

2. **统计查询**：高频统计（患者数、就诊数）使用物化视图，定时刷新，避免实时 COUNT 全表

3. **慢查询监控**：启用 pg\_stat\_statements 扩展，监控慢查询，定期优化

4. **连接池**：使用 PgBouncer 连接池，管理数据库连接，避免连接数耗尽

5. **读写分离**：读操作走只读从库，写操作走主库，减轻主库压力

6. **批量操作**：批量插入 / 更新使用 COPY 或批量 INSERT，减少事务开销

#### 3.5.2 分区管理自动化



```
\-- 分区维护任务（每日凌晨执行，通过pg\_cron或外部调度器）

\-- 1. 创建未来3个月的分区（避免跨月时无分区可用）

\-- 2. 归档超期分区（迁移至MinIO， detach分区）

\-- 3. 分析分区统计信息（ANALYZE，确保查询优化器有最新统计）

\-- 归档超期分区示例

CREATE OR REPLACE FUNCTION archive\_old\_message\_partitions(archive\_age\_months INTEGER DEFAULT 24)

RETURNS void AS \$\$

DECLARE

&#x20;   partition\_record RECORD;

&#x20;   archive\_date DATE := CURRENT\_DATE - (archive\_age\_months || ' months')::INTERVAL;

BEGIN

&#x20;   FOR partition\_record IN

&#x20;       SELECT relname

&#x20;       FROM pg\_class

&#x20;       WHERE relname LIKE 'message\_%'

&#x20;         AND relname < 'message\_' || TO\_CHAR(archive\_date, 'YYYY\_MM')

&#x20;       ORDER BY relname

&#x20;   LOOP

&#x20;       \-- 1. 将分区数据导出至MinIO（通过外部脚本）

&#x20;       \-- 2. Detach分区

&#x20;       EXECUTE format('ALTER TABLE message DETACH PARTITION %I', partition\_record.relname);

&#x20;       \-- 3. 删除分区表（数据已归档）

| 恢复场景            | 恢复步骤                                                  | RTO 目标 | RPO 目标          |

## 4. 上下文管理医疗化改造

### 4.1 基于 claude-code 四级压缩流水线的医疗场景适配

健澜科技数智医院智能体复用 claude-code 核心引擎的**四级渐进式压缩流水线**（Snip→Microcompact→ContextCollapse→Autocompact），并针对医疗场景进行适配改造，确保在有限的 Token 窗口内最大化保留临床关键信息。

#### 4.1.1 claude-code 四级压缩流水线回顾



| 压缩级别                         | 触发条件                     | 压缩机制                                                       | 医疗场景适配                                                                            |
| ---------------------------- | ------------------------ | ---------------------------------------------------------- | --------------------------------------------------------------------------------- |
| **第 1 级：Snip 裁剪**            | 消息数超过 HISTORY\_SNIP 阈值   | 保留最近 N 轮完整对话，裁剪早期轮次，生成 snip boundary 标记                    | 医疗化：优先保留当前就诊相关消息，裁剪历史就诊的非关键对话；裁剪前提取关键临床信息（诊断、医嘱、异常检验）保留在摘要中                       |
| **第 2 级：Microcompact 微压缩**   | 单个工具结果超过大小阈值             | 大体积 tool\_result 替换为摘要 + 文件引用，cachedMicrocompact 利用 API 缓存 | 医疗化：检验 / 检查报告工具结果只保留异常值和关键结论，正常值折叠为摘要；病历全文引用外部存储路径                                |
| **第 3 级：ContextCollapse 折叠** | 用户手动折叠或自动折叠              | 交互式折叠视图，折叠摘要存储在独立 collapse store，读取时投影不修改原始消息              | 医疗化：支持按临床事件折叠（如 "入院评估"、"手术过程"、"出院小结"），折叠摘要包含关键临床决策点                               |
| **第 4 级：Autocompact 自动压缩**   | Token 数超过阈值（如上下文窗口的 70%） | 使用独立 LLM 请求生成历史摘要，生成 compact\_boundary 系统消息，摘要 + 保留段替换历史   | 医疗化：摘要生成使用医疗专用提示词，确保保留诊断演变、治疗调整、关键检验趋势、临床决策依据等医疗关键信息；摘要结构化为 "患者摘要 + 就诊摘要 + 诊疗时间线" |

医疗上下文是 AI 智能体进行临床推理的基础，健澜科技数智医院智能体采用**结构化医疗上下文构建策略**，在每次 API 请求前动态组装患者摘要、就诊摘要、活跃医嘱和近期检验检查结果，确保 AI 获得完整、准确、最新的临床信息。

#### 4.2.1 上下文构建流水线



```

&#x20;   │

&#x20;   ▼

│  医疗上下文构建器（Medical Context Builder）                  │

│                                                              │

│  1. 识别当前患者（从session.medical\_context.currentPatient） │

│     ├─ 活跃医嘱与处方（Order/Prescription表，status=active） │

│     ├─ 近期检验结果（LabResult表，最近30天，异常值优先）     │

### 4.3 Token 预算分配策略

健澜科技数智医院智能体采用**固定比例 + 动态调整**的 Token 预算分配策略，在 1M 上下文窗口（或模型支持的最大窗口）内，按医疗场景的信息重要性分配 Token 预算。

#### 4.3.1 基础 Token 预算分配



| 上下文组件       | 预算占比 | Token 数（以 200K 窗口为例） | 说明                              |
| ----------- | ---- | -------------------- | ------------------------------- |
| **系统提示词**   | 5%   | \~10,000             | 医疗助手系统提示词、工具定义、医疗伦理声明、安全约束      |
| **患者摘要**    | 15%  | \~30,000             | 固定包含：基本信息、过敏史、既往史、当前诊断、紧急联系人    |
| **就诊摘要**    | 25%  | \~50,000             | 本次就诊：主诉、现病史、查体、辅助检查、诊断、诊疗经过     |
| **活跃医嘱与处方** | 10%  | \~20,000             | 当前活跃医嘱、处方明细、用药方案                |
| **近期检验检查**  | 15%  | \~30,000             | 异常值优先，正常值折叠，趋势分析                |
| **工具结果**    | 15%  | \~30,000             | 当前轮次工具调用结果（检验查询、知识库检索、CDS 校验等）  |
| **对话历史**    | 15%  | \~30,000             | 最近 N 轮对话，超阈值触发四级压缩              |
| **输出预留**    | -    | \~20,000             | 模型输出 Token 预留（不占输入预算，但需在总窗口内预留） |

> **注意**
>
> ：以上为基础分配比例，实际执行时根据场景动态调整。例如急诊场景增加检验检查和工具结果占比，门诊随访场景增加对话历史和患者摘要占比。

#### 4.3.2 动态调整机制



```
Token预算动态调整流程：

1\. 计算各组件实际Token占用

&#x20;  │

&#x20;  ├─ 患者摘要：固定结构，Token数相对稳定（300-500）

&#x20;  ├─ 就诊摘要：根据病历复杂度动态（500-2000）

&#x20;  ├─ 活跃医嘱：根据医嘱数量动态（200-1000）

&#x20;  ├─ 近期检验检查：根据异常项数量动态（300-2000）

&#x20;  ├─ 工具结果：根据当前轮次工具调用动态（500-5000）

&#x20;  └─ 对话历史：根据会话轮次动态（1000-50000+）

&#x20;  │

2\. 优先级排序（Token不足时按优先级裁剪）

&#x20;  │

&#x20;  ├─ P0（不可裁剪）：系统提示词、患者摘要、当前就诊诊断

&#x20;  ├─ P1（优先保留）：就诊摘要核心信息、活跃医嘱、异常检验值

&#x20;  ├─ P2（可压缩）：就诊摘要细节、正常检验值、检查所见

&#x20;  ├─ P3（可裁剪）：早期对话历史、非关键工具结果、知识库引用全文

&#x20;  │

3\. 触发压缩

&#x20;  │

&#x20;  ├─ 对话历史超预算 → Snip裁剪 → Microcompact → Autocompact

&#x20;  ├─ 工具结果超预算 → Microcompact（大结果摘要+引用）

&#x20;  ├─ 检验检查超预算 → 只保留异常值，正常值折叠为计数

&#x20;  └─ 就诊摘要超预算 → 保留主诉+诊断+治疗方案，细节折叠
```

### 4.4 医疗场景的上下文压缩规则

医疗场景的上下文压缩遵循 \*\*"临床关键信息零丢失，非关键信息渐进压缩"\*\* 原则，确保压缩后的上下文仍支持 AI 进行准确的临床推理。

#### 4.4.1 检验结果压缩规则



| 压缩级别         | 规则                   | 示例                                    |
| ------------ | -------------------- | ------------------------------------- |
| **L0 完整保留**  | 危急值、本次就诊新增异常值、趋势恶化指标 | 肌钙蛋白 I 0.08↑（危急值），完整保留数值 + 参考值 + 异常标记 |
| **L1 摘要保留**  | 既往异常但已稳定的指标、非关键异常指标  | "糖化血红蛋白 7.8%↑（2026-09-10）"，保留数值和日期    |
| **L2 分类折叠**  | 大量正常值项目              | "血常规、肝肾功能、电解质均正常"，折叠为分类摘要             |
| **L3 仅保留结论** | 历史检验报告（>30 天）        | "2026-08 血脂异常（LDL-C 3.5）"，仅保留关键异常结论   |

#### 4.4.2 病历摘要压缩规则



| 病历类型     | 压缩规则                                | 保留的关键字段          |
| -------- | ----------------------------------- | ---------------- |
| **门诊病历** | 保留主诉 + 诊断 + 治疗方案，现病史和查体压缩为摘要        | 主诉、诊断、处方、随访建议    |
| **入院记录** | 保留主诉 + 现病史摘要 + 既往史 + 初步诊断，查体和辅助检查折叠 | 主诉、现病史核心、诊断、诊疗计划 |
| **病程记录** | 保留病情变化 + 治疗调整 + 上级医师意见，日常记录折叠       | 病情变化、治疗调整、关键决策   |
| **手术记录** | 保留手术名称 + 关键步骤 + 术中发现 + 术后诊断，细节折叠    | 手术名称、术中发现、术后诊断   |
| **出院小结** | 完整保留（作为就诊总结的核心依据）                   | 全部字段             |
| **抢救记录** | 完整保留（医疗法律关键文档）                      | 全部字段             |

#### 4.4.3 对话历史压缩规则



| 压缩级别                | 触发条件                | 压缩规则                                                          |
| ------------------- | ------------------- | ------------------------------------------------------------- |
| **Snip 裁剪**         | 消息数 > 50 轮          | 保留最近 10 轮完整对话，更早轮次裁剪为 "历史对话摘要"，提取关键临床决策点                      |
| **Microcompact**    | 单条工具结果 > 2000 Token | 检验 / 检查结果只保留异常值，病历只保留结构化摘要，大结果持久化到外部存储                        |
| **ContextCollapse** | 用户手动折叠或连续 5 轮同一主题   | 按临床事件折叠（如 "术前讨论"、"抢救过程"），折叠摘要包含事件类型 + 关键决策 + 结果               |
| **Autocompact**     | Token 占用 > 窗口 70%   | 使用医疗专用 LLM 提示词生成结构化摘要：患者摘要 + 就诊摘要 + 诊疗时间线 + 待办事项，保留最近 3 轮完整对话 |

#### 4.4.4 压缩后信息完整性校验

每次压缩执行后，系统自动进行**临床关键信息完整性校验**，确保以下信息零丢失：



| 校验项   | 校验方法                   | 丢失处理                   |
| ----- | ---------------------- | ---------------------- |
| 过敏史   | 压缩后摘要中必须包含完整过敏史列表      | 如丢失，从患者摘要重新注入          |
| 当前诊断  | 压缩后摘要中必须包含主诊断和其他诊断     | 如丢失，从就诊摘要重新注入          |
| 活跃医嘱  | 压缩后摘要中必须包含全部活跃药品医嘱     | 如丢失，从 Order 表重新查询注入    |
| 危急值   | 压缩后摘要中必须包含全部未解决的危急值    | 如丢失，从 LabResult 重新查询注入 |
| 未解决问题 | 压缩后摘要中必须包含待办事项和未解决临床问题 | 如丢失，从会话状态重新提取          |

校验通过后，压缩结果才生效；如校验失败，触发重新压缩或回退到上一版本。

## 5. 知识库架构设计

### 5.1 知识库分层架构

#### 5.2.3 知识冲突处理机制

当不同来源的知识出现不一致时，系统按以下优先级处理：



| 冲突类型          | 处理策略                                         | 示例                                             |
| ------------- | -------------------------------------------- | ---------------------------------------------- |
| **不同层级冲突**    | 高层级优先（L2>L3>L4>L5），L1 作为基础不参与冲突              | 国际指南推荐 A 方案，医院本地规范推荐 B 方案 → 优先引用国际指南，同时标注医院规范  |
| **同层级不同来源冲突** | 权威性排序：官方指南 > 专家共识 > 教材 > 文献 > 经验；标注冲突，呈现双方观点 | ACC/AHA 指南推荐 A，ESC 指南推荐 B → 同时呈现，标注适用人群差异      |
| **新旧版本冲突**    | 新版本优先，旧版本标记为 "已过时"，保留历史版本供追溯                 | 2023 版指南推荐 A，2025 版更新为 B → 使用 2025 版，旧版归档      |
| **适应症冲突**     | 按患者具体情况匹配，标注适用条件                             | 某药物在肾功能正常时推荐 A 剂量，肾功能不全时推荐 B 剂量 → 根据患者 eGFR 选择 |
| **经验知识与指南冲突** | 指南优先，经验知识仅作为补充参考，明确标注                        | 某医生经验用 A 方案，指南推荐 B 方案 → 优先指南，经验标注 "个人经验，非指南推荐" |

**冲突处理输出**：AI 在生成回答时，如存在知识冲突，必须：



1. 明确标注存在不同观点

2. 呈现各来源的观点和依据

3. 按权威性排序推荐

4. 建议医生根据患者具体情况判断

5. 不单方面选择某一观点作为唯一答案

### 5.3 知识版本管理

#### 5.3.1 版本管理策略



| 管理维度      | 策略                          | 说明                                 |
| --------- | --------------------------- | ---------------------------------- |
| **版本号规则** | 语义化版本：主版本。次版本。修订号（如 v2.1.0） | 主版本：重大更新（指南全面修订）；次版本：新增内容；修订号：勘误修正 |
| **版本保留**  | 全量保留所有历史版本，不删除              | 支持追溯知识演变，满足医疗合规要求                  |
| **版本对比**  | 支持任意两个版本的差异对比（diff）         | 高亮新增、删除、修改的内容                      |
| **版本回滚**  | 支持回滚到任意历史版本                 | 新版本出现问题时可快速回滚                      |
| **版本引用**  | AI 引用知识时必须标注版本号和发布日期        | 确保引用的是当前有效版本，避免引用过时知识              |
| **版本有效期** | 每条知识标注生效日期和失效日期             | 过期知识自动标记，不参与检索（或检索时标注 "已过期"）       |

## 6. RAG 检索增强生成设计

### 6.1 RAG 流水线架构

### 6.2 检索策略

#### 6.2.1 向量检索（语义相似度）

向量检索基于文本的语义相似度，能够理解查询和文档之间的深层语义关联，是 RAG 系统的核心检索方式。



| 维度               | 设计                                     | 说明                                                    |
| ---------------- | -------------------------------------- | ----------------------------------------------------- |
| **Embedding 模型** | 医疗领域微调的 BGE-large-zh-v1.5 或同类模型        | 在通用中文 Embedding 基础上，使用医学文献、临床指南、病历文本进行领域微调，提升医学语义理解能力 |
| **向量维度**         | 1024 维                                 | 平衡检索精度和存储 / 计算成本                                      |
| **相似度度量**        | 余弦相似度（Cosine Similarity）               | 向量归一化后内积计算，适合语义相似度场景                                  |
| **索引类型**         | HNSW（分层可导航小世界图）                        | ANN 近似最近邻索引，支持高维向量快速检索，召回率 > 95%，查询延迟 < 50ms          |
| **索引参数**         | M=32, efConstruction=200, efSearch=100 | 平衡索引构建速度、内存占用和查询精度                                    |
| **检索 Top-K**     | Top-50 候选                              | 向量检索返回 50 个候选结果，供后续重排序                                |
| **过滤条件**         | 支持按知识层级、分类、发布日期、权威性过滤                  | 检索前可指定过滤条件，如 "仅检索 L2 临床指南，2023 年后发布"                  |

**向量检索适用场景**：



* 自然语言问题（如 "急性胸痛的鉴别诊断有哪些？"）

* 语义相关但关键词不匹配的文档

* 临床场景的模糊查询

* 相似病例检索

#### 6.2.2 关键词检索（BM25）

关键词检索基于词频匹配，适合精确术语和专有名词的检索，与向量检索形成互补。



| 维度           | 设计                                               | 说明                                  |
| ------------ | ------------------------------------------------ | ----------------------------------- |
| **检索算法**     | BM25（Best Matching 25）                           | 经典概率检索算法，考虑词频、文档长度、逆文档频率            |
| **分词器**      | 中文医学分词器（基于 Jieba + 医学词典扩展）                       | 支持医学术语精确分词，避免 "冠心病" 被拆为 "冠 / 心 / 病" |
| **索引引擎**     | PostgreSQL 全文检索（tsvector/tsquery）或 Elasticsearch | 小规模用 PG 全文检索，大规模用 Elasticsearch     |
| **检索字段**     | 标题、摘要、标签、关键推荐、全文                                 | 标题权重最高，全文权重最低                       |
| **检索 Top-K** | Top-30 候选                                        | 关键词检索返回 30 个候选                      |
| **模糊匹配**     | 支持拼音、同义词、缩写扩展                                    | 如 "ACS" 匹配 "急性冠脉综合征"，"心梗" 匹配 "心肌梗死" |

**关键词检索适用场景**：



* 精确医学术语查询（如 "ST 段抬高型心肌梗死"）

* 药品名称、检查项目名称检索

* 指南编号、ICD 编码检索

* 需要精确匹配的场景

#### 6.2.3 结构化检索（知识图谱）

结构化检索基于医学知识图谱，利用实体间关系进行精准推理和关联检索。



| 维度       | 设计                                 | 说明                                  |
| -------- | ---------------------------------- | ----------------------------------- |
| **知识图谱** | 医学知识图谱（疾病 - 症状 - 检查 - 药物 - 治疗关系网络） | 包含 10 万 + 医学实体，100 万 + 关系，覆盖主要疾病和药物 |
| **图数据库** | Neo4j 或 Apache AGE（PostgreSQL 图扩展） | 支持 Cypher 查询语言，高效遍历实体关系             |
| **实体类型** | 疾病、症状、体征、药物、检查、治疗、手术、并发症、禁忌症、适应症   | 覆盖临床核心实体类型                          |
| **关系类型** | 有症状、需要检查、用药物、禁忌、并发症、鉴别诊断、适应症、不良反应  | 覆盖临床推理核心关系                          |
| **检索方式** | 实体链接→关系遍历→子图提取                     | 从查询中的实体出发，遍历相关关系，提取关联知识子图           |
| **推理能力** | 支持多跳推理（如疾病→并发症→检查→诊断标准）            | 支持 2-3 跳关系推理，挖掘深层关联知识               |

**结构化检索适用场景**：



* 疾病的鉴别诊断（查询疾病→相关症状→相似疾病）

* 药物相互作用（药物 A→代谢酶→药物 B）

* 禁忌症检查（患者疾病→禁忌药物）

* 检查项目选择（症状→可能疾病→需要检查）

* 治疗方案关联（疾病→治疗指南→药物→剂量）

#### 6.2.4 混合检索（多策略融合）

混合检索将向量检索、关键词检索和结构化检索的结果融合，兼顾语义理解、精确匹配和关系推理。



```
混合检索融合流程：

查询输入

&#x20;   │

&#x20;   ├─→ 向量检索 → Top-50候选（带语义相似度分数）

&#x20;   ├─→ 关键词检索 → Top-30候选（带BM25分数）

&#x20;   └─→ 结构化检索 → Top-20候选（带图谱关联度分数）

&#x20;   │

&#x20;   ▼

结果合并（按knowledgeId去重，保留各检索方式的分数）

&#x20;   │

&#x20;   ▼

RRF融合排序（Reciprocal Rank Fusion）

&#x20;   │

&#x20;   │  RRF分数 = Σ 1/(k + rank\_i)

&#x20;   │  k=60（RRF默认参数）

&#x20;   │  rank\_i为该结果在第i种检索方式中的排名

&#x20;   │

&#x20;   ▼

融合后候选集（Top-50，带融合分数）

&#x20;   │

&#x20;   ▼

进入重排序阶段
```

**混合检索优势**：



* 向量检索捕捉语义关联，关键词检索保证精确匹配，结构化检索提供关系推理

* 三种方式互补，显著提升召回率（相比单一检索提升 20-30%）

* RRF 融合算法无需调参，对不同检索方式的分数尺度不敏感

* 支持动态调整各检索方式的权重（如用药查询侧重关键词和图谱，诊断查询侧重向量和图谱）

### 6.3 向量数据库选型与设计

#### 6.3.1 选型决策



| 维度            | Milvus 2.x     | Qdrant           | PostgreSQL + pgvector | 选型结论                                 |
| ------------- | -------------- | ---------------- | --------------------- | ------------------------------------ |
| **部署复杂度**     | 中（分布式架构，组件较多）  | 低（单二进制，Rust 编写）  | 低（随 PostgreSQL 部署）    | PG+pgvector 胜出，医院私有化部署简化运维           |
| **性能（百万级向量）** | 优（分布式扩展，支持十亿级） | 优（HNSW 索引，高性能）   | 良（HNSW 索引，百万级可接受）     | 均满足需求，PG+pgvector 适合医院规模（10-100 万向量） |
| **过滤能力**      | 强（标量过滤 + 向量检索） | 强（Payload 过滤，高效） | 中（SQL WHERE 过滤，灵活）    | 相当，PG+pgvector 的 SQL 过滤更灵活           |
| **数据一致性**     | 中（最终一致性）       | 强（ACID）          | 强（PostgreSQL ACID）    | PG+pgvector 胜出，医疗数据需强一致性             |
| **运维成本**      | 中（需独立集群）       | 低（单节点 / 集群）      | 极低（复用 PG 运维）          | PG+pgvector 胜出                       |
| **生态集成**      | 独立服务，需 API 对接  | 独立服务，需 API 对接    | 原生 SQL，与业务数据同库        | PG+pgvector 胜出，减少系统组件                |
| **扩展性**       | 优（水平扩展）        | 良（垂直扩展 + 分片）     | 中（垂直扩展，分区表）           | Milvus 胜出，但医院规模不需要十亿级                |

**最终选型**：**PostgreSQL + pgvector** 作为向量数据库，理由：



1. 医院知识库规模预计 10-100 万条向量，pgvector 完全满足性能需求

2. 与业务数据同库，保证 ACID 一致性，简化事务管理

3. 复用 PostgreSQL 运维体系，降低医院私有化部署的运维复杂度

4. 支持 SQL 原生过滤，与业务查询无缝集成

5. 如未来规模超千万级，可平滑迁移至 Milvus（向量格式兼容）

&#x20;   token\_count     INTEGER      NOT NULL,             -- 分块Token数

&#x20;   created\_at      TIMESTAMP    NOT NULL DEFAULT CURRENT\_TIMESTAMP,

&#x20;   updated\_at      TIMESTAMP    NOT NULL DEFAULT CURRENT\_TIMESTAMP,

&#x20;   CONSTRAINT uq\_knowledge\_chunk UNIQUE (knowledge\_id, chunk\_id, hospital\_id)

);

\-- 向量索引（HNSW）

CREATE INDEX idx\_knowledge\_embedding\_vector ON knowledge\_embedding

&#x20;   USING hnsw (embedding vector\_cosine\_ops)

&#x20;   WITH (m = 32, ef\_construction = 200);

\-- 标量索引（过滤用）

CREATE INDEX idx\_knowledge\_embedding\_level ON knowledge\_embedding (hospital\_id, knowledge\_level, is\_active);

CREATE INDEX idx\_knowledge\_embedding\_category ON knowledge\_embedding (hospital\_id, category, subcategory);

CREATE INDEX idx\_knowledge\_embedding\_tags ON knowledge\_embedding USING GIN (tags);

CREATE INDEX idx\_knowledge\_embedding\_date ON knowledge\_embedding (publish\_date DESC);

CREATE INDEX idx\_knowledge\_embedding\_authority ON knowledge\_embedding (authority\_level DESC);

\-- 分区（按知识层级分区，L1/L2为全局共享，L3/L4/L5按医院隔离）

\-- 实际部署时可按hospital\_id进一步分区
```

#### 6.3.3 向量检索 SQL 示例



```
\-- 混合检索：向量相似度 + 标量过滤 + 权威性/时效性排序

SELECT

&#x20;   ke.knowledge\_id,

&#x20;   ke.chunk\_id,

&#x20;   ke.content\_chunk,

&#x20;   ke.knowledge\_level,

&#x20;   ke.category,

&#x20;   ke.publish\_date,

&#x20;   ke.version,

&#x20;   ke.authority\_level,

&#x20;   1 - (ke.embedding <=> :query\_embedding) AS similarity,  -- 余弦相似度

&#x20;   -- 综合评分：相似度\*0.6 + 权威性\*0.2 + 时效性\*0.2

&#x20;   (1 - (ke.embedding <=> :query\_embedding)) \* 0.6

&#x20;   \+ (ke.authority\_level / 5.0) \* 0.2

&#x20;   \+ (EXTRACT(YEAR FROM age(CURRENT\_DATE, ke.publish\_date)) < 2)::int \* 0.2

&#x20;   AS combined\_score

FROM knowledge\_embedding ke

WHERE ke.hospital\_id = :hospital\_id

&#x20; AND ke.is\_active = true

&#x20; AND ke.knowledge\_level IN ('L1', 'L2', 'L3')  -- 过滤层级

&#x20; AND ke.publish\_date >= :date\_from               -- 时效性过滤

ORDER BY combined\_score DESC

LIMIT 50;
```

### 6.4 Embedding 模型选型

#### 6.4.1 选型要求

医疗领域 Embedding 模型需满足以下要求：



1. **中文支持**：优秀的中文语义理解能力

2. **医学领域适配**：理解医学术语、临床概念、诊疗逻辑

3. **长文本支持**：支持临床指南、病历等长文本的向量化

4. **私有化部署**：支持本地部署，数据不出院

5. **性能**：推理速度满足实时检索需求（单条 < 50ms）

#### 6.4.2 候选模型对比



| 模型                         | 维度   | 中文能力  | 医学适配        | 长文本       | 部署方式      | 推理速度   | 推荐度      |
| -------------------------- | ---- | ----- | ----------- | --------- | --------- | ------ | -------- |
| **BGE-large-zh-v1.5**      | 1024 | ★★★★★ | ★★★☆（需微调）   | 512token  | 私有化       | 快（GPU） | ★★★★★    |
| **BGE-m3**                 | 1024 | ★★★★★ | ★★★☆（需微调）   | 8192token | 私有化       | 中      | ★★★★☆    |
| **text-embedding-3-large** | 3072 | ★★★★☆ | ★★★★        | 8191token | API（数据出境） | 快      | ★★☆（不合规） |
| **Conan-embedding**        | 1024 | ★★★★★ | ★★★★（医学预训练） | 512token  | 私有化       | 快      | ★★★★☆    |
| **STM-embedding**          | 1024 | ★★★★☆ | ★★★★（医学微调）  | 512token  | 私有化       | 快      | ★★★★☆    |

**最终选型**：**BGE-large-zh-v1.5 + 医学领域微调**

**选型理由**：



1. BGE 系列是开源中文 Embedding 的 SOTA 模型，中文语义理解能力优秀

2. 1024 维向量平衡精度和存储 / 计算成本

3. 支持私有化部署，满足医疗数据不出院要求

4. 使用医学文献、临床指南、病历文本进行领域微调后，医学语义理解能力显著提升

5. 社区活跃，文档完善，易于集成和维护

#### 6.4.3 医学领域微调方案



```
微调数据构建：

├── 医学文献摘要（10万条）：PubMed中文翻译、知网医学论文摘要

├── 临床指南全文（5000+篇）：中华医学会指南、国家卫健委临床路径

├── 医学教材章节（500+章节）：人卫版医学教材核心章节

├── 病历文本（100万份，脱敏）：门诊病历、入院记录、病程记录

├── 医学问答对（50万对）：临床问答、用药咨询、检查解读

└── 医学术语同义词对（10万对）：疾病别名、药物商品名→通用名

微调方法：

├── 基座模型：BGE-large-zh-v1.5

├── 微调方式：LoRA（低秩适应）+ 全量微调两阶段

│   ├── 第一阶段：LoRA微调（医学领域适配，低成本快速迭代）

│   └── 第二阶段：全量微调（精选高质量数据，最终模型固化）

├── 训练目标：对比学习（Contrastive Learning）

│   ├── 正样本：语义相关的医学文本对

│   └── 负样本：语义不相关的医学文本对（硬负样本挖掘）

├── 评估指标：

│   ├── 医学检索Recall@10（目标>90%）

│   ├── 医学问答准确率（目标>85%）

│   └── 医学实体相似度相关性（目标>0.85）

└── 部署：ONNX/TensorRT加速，GPU推理（单条<30ms）
```

### 6.5 分块策略（Chunking）

知识库文档的分块策略直接影响检索精度和上下文构建质量，健澜科技数智医院智能体采用**按文档结构分块 + 重叠窗口**的策略。

#### 6.5.1 分块策略对比



| 分块策略        | 优点            | 缺点                | 适用场景              |
| ----------- | ------------- | ----------------- | ----------------- |
| **固定长度分块**  | 简单，Token 数均匀  | 切断语义单元，丢失上下文      | 无结构文本（如自由文本病历）    |
| **按段落分块**   | 保留段落语义完整性     | 段落长度差异大，超长段落需二次切分 | 有段落结构的文档          |
| **按标题结构分块** | 保留文档层级结构，语义完整 | 需要解析文档结构，实现复杂     | 有明确标题层级的文档（指南、教材） |
| **按语义分块**   | 语义最完整，检索精度最高  | 需要语义分割模型，计算成本高    | 高质量知识库（L2 指南）     |
| **混合分块**    | 兼顾结构和语义，灵活性高  | 实现复杂，需多种策略协同      | 全场景适用（推荐）         |

#### 6.5.2 健澜科技混合分块策略



```
混合分块流程：

文档输入（PDF/Word/HTML/Markdown）

&#x20;   │

&#x20;   ▼

文档结构解析

&#x20;   ├─ 提取标题层级（H1/H2/H3/H4）

&#x20;   ├─ 提取段落、列表、表格

&#x20;   ├─ 识别特殊结构（推荐意见、证据等级、表格、图表说明）

&#x20;   └─ 生成文档结构树

&#x20;   │

&#x20;   ▼

按结构分块（第一级切分）

&#x20;   ├─ 按H2章节切分为大块（Chapter Chunk）

&#x20;   ├─ 每个大块保留章节标题路径（如"高血压防治指南>诊断和评估>诊断标准"）

&#x20;   └─ 大块Token数控制在2000以内

&#x20;   │

&#x20;   ▼

按段落/语义分块（第二级切分）

&#x20;   ├─ 大块内按段落切分（Paragraph Chunk）

&#x20;   ├─ 单段超过500Token时，按句子边界二次切分

&#x20;   ├─ 表格作为独立块保留（Table Chunk），不拆散

&#x20;   ├─ 推荐意见作为独立块保留（Recommendation Chunk），标注证据等级

&#x20;   └─ 每个小块Token数控制在300-500

&#x20;   │

&#x20;   ▼

重叠窗口（Overlap）

&#x20;   ├─ 相邻块之间保留15%重叠（约50-75Token）

&#x20;   ├─ 重叠内容为前一块末尾和后一块开头的完整句子

&#x20;   └─ 避免切断关键语义（如"诊断标准为..."不被切断）

&#x20;   │

&#x20;   ▼

块元数据增强

&#x20;   ├─ 每个块添加：文档标题、章节路径、块序号、总块数

&#x20;   ├─ 添加：知识层级、分类、标签、发布日期、版本、权威性

&#x20;   ├─ 添加：医学实体（疾病、药物、检查、症状）自动抽取结果

&#x20;   └─ 添加：块摘要（对超长块生成1句话摘要，用于检索匹配）

&#x20;   │

&#x20;   ▼

向量化与入库

&#x20;   ├─ 每个块独立向量化（内容+标题路径+摘要）

&#x20;   ├─ 向量和元数据存入knowledge\_embedding表

&#x20;   └─ 建立向量索引和标量索引
```

#### 6.5.3 分块参数配置



| 参数        | 值                       | 说明            |
| --------- | ----------------------- | ------------- |
| **目标块大小** | 400 Token（300-500 范围）   | 平衡检索精度和上下文完整性 |
| **重叠大小**  | 60 Token（15%）           | 相邻块重叠，避免语义切断  |
| **最大块大小** | 800 Token               | 超过则强制二次切分     |
| **最小块大小** | 100 Token               | 小于则合并到相邻块     |
| **表格块**   | 独立保留，不切分                | 表格数据完整性优先     |
| **推荐意见块** | 独立保留，标注证据等级             | 临床核心推荐优先检索    |
| **标题路径**  | 拼接到块内容开头                | 增强块的上下文语义     |
| **块摘要**   | 超长块（>500Token）生成 1 句话摘要 | 提升检索匹配精度      |

### 6.6 检索结果重排序（Re-ranking）

重排序是 RAG 流水线的关键环节，对初检结果进行精细化排序，确保最相关、最权威、最新的知识排在前面。

#### 6.6.1 重排序架构



```
初检结果（Top-50，带融合分数）

&#x20;   │

&#x20;   ▼

┌────────────────────────────────────────────────────────────┐

│  第一阶段：粗筛过滤（快速，<10ms）                          │

│  ├─ 过滤已过期/作废的知识（is\_active=false）                │

│  ├─ 过滤与查询意图不匹配的知识分类（如用药查询过滤解剖学）   │

│  ├─ 过滤低质量/低权威性知识（L5经验知识且无审核）            │

│  └─ 结果缩减至Top-30                                        │

└────────────────────────────────────────────────────────────┘

&#x20;   │

&#x20;   ▼

┌────────────────────────────────────────────────────────────┐

│  第二阶段：Cross-encoder语义重排序（GPU推理，<200ms）       │

│  ├─ 将查询与每个候选块组成"\[查询] \[SEP] \[文档块]"对         │

│  ├─ 输入Cross-encoder模型（BGE-reranker-large或同类）       │

│  ├─ 模型输出查询-文档对的相关性分数（0-1）                   │

│  ├─ 按Cross-encoder分数排序                                  │

│  └─ 结果缩减至Top-10                                         │

└────────────────────────────────────────────────────────────┘

&#x20;   │

&#x20;   ▼

┌────────────────────────────────────────────────────────────┐

│  第三阶段：医疗加权重排序（规则+学习，<10ms）                 │

│  ├─ 权威性加权：L2(×1.2) > L3(×1.1) > L4(×1.0) > L5(×0.8)│

│  ├─ 时效性加权：1年内(×1.2) > 2年内(×1.1) > 3年内(×1.0) > 更久(×0.8) │

│  ├─ 来源加权：官方指南(×1.2) > 专家共识(×1.1) > 教材(×1.0) > 经验(×0.7) │

│  ├─ 患者匹配加权：与当前患者诊断/用药/检验匹配的知识(×1.1)  │

│  ├─ 多样性调整：同一来源/同一主题最多保留2条，避免结果同质化  │

│  └─ 最终排序，输出Top-5                                      │

└────────────────────────────────────────────────────────────┘

&#x20;   │

&#x20;   ▼

最终检索结果（Top-5，带综合分数和各维度分数）
```

| 模型                     | 中文能力  | 医学适配      | 推理速度                | 推荐度   |
| ---------------------- | ----- | --------- | ------------------- | ----- |
| **BGE-reranker-large** | ★★★★★ | ★★★☆（需微调） | 快（GPU 50 条 < 200ms） | ★★★★★ |
| **bge-reranker-v2-m3** | ★★★★★ | ★★★☆      | 中                   | ★★★★☆ |
| **mmarco-mMiniLM**     | ★★★☆  | ★★☆       | 很快                  | ★★★☆  |

### 6.7 医疗 RAG 的特殊要求

医疗场景的 RAG 系统有其特殊要求，确保生成内容的安全性、准确性和可追溯性。

#### 6.7.1 证据追溯（Citation Tracking）

**要求**：AI 生成的每个临床论断必须标注来源，医生可追溯到原始知识文档。

**实现机制**：



1. 检索结果携带完整元数据（knowledgeId、标题、来源、版本、发布日期、页码 / 章节）

2. LLM 生成时，每个论断后标注引用编号 `[1]` `[2]`

3. 回答末尾附 "参考文献" 列表，包含每条引用的完整信息

4. 引用可点击跳转，展示原始知识片段和全文链接

5. 无来源支撑的论断必须标注 "无明确证据支持，建议进一步查证"

6. 系统校验：生成后自动检查引用编号与参考文献列表的一致性，删除无来源的论断

**输出示例**：



```
对于该患者的高血压治疗，建议如下：

1\. 诊断：患者收缩压165mmHg，舒张压98mmHg，符合高血压2级诊断标准\[1]。

2\. 治疗目标：一般高血压患者血压目标<140/90mmHg，能耐受者可降至<130/80mmHg\[1]\[2]。

3\. 药物选择：可选用CCB类药物（如氨氯地平5mg qd），患者合并糖尿病时优先选择ACEI/ARB类\[1]\[3]。

4\. 生活方式干预：限盐（<5g/天）、控制体重、规律运动、戒烟限酒\[1]。

参考文献：

\[1] 中国高血压防治指南（2024年修订版）, 中国高血压联盟, 2024-10

\[2] 中国2型糖尿病防治指南（2024年版）, 中华医学会糖尿病学分会, 2024-05

\[3] 高血压合理用药指南（第3版）, 国家心血管病中心, 2023-08
```

#### 6.7.2 时效性控制（Timeliness Control）

**要求**：确保 AI 引用的知识是当前有效的，不引用已过时 / 作废的指南或药品说明书。

**实现机制**：



1. 每条知识标注生效日期和失效日期，过期知识自动标记 is\_active=false

2. 检索时默认过滤 is\_active=false 的知识，如用户明确要求历史版本才返回

3. 时效性加权：新版本知识排序优先，旧版本知识排序靠后

4. 主动监控：定期检查官方指南更新，新版本发布后自动触发知识更新流程

5. 版本标注：引用时必须标注版本号和发布日期，如 "（2024 年修订版）"

6. 过期警告：如检索到的最新知识已超过 3 年未更新，标注 "该知识已超过 3 年未更新，请注意是否有新版本"

#### 6.7.3 权威性排序（Authority Ranking）

**要求**：高权威性知识优先引用，经验知识不能作为唯一决策依据。

**权威性等级**：



| 等级            | 知识来源                                           | 引用规则                              |
| ------------- | ---------------------------------------------- | --------------------------------- |
| **★★★★★（最高）** | 国家卫健委指南、中华医学会指南、国际权威指南（ACC/AHA/ESC/NCCN）、药品说明书 | 优先引用，可作为主要决策依据                    |
| **★★★★**      | 专家共识、权威教材（人卫版）、临床路径                            | 可引用，作为辅助依据                        |
| **★★★**       | 医院本地规范、科室专科知识、高质量文献（SCI 一区 / NEJM/Lancet）      | 可引用，需标注来源                         |
| **★★**        | 一般文献、医生经验、病例库                                  | 仅作为补充参考，必须标注 "经验知识，仅供参考"，不能作为唯一依据 |
| **★（最低）**     | 网络来源、未审核内容                                     | 不纳入知识库                            |

**实现机制**：



1. 检索结果按权威性加权排序，高权威知识优先

2. 生成回答时，核心论断必须有★★★★及以上知识支撑

3. 引用★★及以下知识时，必须明确标注权威性等级和 "仅供参考"

4. 如某问题仅有★★及以下知识支撑，系统必须提示 "该问题缺乏高权威性证据支持，建议查阅最新指南或咨询专家"

5. 冲突处理时，高权威性知识优先（详见 5.2.3）

#### 6.7.4 冲突处理（Conflict Resolution）

**要求**：当不同来源知识不一致时，AI 必须呈现冲突，不能单方面选择。

**处理策略**（详见 5.2.3）：



1. 检索阶段标记冲突：检测到同一问题存在不同观点时，标记为冲突

2. 上下文构建时保留冲突双方：不提前过滤，将冲突双方都纳入上下文

3. 生成时呈现冲突：明确说明 "不同指南对此有不同建议"，分别呈现各方观点和依据

4. 按权威性推荐：优先推荐高权威性来源的观点，但同时说明其他观点

5. 给出决策建议：建议医生根据患者具体情况（年龄、合并症、耐受性等）选择

6. 标注不确定性：明确表达 "该领域存在争议，尚无统一结论"

**输出示例**：



```
关于该患者的抗血小板治疗疗程，不同指南存在差异：

### 7.2 规则类型

健澜科技 CDS 系统覆盖以下六大类临床规则，每类规则有明确的触发时机、判断逻辑和输出级别。

#### 7.2.1 规则类型总览



| 规则类型          | 规则编号前缀  | 触发时机              | 典型规则数       | 输出级别             |
| ------------- | ------- | ----------------- | ----------- | ---------------- |
| **药物相互作用规则**  | DDI-    | 开医嘱 / 开处方时        | 5000+       | warning/critical |
| **药物过敏规则**    | ALL-    | 开医嘱 / 开处方时        | 基于患者过敏史动态   | critical         |
| **剂量异常规则**    | DOSE-   | 开医嘱 / 开处方时        | 2000+       | warning/critical |
| **禁忌症规则**     | CONTRA- | 开医嘱 / 开处方 / 检查申请时 | 1000+       | critical         |
| **检验危急值规则**   | CRIT-   | 检验结果报告时           | 500+        | critical         |
| **诊疗规范符合度规则** | COMP-   | 病历书写 / 诊疗过程中      | 可配置（病种质控规则） | info/warning     |

#### 7.2.2 药物相互作用规则（DDI）

**规则逻辑**：检测患者当前用药与新开药物之间的相互作用，包括药代动力学相互作用（代谢酶竞争、蛋白结合置换）和药效动力学相互作用（协同 / 拮抗作用）。

**严重程度分级**：



| 级别                  | 说明                | 处理方式                    |
| ------------------- | ----------------- | ----------------------- |
| **contraindicated** | 禁忌合用，可能导致严重不良反应   | 拦截，禁止开具，必须医生确认 override |
| **major**           | 严重相互作用，需密切监测或调整剂量 | 警告，提示医生注意，建议调整方案        |
| **moderate**        | 中度相互作用，需注意监测      | 提醒，提示医生关注               |
| **minor**           | 轻度相互作用，临床意义有限     | 信息提示，不干扰操作              |

**数据来源**：国家药品说明书、Micromedex、Lexicomp、临床药学文献。

#### 7.2.3 药物过敏规则（ALL）

**规则逻辑**：检测新开药物与患者过敏史的匹配，包括药物本身过敏、同类药物交叉过敏、辅料过敏。

**匹配策略**：



1. 精确匹配：药物通用名直接匹配患者过敏史

2. 分类匹配：药物所属药理分类匹配（如青霉素类→所有青霉素类药物）

3. 交叉过敏：已知交叉过敏关系（如青霉素与头孢菌素交叉过敏风险）

4. 成分匹配：药物辅料成分匹配（如磺胺类辅料）

**处理方式**：



* 确认过敏史：critical 级别，拦截，必须医生确认 "已知过敏但仍需使用" 并记录理由

* 可疑过敏史：warning 级别，提醒医生核实过敏史

* 交叉过敏风险：warning 级别，提示交叉过敏风险，建议谨慎使用

#### 7.2.4 剂量异常规则（DOSE）

**规则逻辑**：检测新开药物的剂量、频次、疗程是否在安全范围内，考虑患者年龄、体重、肝肾功能、特殊人群等因素。

**检查维度**：



| 维度        | 检查内容                            |
| --------- | ------------------------------- |
| **单次剂量**  | 单次给药剂量是否在说明书推荐范围内               |
| **日剂量**   | 每日总剂量是否超过最大日剂量                  |
| **频次**    | 给药频次是否合理（如 qd/bid/tid 与药物半衰期匹配） |
| **疗程**    | 用药疗程是否超过推荐疗程（如抗菌药物疗程）           |
| **年龄调整**  | 儿童 / 老年患者剂量是否需调整（按年龄 / 体重计算）    |
| **肾功能调整** | 肾功能不全患者（eGFR 降低）剂量是否需调整         |
| **肝功能调整** | 肝功能不全患者剂量是否需调整                  |
| **特殊人群**  | 孕妇、哺乳期、哺乳期女性用药安全性               |

**处理方式**：



* 超最大剂量：critical 级别，拦截，必须医生确认

* 超推荐剂量但 < 最大剂量：warning 级别，提醒

* 特殊人群未调整：warning 级别，建议调整

* 剂量不足：info 级别，提示（避免治疗不足）

#### 7.2.5 禁忌症规则（CONTRA）

**规则逻辑**：检测新开药物 / 检查 / 治疗是否存在患者相关的禁忌症，包括疾病禁忌症、生理状态禁忌症、检查禁忌症。

**规则分类**：



| 分类          | 示例                                              |
| ----------- | ----------------------------------------------- |
| **疾病禁忌症**   | 胃溃疡患者禁用 NSAIDs；哮喘患者禁用 β 受体阻滞剂；痛风患者禁用噻嗪类利尿剂      |
| **生理状态禁忌症** | 孕妇禁用 ACEI/ARB；哺乳期禁用四环素类；儿童禁用喹诺酮类                |
| **检查禁忌症**   | 肾功能不全患者禁用含碘造影剂（CT 增强）；幽闭恐惧症患者慎用 MRI；起搏器患者禁用 MRI |
| **治疗禁忌症**   | 活动性出血患者禁用抗凝药；严重低血压患者禁用硝酸酯类                      |
| **过敏禁忌症**   | 见药物过敏规则                                         |

**处理方式**：



* 绝对禁忌症：critical 级别，拦截，必须医生确认 override 并记录理由

* 相对禁忌症：warning 级别，提示风险，建议评估获益风险比

#### 7.2.6 检验危急值规则（CRIT）

**规则逻辑**：检验结果报告时，自动检测是否达到危急值阈值，触发危急值通知流程。

**危急值项目示例**：



| 检验项目              | 危急值阈值（成人）                 | 临床意义                    |
| ----------------- | ------------------------- | ----------------------- |
| 血钾                | <2.8 mmol/L 或>6.2 mmol/L  | 严重低钾 / 高钾，可致心律失常 / 心跳骤停 |
| 血钠                | <120 mmol/L 或>160 mmol/L  | 严重低钠 / 高钠，可致意识障碍        |
| 血糖                | <2.2 mmol/L 或>22.2 mmol/L | 严重低血糖 / 高血糖危象           |
| 血钙                | <1.75 mmol/L 或>3.5 mmol/L | 严重低钙 / 高钙，可致抽搐 / 心律失常   |
| 血红蛋白              | <50 g/L                   | 重度贫血，需紧急输血              |
| 白细胞               | <1.0×10⁹/L 或>100×10⁹/L    | 粒细胞缺乏 / 白血病可能           |
| 血小板               | <30×10⁹/L                 | 严重血小板减少，出血风险高           |
| 凝血酶原时间 (PT)       | >30 秒（INR>4.0）            | 严重凝血障碍，出血风险             |
| 活化部分凝血活酶时间 (APTT) | >100 秒                    | 严重内源性凝血障碍               |
| 肌钙蛋白 I            | >0.5 ng/mL（伴胸痛）           | 急性心肌梗死可能                |
| 动脉血气 pH           | <7.2 或>7.6                | 严重酸碱失衡                  |
| 动脉血氧分压 (PaO2)     | <40 mmHg                  | 严重低氧血症                  |

**处理流程**：



1. 检验结果到达时自动匹配危急值规则

2. 匹配成功 → 标记 critical\_value\_flag=true

3. 触发通知：系统消息推送 + 短信通知 + 电话通知（可配置）

4. 通知记录：记录通知时间、通知对象、确认时间、确认人

5. 未确认升级：30 分钟未确认 → 升级通知上级医师 / 科主任

6. 全程记录：危急值从发现到处理的完整时间线记录

#### 7.2.7 诊疗规范符合度规则（COMP）

**规则逻辑**：基于病种诊疗规范和临床路径，检测患者诊疗过程是否符合规范要求，包括必要检查是否完成、关键治疗是否及时、文书要素是否完整。

**规则来源**：



* 国家卫健委临床路径（1212 个病种）

* 中华医学会诊疗指南

* 医院 / 科室自定义诊疗规范

* 单病种质控标准（如 PPGL 质控 18 条规则）

**规则示例（PPGL 嗜铬细胞瘤质控）**：



| 规则编号          | 规则名称                 | 校验类型          | 严重度 | 扣分  |
| ------------- | -------------------- | ------------- | --- | --- |
| COMP-PPGL-008 | 术前 α 受体阻滞剂扩容方案缺失     | 围手术期要素校验      | 严重  | -15 |
| COMP-PPGL-010 | MNs 及 3-MT 生化诊断检查未完成 | 医嘱检测闭环校验      | 一般  | -10 |
| COMP-PPGL-018 | 病理报告缺少转移风险评估要素       | 跨文书一致性校验      | 一般  | -10 |
| COMP-PPGL-006 | 肿瘤部位大小及毗邻关系未记录       | 文书存在性 / 字段一致性 | 一般  | -2  |

**处理方式**：



* 严重违规（如关键治疗缺失）：warning 级别，实时提醒医生补充

* 一般违规：info 级别，记录质控问题，汇总到质控评分

* 实时质控：病历书写过程中实时提示，问题在可修正阶段暴露

* 终末质控：出院 / 归档前全量校验，生成质控报告

### 7.3 规则定义格式与示例

健澜科技 CDS 规则采用**YAML 格式**定义，支持条件表达式、动作定义、严重程度配置，便于非技术人员（医生、药师、质控员）编辑和维护。

#### 7.3.1 规则定义格式规范



```
\# 规则元数据

ruleId: DDI-001                          # 规则唯一编号

ruleName: 华法林与阿司匹林相互作用         # 规则名称

ruleType: drug\_interaction                # 规则类型

version: "1.2.0"                          # 规则版本

status: active                             # 状态：active/inactive/deprecated

author: 药学部-李药师                       # 规则作者

createdAt: "2026-01-15"                   # 创建日期

updatedAt: "2026-06-20"                   # 更新日期

reviewDate: "2026-12-31"                  # 下次审核日期

\# 规则分类与标签

category: 药物相互作用                      # 一级分类

subcategory: 抗凝药与抗血小板药             # 二级分类

tags: \[华法林, 阿司匹林, 出血风险, DDI]    # 标签

severity: major                            # 严重程度：contraindicated/major/moderate/minor

confidence: high                           # 证据置信度：high/medium/low

evidenceLevel: A                           # 证据等级：A/B/C/D

\# 触发条件

trigger:

&#x20; events:                                   # 触发事件

&#x20;   \- order\_create                          # 开医嘱时

&#x20;   \- prescription\_create                   # 开处方时

&#x20; context:                                  # 触发上下文条件

&#x20;   patientAge: ">=18"                      # 成人

&#x20;   encounterType: \[outpatient, inpatient]  # 门诊/住院

\# 规则条件（When）

conditions:

&#x20; operator: AND                             # 条件组合：AND/OR/NOT

&#x20; rules:

&#x20;   \- field: new\_order.drug\_category        # 新开药物分类

&#x20;     operator: equals                       # 操作符：equals/not\_equals/in/not\_in/gt/lt/gte/lte/contains/regex

&#x20;     value: "anticoagulant"                # 抗凝药

&#x20;   \- field: new\_order.drug\_generic\_name    # 新开药物通用名

&#x20;     operator: in

&#x20;     value: \["华法林", "warfarin"]

&#x20;   \- field: active\_medications.drug\_category # 患者当前用药分类

&#x20;     operator: contains

&#x20;     value: "antiplatelet"                  # 抗血小板药

&#x20;   \- field: active\_medications.drug\_generic\_name

&#x20;     operator: contains

&#x20;     value: \["阿司匹林", "aspirin", "氯吡格雷", "clopidogrel"]

\# 规则动作（Then）

actions:

&#x20; \- action: alert                            # 动作类型：alert/warn/block/suggest/log

&#x20;   severity: major                          # 提醒级别

&#x20;   title: "药物相互作用警告"                 # 提醒标题

&#x20;   message: |                               # 提醒内容（支持模板变量）

### 7.5 规则冲突解决策略

当多条规则同时触发或规则之间存在矛盾时，CDS 系统采用以下策略解决冲突，确保输出清晰、不矛盾、可操作。

#### 7.5.1 冲突类型与解决策略



| 冲突类型       | 说明                               | 解决策略                                                          |
| ---------- | -------------------------------- | ------------------------------------------------------------- |
| **严重度冲突**  | 多条规则触发，严重程度不同                    | 按严重度排序展示，critical 优先，warning 其次，info 最后；critical 规则必须处理，其他可折叠 |
| **同类规则重复** | 多条规则描述同一问题（如不同来源的 DDI 规则）        | 合并为一条提醒，展示所有来源依据；取最高严重度                                       |
| **建议矛盾**   | 不同规则给出矛盾的处理建议                    | 不合并，分别展示各方建议和依据；标注 "存在不同建议，请医生判断"；按权威性排序推荐                    |
| **规则条件重叠** | 规则 A 和规则 B 的条件部分重叠，导致同一问题被多条规则覆盖 | 规则设计时避免重叠（规则审核环节检查）；运行时合并相似提醒                                 |
| **新旧版本冲突** | 规则库更新后，新旧规则对同一问题有不同判断            | 使用当前有效版本（is\_active=true），旧版本标记为已过期不执行                        |
| **患者特殊情况** | 规则建议与患者特殊情况矛盾（如禁忌但必须用）           | 展示规则警告，同时提示 "患者存在特殊情况，如确需使用请 override 并记录理由"                  |

#### 7.5.2 规则优先级排序算法



```
规则触发列表（N条）

&#x20;   │

&#x20;   ▼

第1步：严重度排序（最高优先级）

&#x20;   critical > major > moderate > minor > info

&#x20;   │

&#x20;   ▼

第2步：同严重度内按权威性排序

&#x20;   药品说明书 > 官方指南 > 专家共识 > 医院规范 > 文献证据 > 经验

&#x20;   │

&#x20;   ▼

第3步：同权威度按时效性排序

&#x20;   1年内 > 2年内 > 3年内 > 更久

&#x20;   │

&#x20;   ▼

第4步：相似规则合并

&#x20;   合并描述同一问题的规则，保留所有来源和依据

&#x20;   │

&#x20;   ▼

第5步：输出排序结果

&#x20;   Top-N展示（默认Top-5，critical全部展示）

&#x20;   每条规则携带：严重度、标题、内容、依据、建议、操作选项
```

### 7.6 CDS 与 Agent 的集成方式

CDS 系统与健澜科技数智医院智能体深度集成，通过三种方式为 AI 智能体提供临床决策支持能力。

#### 7.6.1 集成方式总览



| 集成方式                                  | 说明                         | 适用场景                | 触发方式          |
| ------------------------------------- | -------------------------- | ------------------- | ------------- |
| **工具调用（Tool Call）**                   | CDS 作为 AI 工具，AI 主动调用获取决策支持 | 鉴别诊断、治疗方案、检验解读、用药咨询 | AI 根据用户意图自动调用 |
| **主动提醒（Proactive Alert）**             | CDS 独立监控，主动向 AI 和医生推送提醒    | 危急值、风险预警、医嘱到期、规范违规  | 事件触发，自动推送     |
| **拦截确认（Interception & Confirmation）** | CDS 在关键操作节点拦截，要求医生确认       | 开禁忌药、超剂量、严重 DDI     | 操作触发，同步拦截     |

CDS 能力封装为 AI 工具，供智能体在诊疗对话中主动调用：

#### 7.6.3 主动提醒集成

CDS 系统独立运行，在检测到需要关注的临床事件时，主动推送给 AI 智能体和医生：

**主动提醒场景**：



| 场景       | 触发条件                   | 提醒对象     | 提醒方式           |
| -------- | ---------------------- | -------- | -------------- |
| 危急值通知    | 检验结果达到危急值阈值            | 主治医生、护士  | 系统弹窗 + 短信 + 电话 |
| 患者风险预警   | 多参数分析识别高危患者（脓毒症、AKI 等） | 管床医生、护士  | 系统消息 + 患者列表标记  |
| 医嘱到期提醒   | 长期医嘱到达审核周期（如 7 天）      | 管床医生     | 系统消息 + 待办任务    |

## 8. 数据安全与隐私保护

### 8.1 数据分级分类标准

健澜科技数智医院智能体建立完善的数据分级分类标准，对所有医疗数据进行统一标识和差异化保护，符合《数据安全法》《个人信息保护法》《医疗卫生机构网络安全管理办法》要求。

#### 8.1.1 数据分级标准



| 级别     | 名称   | 定义                                            | 典型数据                                       | 保护要求                                                    |
| ------ | ---- | --------------------------------------------- | ------------------------------------------ | ------------------------------------------------------- |
| **L4** | 机密数据 | 一旦泄露 / 篡改 / 丢失，会对患者生命安全、医院核心利益或社会公共利益造成特别严重危害 | 身份证号、银行卡号、基因信息、生物识别数据、HIV / 精神疾病等特殊诊断、核心密钥 | 加密存储 + 加密传输 + 严格访问控制 + 全程审计 + 脱敏展示，禁止进入 LLM 上下文（除非明确授权） |
| **L3** | 敏感数据 | 一旦泄露 / 篡改 / 丢失，会对患者权益或医院利益造成严重危害              | 患者姓名、出生日期、联系方式、住址、病历全文、诊断信息、检验检查结果、医嘱处方    | 加密存储 + 加密传输 + 授权访问 + 审计日志 + 脱敏展示，进入 LLM 上下文需脱敏          |
| **L2** | 内部数据 | 仅限院内使用，泄露会造成一定影响                              | 医院规章制度、操作规程、药品目录、质控规则、系统配置、非敏感统计数据         | 院内网络访问 + 身份认证 + 操作审计，不对外公开                              |
| **L1** | 公开数据 | 可对外公开，无敏感性                                    | 医学科普知识、公开指南、药品说明书（公开版）、医院公开信息              | 公开访问，基础安全保护                                             |

#### 8.1.2 数据分类标准



| 分类          | 子类                      | 说明        | 默认分级  |
| ----------- | ----------------------- | --------- | ----- |
| **患者个人信息**  | 基本信息、联系方式、身份标识、生物特征     | 患者 PII 数据 | L3-L4 |
| **医疗健康数据**  | 病历、诊断、检验、检查、医嘱、处方、手术、随访 | 核心诊疗数据    | L3    |
| **基因与生物数据** | 基因检测、生物样本、生物识别          | 特殊敏感数据    | L4    |
| **医疗费用数据**  | 费用明细、医保结算、收费记录          | 费用相关数据    | L3    |
| **医院运营数据**  | 规章制度、操作规程、质控数据、统计报表     | 医院管理数据    | L2-L3 |
| **系统安全数据**  | 用户账号、权限配置、密钥、审计日志、安全策略  | 系统安全相关    | L2-L4 |
| **医学知识数据**  | 指南、文献、教材、知识库、药品说明书      | 知识资产      | L1-L2 |
| **AI 模型数据** | 训练数据、模型参数、提示词、向量数据      | AI 相关     | L2-L3 |

#### 8.1.3 数据分级标识与执行



* **元数据标注**：每个数据字段在数据模型中标注 data\_level（见 2.1 患者表设计），驱动自动化保护策略

* **自动分级**：新数据入库时，基于分类规则和敏感信息识别（NLP + 正则）自动推荐分级，人工审核确认

* **分级变更**：数据分级可根据使用场景动态调整（如科研场景下的脱敏数据可降级），变更需审批并记录

* **策略联动**：数据分级结果自动联动加密策略、访问控制、脱敏规则、审计要求、留存期限

### 8.2 敏感字段加密存储（AES-256）

#### 8.2.1 加密策略



| 数据分级      | 加密要求             | 加密算法                      | 密钥管理                          |
| --------- | ---------------- | ------------------------- | ----------------------------- |
| **L4 机密** | 必须加密存储，字段级加密     | AES-256-GCM（认证加密）         | 医院 KMS（密钥管理系统），主密钥 + 数据密钥双层加密 |
| **L3 敏感** | 必须加密存储，字段级或表空间加密 | AES-256-GCM / AES-256-CBC | 医院 KMS                        |
| **L2 内部** | 建议加密存储，表空间加密     | AES-256（TDE 透明数据加密）       | 数据库加密密钥                       |
| **L1 公开** | 不要求加密            | -                         | -                             |

#### 8.2.2 加密字段清单



| 实体                | 加密字段                                               | 加密方式              | 说明                            |
| ----------------- | -------------------------------------------------- | ----------------- | ----------------------------- |
| **Patient**       | id\_card, phone, address, emergency\_contact.phone | AES-256-GCM 字段级加密 | 直接标识符（PII），加密存储，支持精确查询（加密值索引） |
| **Patient**       | name, birth\_date                                  | AES-256 加密存储      | 准标识符，加密存储，展示时脱敏               |
| **Encounter**     | chief\_complaint                                   | AES-256 加密        | 含患者健康信息                       |
| **MedicalRecord** | content（自由文本部分）                                    | AES-256 加密        | 病历全文含大量敏感信息                   |
| **Prescription**  | diagnosis                                          | AES-256 加密        | 诊断信息                          |
| **Session**       | medical\_context, summary                          | AES-256 加密        | 含患者诊疗信息                       |
| **Message**       | content（含患者信息的部分）                                  | AES-256 加密        | 对话内容可能含敏感信息                   |
| **AuditLog**      | input\_params（含患者信息的参数）                            | AES-256 加密        | 审计日志可能记录敏感参数                  |

#### 8.2.3 密钥管理体系



```
密钥管理架构（双层加密）：

┌────────────────────────────────────────────────────────────┐

│  医院KMS（密钥管理系统）                                     │

│  ┌──────────────────────────────────────────────────────┐ │

│  │ 主密钥（Master Key, MK）                               │ │

│  │ - 存储在硬件安全模块（HSM）中，不可导出                │ │

│  │ - 每年轮换一次，旧密钥保留用于解密历史数据              │ │

│  │ - 访问需多人授权（M-of-N）                             │ │

│  └──────────────────────────────────────────────────────┘ │

│                         │ 加密/解密                          │

│                         ▼                                    │

│  ┌──────────────────────────────────────────────────────┐ │

│  │ 数据密钥（Data Encryption Key, DEK）                  │ │

│  │ - 由主密钥加密后存储在数据库中                         │ │

│  │ - 每个租户/每个表空间一个DEK                           │ │

│  │ - 每90天轮换一次，旧DEK保留用于解密                    │ │

│  └──────────────────────────────────────────────────────┘ │

└────────────────────────────────────────────────────────────┘

&#x20;                        │ 加密/解密

&#x20;                        ▼

&#x20;             应用层字段加密/解密

&#x20;                        │

&#x20;                        ▼

&#x20;             数据库存储加密后的数据
```

**密钥管理要求**：



1. **HSM 存储**：主密钥存储在硬件安全模块（HSM）中，不可导出，符合等保三级要求

2. **双人授权**：主密钥访问需至少 2 人授权（M-of-N 机制），防止单人操作

3. **定期轮换**：主密钥每年轮换，数据密钥每 90 天轮换，轮换过程不影响业务（旧密钥保留解密）

4. **密钥审计**：所有密钥操作（创建、轮换、使用、销毁）记录审计日志

5. **密钥备份**：密钥分片备份，异地存储，恢复需多人协作

6. **应用层加密**：加密 / 解密在应用层完成，数据库只存储密文，即使数据库泄露也无法解密

#### 8.2.4 加密查询支持

加密字段需要支持查询，采用以下策略：



* **精确查询**：对加密字段生成 "盲索引"（Blind Index），存储字段值的 HMAC-SHA256 哈希，查询时先哈希再匹配，不暴露明文

* **模糊查询**：敏感字段不支持模糊查询（如身份证号、手机号），如需查询使用精确匹配

* **范围查询**：出生日期等支持范围查询的字段，使用保序加密（OPE）或分桶索引

* **解密展示**：查询结果在应用层解密，根据用户权限决定返回明文或脱敏值

### 8.3 数据传输加密（TLS 1.3）

#### 8.3.1 传输加密策略



| 传输场景                      | 加密协议                | 加密套件                                                      | 证书要求                                  |
| ------------------------- | ------------------- | --------------------------------------------------------- | ------------------------------------- |
| **用户端→应用服务器**             | TLS 1.3（最低 TLS 1.2） | ECDHE-ECDSA-AES256-GCM-SHA384、ECDHE-RSA-AES256-GCM-SHA384 | 医院 CA 签发的 SSL 证书，支持国密 SM2/SM3/SM4（可选） |
| **应用服务器→数据库**             | TLS 1.3 + 数据库原生加密   | AES-256-GCM                                               | 数据库服务器证书，双向认证                         |
| **应用服务器→对象存储**            | TLS 1.3 + S3 加密     | AES-256-GCM                                               | 对象存储服务证书                              |
| **应用服务器→AI 模型服务**         | TLS 1.3 + mTLS 双向认证 | AES-256-GCM                                               | 双向证书认证，确保模型服务身份                       |
| **服务间调用（微服务）**            | mTLS 双向认证（TLS 1.3）  | AES-256-GCM                                               | 服务间双向证书，SPIFFE/SPIRE 身份管理             |
| **与 HIS/EMR/LIS/PACS 集成** | TLS 1.3 + VPN 专网    | AES-256-GCM                                               | 医院内网 VPN + TLS 双层加密                   |
| **消息队列**                  | TLS 1.3 + 消息体加密     | AES-256-GCM                                               | 消息中间件证书                               |

#### 8.3.2 传输安全要求



1. **协议版本**：强制 TLS 1.3，最低支持 TLS 1.2，禁用 SSL v3、TLS 1.0、TLS 1.1

2. **加密套件**：仅启用前向保密（PFS）套件，禁用弱加密（RC4、3DES、CBC 模式优先 GCM）

3. **证书管理**：使用医院 CA 签发证书，证书有效期≤1 年，自动轮换，禁用自签名证书（测试环境除外）

4. **国密支持**：支持国密算法（SM2/SM3/SM4），满足等保三级和医疗行业国密要求

5. **HSTS**：启用 HTTP Strict Transport Security，强制 HTTPS，max-age≥1 年

6. **证书固定**：移动端和关键服务启用证书固定（Certificate Pinning），防止中间人攻击

7. **内网加密**：内网服务间通信也启用 TLS 加密（零信任架构），不假设内网安全

8. **VPN 专网**：与外部系统（HIS/EMR 等）集成通过医院 VPN 专网，双层加密

### 8.4 数据脱敏规则

数据脱敏是保护患者隐私的关键措施，健澜科技数智医院智能体在数据展示、AI 上下文构建、数据导出等场景执行差异化脱敏。

#### 8.4.1 脱敏规则矩阵



| 字段         | 脱敏规则                     | 示例（明文→脱敏）                                                                  | 应用场景            |
| ---------- | ------------------------ | -------------------------------------------------------------------------- | --------------- |
| **姓名**     | 保留姓氏，名替换为 \*             | 李秀英 → 李*英；张三 → 张*                                                          | 列表展示、AI 上下文     |
| **身份证号**   | 保留前 3 位和后 4 位，中间 \*      | 330106196803151234 → 330\*\*\*\*\*\*\*\*\*\*\*1234                         | 所有场景（机密字段默认不展示） |
| **手机号**    | 保留前 3 位和后 4 位，中间 \*      | 13812345678 → 138\*\*\*\*5678                                              | 列表展示、AI 上下文     |
| **住址**     | 保留到区 / 县，详细地址 \*         | 杭州市西湖区文三路 123 号 → 杭州市西湖区 \*\*\*\*                                          | 列表展示            |
| **出生日期**   | 保留年份，月日 \*（或仅显示年龄）       | 1968-03-15 → 1968-**-**（或 58 岁）                                            | 列表展示、AI 上下文     |
| **病历号**    | 保留前 2 位和后 2 位            | P20260914001 → P2\*\*\*\*\*\*\*\*01                                        | 非授权场景           |
| **邮箱**     | 保留首字母和域名                 | lixiuying@example.com → l\*\*\*\*\*\*\*@[example.com](https://example.com) | 所有场景            |
| **银行卡号**   | 保留后 4 位                  | 6222021234567890123 → \*\*\*\*\*\*\*\*\*\*\*\*\*\*\*0123                   | 所有场景（默认不展示）     |
| **诊断（特殊）** | HIV / 精神疾病 / 性病等特殊诊断默认隐藏 | HIV 感染 → 特殊感染（需授权查看）                                                       | 非授权场景           |
| **病历全文**   | 自由文本中自动识别并脱敏 PII         | "患者李秀英，身份证 330...，电话 138..." → " 患者李*英，身份证 330*\*\*\*，电话 138\*\*\*\*..."   | AI 上下文、数据导出     |

#### 8.4.2 脱敏执行场景



| 场景           | 脱敏级别  | 说明                                    |
| ------------ | ----- | ------------------------------------- |
| **列表页展示**    | 标准脱敏  | 姓名、手机号、身份证等按规则脱敏                      |
| **详情页展示**    | 按权限脱敏 | 有权限的医生可查看明文，无权限查看脱敏值                  |
| **AI 上下文构建** | 强制脱敏  | 所有进入 LLM 的患者数据必须脱敏，机密字段（身份证、地址）不进入上下文 |
| **AI 生成输出**  | 输出后还原 | AI 生成的病历等内容，在医生界面还原为明文（医生有权限）         |
| **数据导出**     | 按用途脱敏 | 科研导出需脱敏到不可识别个人，业务导出按权限                |
| **日志记录**     | 强制脱敏  | 所有日志中不记录明文 PII，参数脱敏后记录                |
| **测试环境**     | 完全脱敏  | 测试环境使用脱敏 / 合成数据，禁止真实患者数据              |
| **科研使用**     | 去标识化  | 去除所有直接标识符，准标识符泛化（年龄→年龄段），满足去标识化标准     |

#### 8.5.1 审计范围

健澜科技数智医院智能体对所有数据访问操作进行全程审计，审计范围包括：

| **密钥操作**    | 密钥创建、轮换、使用、销毁                 | 每次密钥操作记录（HSM 审计）             |

#### 8.5.3 审计日志管理要求



| 要求        | 说明                                                        |
| --------- | --------------------------------------------------------- |
| **不可篡改**  | 审计日志采用追加写入（Append-only），禁止修改和删除；使用哈希链确保日志完整性              |
| **留存期限**  | 审计日志在线保留≥6 个月，归档保留≥3 年（符合《网络安全法》等保三级要求）；医疗操作相关审计建议保留≥15 年 |
| **实时写入**  | 审计操作实时写入，不允许批量延迟写入（防止日志丢失）                                |
| **独立存储**  | 审计日志独立存储，与业务数据分离，审计日志库权限严格控制                              |
| **防删除保护** | 审计日志表禁止 DELETE 和 UPDATE 操作，仅允许 INSERT；数据库层面设置触发器保护        |
| **完整性校验** | 每日对审计日志进行哈希校验，检测是否被篡改；校验结果记录                              |
| **审计查询**  | 支持按时间、用户、患者、操作类型等多维度查询审计日志；审计查询本身也记录审计                    |
| **告警机制**  | 异常访问行为自动告警（如非工作时间大量查询、跨科室访问、短时间内查询大量不同患者）                 |

### 8.6 数据留存与销毁策略

#### 8.6.1 数据留存期限



| 数据类型            | 留存期限                            | 法律依据                    | 到期处理                        |
| --------------- | ------------------------------- | ----------------------- | --------------------------- |
| **门诊病历**        | ≥15 年                           | 《医疗机构病历管理规定》            | 到期后归档至冷存储，继续保存（建议永久保存数字化病历） |
| **住院病历**        | ≥30 年                           | 《医疗机构病历管理规定》            | 到期后归档至冷存储，继续保存              |
| **检验检查报告**      | ≥15 年                           | 《医疗机构病历管理规定》            | 与病历同期保存                     |
| **医嘱处方**        | ≥15 年（普通处方≥1 年，麻醉 / 精神药品处方≥3 年） | 《处方管理办法》                | 到期后按规定销毁                    |
| **影像数据（DICOM）** | ≥15 年（建议≥30 年）                  | 《医疗机构病历管理规定》、PACS 行业规范  | 冷存储归档，继续保存                  |
| **录音文件（ADS）**   | ≥15 年（与病历同期）                    | 病历管理规定（原始资料留存）          | 加密归档，继续保存                   |
| **AI 会话记录**     | ≥15 年（与关联病历同期）                  | 病历管理规定（AI 生成内容作为病历辅助资料） | 到期后归档                       |
| **审计日志**        | 在线≥6 个月，归档≥3 年                  | 《网络安全法》、等保三级            | 到期后安全销毁                     |
| **系统日志**        | ≥6 个月                           | 等保三级                    | 到期后安全销毁                     |
| **缓存数据（Redis）** | 会话结束后 24 小时自动清除                 | 数据最小化原则                 | 自动过期清除                      |
| **临时文件**        | 处理完成后立即删除                       | 数据最小化原则                 | 自动清理                        |
| **备份数据**        | 全量备份保留 30 天，逻辑备份保留 90 天         | 备份策略                    | 到期后安全销毁                     |

#### 8.6.2 数据销毁策略



| 销毁场景       | 销毁方式                        | 销毁要求                           |
| ---------- | --------------------------- | ------------------------------ |
| **到期数据销毁** | 加密擦除（Cryptographic Erasure） | 删除数据加密密钥，使密文不可解密；存储介质覆写 3 次以上  |
| **患者要求删除** | 按个保法要求删除（见 8.7）             | 删除患者可识别个人信息，匿名化的统计数据可保留        |
| **存储介质报废** | 物理销毁（消磁 + 粉碎）               | 硬盘消磁后物理粉碎，出具销毁证明，双人监督          |
| **云存储删除**  | 多副本删除 + 密钥销毁                | 删除所有副本，销毁加密密钥，确认不可恢复           |
| **缓存清除**   | 主动删除 + 过期自动清除               | Redis DEL 命令 + TTL 过期，确认内存中无残留 |
| **备份销毁**   | 安全擦除 + 记录                   | 备份磁带消磁粉碎，云备份删除所有版本，记录销毁过程      |

**销毁流程**：



1. 销毁申请：数据管理员提出销毁申请，说明销毁数据范围、原因、依据

2. 审批：信息科主任 + 医务处主任双重审批

3. 执行：双人执行销毁操作，全程记录

4. 验证：销毁后验证数据不可恢复（抽样检查）

5. 记录：出具销毁报告，记录销毁时间、范围、方式、执行人、监督人

6. 归档：销毁报告归档保存≥10 年

### 8.7 患者数据导出与删除权（GDPR / 个人信息保护法合规）

健澜科技数智医院智能体全面支持《中华人民共和国个人信息保护法》赋予患者的个人信息权利，包括知情权、查阅权、复制权、更正权、删除权等。

#### 8.7.1 患者权利实现矩阵



| 患者权利         | 法律依据      | 实现方式                                      | 处理时限        |
| ------------ | --------- | ----------------------------------------- | ----------- |
| **知情权**      | 个保法第 17 条 | 隐私政策告知：收集什么数据、为什么收集、如何使用、保存多久、患者权利        | 就诊前告知       |
| **查阅权**      | 个保法第 45 条 | 患者可通过 APP / 自助机 / 窗口申请查阅本人病历和诊疗记录         | ≤15 个工作日    |
| **复制权（导出权）** | 个保法第 45 条 | 患者可申请导出本人全部健康数据，支持标准格式（FHIR JSON/XML、PDF） | ≤15 个工作日    |
| **更正权**      | 个保法第 46 条 | 患者认为信息不准确 / 不完整，可申请更正；医院核实后予以更正           | ≤15 个工作日    |
| **删除权**      | 个保法第 47 条 | 符合法定情形时，患者可申请删除个人信息                       | ≤15 个工作日    |
| **可携带权**     | 个保法第 45 条 | 导出数据采用通用格式（FHIR），可转移至其他医疗机构               | ≤15 个工作日    |
| **解释说明权**    | 个保法第 48 条 | 患者可要求对个人信息处理规则进行解释说明                      | 即时 /≤7 个工作日 |
| **投诉举报权**    | 个保法第 50 条 | 提供投诉渠道，患者可向医院或监管部门投诉                      | 即时受理        |

#### 8.7.2 患者数据导出实现

**导出流程**：



```
患者申请导出个人健康数据

&#x20;   │

&#x20;   ▼

身份验证（实名认证+人脸识别，确保本人操作）

&#x20;   │

&#x20;   ▼

导出范围选择

&#x20;   ├─ 基本信息

&#x20;   ├─ 门诊记录（全部/指定时间段）

&#x20;   ├─ 住院记录（全部/指定住院）

&#x20;   ├─ 检验检查报告

&#x20;   ├─ 医嘱处方记录

&#x20;   ├─ 影像数据（DICOM）

&#x20;   └─ AI诊疗辅助记录（AI会话、AI生成病历）

&#x20;   │

&#x20;   ▼

数据导出处理

&#x20;   ├─ 从各业务系统归集患者全部数据

&#x20;   ├─ 数据格式转换为标准格式（FHIR R4 JSON/XML）

&#x20;   ├─ 生成数据清单和说明文档

&#x20;   ├─ 数据加密（AES-256加密压缩包）

&#x20;   └─ 生成数字签名（医院CA签名，确保数据完整性和来源可信）

&#x20;   │

&#x20;   ▼

导出交付

&#x20;   ├─ 加密压缩包下载链接（有效期7天，需密码解压）

&#x20;   ├─ 纸质光盘/U盘（窗口领取，需身份验证）

&#x20;   └─ 直接传输至患者指定的其他医疗机构（需患者授权）

&#x20;   │

&#x20;   ▼

审计记录（导出人、导出范围、导出时间、交付方式、数据量）
```

**导出格式**：



* **结构化数据**：HL7 FHIR R4 JSON 格式（Patient、Encounter、Observation、MedicationRequest 等资源）

* **病历文档**：PDF + CDA（临床文档架构）双格式

* **影像数据**：DICOM 标准格式

* **数据字典**：Excel 格式，说明各字段含义

* **说明文档**：PDF，说明数据范围、时间跨度、使用注意事项

#### 8.7.3 患者数据删除权实现

**删除权适用情形**（个保法第 47 条）：



1. 处理目的已实现、无法实现或不再必要

2. 医院停止提供产品或服务，或保存期限已届满

3. 患者撤回同意

4. 医院违反法律、行政法规或违反约定处理个人信息

5. 法律、行政法规规定的其他情形

**删除流程**：



```
患者申请删除个人信息

&#x20;   │

&#x20;   ▼

身份验证（实名认证+人脸识别）

&#x20;   │

&#x20;   ▼

删除申请受理（记录申请时间、申请人、删除范围、删除理由）

&#x20;   │

&#x20;   ▼

合法性审核

&#x20;   ├─ 是否属于法定不得删除的情形（如病历法定保存期未满）

&#x20;   ├─ 是否涉及公共利益、他人合法权益

&#x20;   └─ 删除是否影响医疗安全和连续性

&#x20;   │

&#x20;   ▼

审核结果

&#x20;   ├─ 同意删除 → 执行删除（见下）

&#x20;   ├─ 部分删除 → 删除可删除部分，保留法定必须保存部分，告知患者

&#x20;   └─ 不同意删除 → 书面说明理由，告知患者投诉渠道

&#x20;   │

&#x20;   ▼

执行删除（如同意）

&#x20;   ├─ 删除患者直接标识符（姓名、身份证、手机号等）→ 匿名化处理

&#x20;   ├─ 解除数据与患者身份的关联（无法重新识别到个人）

&#x20;   ├─ 删除AI会话中的患者可识别信息

&#x20;   ├─ 删除缓存中的患者数据

&#x20;   ├─ 备份数据中的患者数据在备份到期后删除（或提前删除）

&#x20;   └─ 注意：法定保存期内的病历不得删除，但可进行匿名化/去标识化处理

&#x20;   │

&#x20;   ▼

删除验证

&#x20;   ├─ 验证患者可识别信息已删除/匿名化

&#x20;   ├─ 验证无法通过剩余数据重新识别患者

&#x20;   └─ 验证备份中的处理（标记待删除）

&#x20;   │

&#x20;   ▼

通知患者删除完成（书面通知，说明删除范围、时间、方式）

&#x20;   │

&#x20;   ▼

审计记录（删除申请、审核、执行、验证全过程）
```

**匿名化标准**：



* 删除所有直接标识符（姓名、身份证号、手机号、住址、病历号）

* 准标识符泛化（出生日期→出生年份，地址→省 / 市）

* 确保无法通过剩余数据（结合其他可用信息）重新识别到特定个人

* 匿名化后的数据可保留用于统计分析和科研（不再属于个人信息）

**不得删除的情形**：



1. 病历在法定保存期限内（门诊≥15 年，住院≥30 年）—— 但可匿名化

2. 涉及未解决的医疗纠纷、诉讼

3. 公共卫生监测需要

4. 法律、行政法规规定的其他不得删除的情形
